## 決まっている事（問いではない）

- 判定の核（CoverageJudge）は時計・乱数・識別子を読まず、行の割合は行ごとの記録から再計算する（NFR2、FR2.3）。道具が最後に出した割合の数字は信じない。
- 結果は「一致・不一致・観測できず」の 3 値。観測できずを一致に読み替えない（FR4.2）。入口の終了コードは 0（落とさない）・1（落とす）・2（入力不正か入口の失敗）（契約 2）。
- 子プロセスの行が数えられない組み合わせは使わない。この単位の Node 組込みの形では、実測で数えられたので使える。
- 再試行しない（契約 6）。期限か総予算を超えたら「観測できず」。
- 既定の閾値は行 100%。この単位は閾値の例外・「記録だけ」・除外を持たない（U4・U5）。
- 入力の JSON の未知の項目は入力不正（契約 2 の仮定）。分母が 0 件に解決されるときも、成功と読まず入力不正にする（取り組みの学びの記録に従う）。

## Q1. [試験の失敗] 試験が 1 つ失敗したとき、門はどう扱うか

門は `node --test` を自分で流して網羅率を測ります。ところが、試験が 1 つ失敗した実行の網羅率は、失敗した試験が通らなかった分だけ行が少なく出ます。必須の試験が「流れた」とは何かも、ここで決める必要があります。

たとえば、利用先の試験 file が 10 本あり、そのうち 1 本の試験が 1 つ失敗したとします。

- 失敗を測定の失敗として扱えば、門の結果は「観測できず」になり、利用先は試験を直して流し直します。行の割合の数字は出ません。
- 失敗を測定の失敗にしなければ、残りの試験で行の割合が出ます（その数字は、失敗した試験の分だけ低い可能性があります）。試験の失敗は別の job が見張る、という分担になります。

また、試験 file の中身がすべて skip か todo の場合や、file の読み込みで失敗した場合に、その file を「流れた」と数えるかも決めます。

- A. 試験が 1 つでも失敗（読み込みの失敗を含む）したら、測定の失敗として「観測できず」にする。「流れた」とは、skip でも todo でもない試験が 1 件以上合格した file だけを指す。すべて skip・todo の file は NOT_RUN
- B. 試験の失敗は測定の失敗にしない。網羅率は得られた記録で計算する。「流れた」とは、skip でも todo でもない試験が 1 件以上実行された（合否を問わない）file を指す。読み込みに失敗した file と、すべて skip・todo の file は NOT_RUN
- C. 設計の段で決める

## Q2. [割合の表し方] 行の割合は、どう比較して、どう表示するか

行の割合は「数えられた行の数」と「全部の行の数」から再計算します。閾値は 100% が既定なので、1 行でも足りなければ成功にならないはずです。表示のために小数に丸めると、足りないのに 100% と見えることがあります。

たとえば、全部で 20,000 行のうち 19,999 行が数えられたとき、割合は 99.995% です。小数第 2 位に四捨五入すると 100.00 と表示されます。切り捨てなら 99.99 と表示されます。

- A. 比較は整数どうしで厳密に行う（数えられた行 × 100 が、全部の行 × 閾値以上か）。表示と JSON の割合は、小数第 2 位で切り捨てる（足りない時に 100 と表示しない）。数えられた行の数と全部の行の数も JSON に残す
- B. 比較は整数どうしで厳密に行う。表示と JSON の割合は、小数第 2 位に四捨五入する。数えられた行の数と全部の行の数も JSON に残す

## Q3. [期限と総予算の既定] 呼ぶ側が書かなかったときの、測定の期限と総予算はいくつか

測定は子プロセスで行い、期限（1 回の測定）と総予算（測定全体）を超えたら「観測できず」になります（FR4.4）。入力では省略でき、省略したときの値は 1 か所に決めて置きます（契約 2）。値が小さすぎると、普通の repo の試験が時間切れで「観測できず」になります。大きすぎると、止まった測定が CI の時間を長く使います（新しい費用は足さない、NFR11）。

たとえば、利用先の試験が 3 分かかる repo は、期限が 120 秒だと毎回「観測できず」になり、利用先が自分で入力に長い期限を書くことになります。

- A. 期限 600 秒、総予算 900 秒（契約の概要の例の値）
- B. 期限 300 秒、総予算 600 秒
- C. 期限 1800 秒、総予算 2700 秒
- D. 設計の段で決める
- X. Other (please specify)

## Q4. [Node の版] この単位で、動作を保証する Node の版はどこまでか

最低条件は Node 22 です（要件 NFR1）。上の実測では、22.23.4・24.22.1・26.12.1 で、小さな 1 つの例の出力が同じでした。新しい版も保証すると、その版でも門の試験を流す必要があります。試験を複数の版で流すには CI の定義に版の行列を足す必要があり、それは workflow の変更（保護対象）で、この単位では行いません（U7 以降）。

たとえば「22 以上を保証する」と書くと、利用先が Node 26 で呼んだときの動作を、門の側が約束することになります。「22 だけを保証する」と書けば、26 で動いても約束ではなく、動いた事実の記録になります。

- A. 保証するのは Node 22 だけ。24・26 の実測は、観測した事実として記録するが保証しない
- B. 22 以上を保証する。この単位では 22・24・26 の実測を記録し、試験の行列（CI の変更）は U7 以降で足す
- C. 設計の段で決める
- X. Other (please specify)

[Answer]: A（arc の答え。Owner の委任 iyasaka-arc#49 6762288830。Owner の言葉ではない。保証するのは Node 22 だけ。24・26 の実測は観測した事実として記録し、保証しない。試験の行列は U7 以降で、入った時に保証を広げる）
