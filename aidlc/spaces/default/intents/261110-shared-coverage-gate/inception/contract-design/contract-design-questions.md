- **公開される面は 2 つ**: (1) 利用先の `ci.yml` が commit（40桁）を固定して呼ぶ再利用 workflow の入力と出力値（FR7.1、FR8.2）、(2) CI の成果物として残る結果の JSON（FR8.1）。どちらも利用先の repo や、後の監査が読む。
- **門の中の境目**（入力の検査 → 測定 → 判定 → 出力、測定の実行の部品、衛生の共通部品）は、同じ repo の中の契約で、公開はしない。
- **失敗を隠さない**（NFR4）。読めない入力・壊れた記録は失敗にする。観測できないことを成功に読み替えない。「記録だけ」でも、結果の区分と理由は成功と書かずに残す（ADR-004）。
- **既存の呼び出し側を壊さない**（NFR8）。追加は追加の順に行い、逆向きの手順を試験する。
- **判定の核は時刻・乱数・識別子を自分で取得しない**（NFR2）。入口が環境から読んで核へ渡す。
- **JSON を sds-gate や監査の入力に組み込むかは、この取り組みの範囲外**（要件の Open Questions 4、FR8.5）。ここでは「読める形」までを契約にする。

## Q1. [入口] 再利用 workflow は、入力を門の入口の command にどう渡すか

利用先は、分母（測る file の一覧）、除外（file と理由の組を 0 件以上）、閾値の例外（決定の URL・値・根拠）、動作、期限と総予算を、`ci.yml` の `with:` で渡します。workflow は、それを門の入口の command に渡して実行します。渡し方で、入力の形の検査を 1 か所にできるか、workflow の step が薄く保てるか（ADR-006）が変わります。

たとえば除外は「file の名前と理由の組」が複数並ぶので、1 つずつの command の引数にすると、引用符や空白の扱いを workflow の step が受け持つことになります。JSON の file 1 つにまとめると、workflow は入力を 1 つの file に書き出して、その path だけを渡し、検査は入口の側の 1 か所で行えます。一方で、引数や環境変数は、先例の `hygiene.yml` と同じ形で、step を読めばどの入力が渡るかが一目で分かります。

- A. 入力を 1 つの JSON の file にまとめ、workflow はその path だけを入口に渡す。形の検査は入口の側の 1 か所
- B. 入力ごとに command の引数として渡す（先例の `hygiene.yml` の `--profile` のような形）。リスト状の入力は 1 つの文字列にまとめ、入口で分解する

## Q2. [終了コード] 門の入口の command は、終了コードで何を伝えるか

判定の結果は「一致・不一致・観測できず」の 3 値と、「落とすか（shouldFail）」の 2 つの情報を持ちます。workflow は終了コードをそのまま job の成否にします（ADR-004）。終了コードに何を載せるかで、利用先が job の失敗から原因を読めるか、「記録だけ」のときの扱いが変わります。

たとえば、2 値にすると job の赤・緑だけで足り、不一致か観測できずかは JSON と出力値で見ることになります。3 値にすると、job の失敗の理由が終了コードにも出ます（先例の衛生の検査は 0・1・2 を使っています。ただし team.md は、衛生の契約を別の契約に無理に揃えないと決めています）。「記録だけ」では、観測できずや不一致でも CI を落とさないので、どちらの場合も 0 で終わります。入力の形が不正なときや入口自身が壊れたときは、判定の結果でなく入口の失敗なので、別に伝える必要があります。

- A. 2 値: 0 = 落とさない、1 = 落とす（不一致・観測できず・入力不正・入口の失敗はすべて 1）。区分は JSON と出力値で読む
- B. 3 値: 0 = 落とさない、1 = 落とす（判定の結果が不一致または観測できず）、2 = 入力不正または入口の失敗（判定に至らなかった）
- C. 設計の段で決める
- X. Other (please specify)

[Answer]: B（arc の答え。Owner の委任 iyasaka-arc#49 6762288830。Owner の言葉ではない。0 落とさない、1 判定が不一致か観測できず、2 入力不正か入口の失敗）

## Q3. [版] 公開される 2 つの面の変え方を、どう取り決めるか

公開される面は、(1) 再利用 workflow の入力と出力値、(2) 結果の JSON です。利用先は commit を固定して workflow を呼ぶので、workflow の変更は利用先が commit を上げるまで届きません。一方、JSON は後の監査が読むので、過去の実行の JSON と新しい JSON が混ざって読まれます。

たとえば、新しい項目を JSON に足すとき、読む側が知らない項目を無視してよいなら、版を上げずに足せます。項目を消す・名前を変える・値の意味を変えるときは、読む側が古い形を新しい形と取り違えると、成功と読んでしまう恐れがあります。

- A. JSON に整数の `schemaVersion` を持たせる。項目の追加は版を上げず、読む側は知らない項目を無視する。項目の削除・改名・意味の変更は版を上げる。読む側は版が未知か欠けているとき失敗にする（fail closed）。workflow の入力は、追加は省略可（省略時は今までの動作を保つ既定）にし、削除・改名は破壊的な変更として扱い、利用先が commit を上げたときに直す
- B. 項目が 1 つでも変わるたびに `schemaVersion` を上げる（追加も上げる）。workflow の入力も、変更のたびに利用先への周知を要する破壊的な変更として扱う
- C. 設計の段で決める
- X. Other (please specify)

[Answer]: A（arc の答え。Owner の委任 iyasaka-arc#49 6762288830。Owner の言葉ではない。追加は版を上げず未知の項目は無視、削除・改名・意味の変更は版を上げる。版が未知か欠けていれば失敗）

## Q4. [失敗時] 測定の実行が失敗・時間切れ・記録なしになったとき、同じ実行を再試行するか

測定は子プロセスで行い、期限と総予算を超えたら「観測できず」を返します（FR4.4）。再試行するかは、境目ごとの失敗の扱いを決める必要があります。

たとえば、再試行すると、たまたま遅かった実行が通って緑になりますが、本当に壊れている測定が何度か運良く通って緑になる恐れもあります。再試行しなければ、一度の失敗で「観測できず」になり、利用先が自分で再実行します。総予算は再試行の分も含めて使い切ります。

- A. 再試行しない。1 回の失敗・時間切れ・記録なしは、そのまま「観測できず」にする。再実行は利用先の CI の再実行に任せる
- B. 時間切れのときだけ、総予算の範囲で 1 回再試行する。道具の失敗・記録なしは再試行しない
- C. 設計の段で決める
