# 共有の網羅率の門 — 順の理由とリスク

Bolt とは、作る作業の 1 まとまりのこと（1 回の作る工程で 1 つ以上の単位を通し、動く物を 1 つ作って終わる）。この取り組みでは 1 つの Bolt = 1 つの単位。walking skeleton とは、最初に作る、端から端まで動く最小の版のこと。

## 使った考え方

点数づけの方法（WSJF など）は使わない。範囲の文書が順を決めており、その順を Bolt の順にした。

1. **最初に小さく費用を減らす物を置く**（value-first の小さな形）: S10（U1・U2）。小さく、CI の費用をすぐ減らせる。kit の版を待つ他の取り組みがあるため、U1・U2 を最初に置く。
2. **次にリスクの高い物を先に確かめる**（risk-first）: 子プロセスの行を数えられるか（R1）を U3 の実測で確かめる。新しい依存の承認（R2）は、承認を待つ時間を取れるよう、U6 を U4・U5 の後に置き、その間に依頼の準備を進める。
3. **残りは依存の順**: U4・U5 は U3 の上に積む。U7 は U3・U4・U5 の後。U8 は出そろった機能に対して書く。

## 依存の順との差

この順は、unit-of-work-dependency.md の辺をすべて満たす。依存の順に反する並べ方は無く、理由を書く逸脱も無い。

依存の記録の許す並べ方は複数ある（例: U3 の直後に U6、U7 を U6 より前）。その中でこの順を選んだ理由は上の表のとおり。選ばなかった並べ方:

- U6 を U3 の直後に置く案: 承認が遅れると、脇へ置いて進むことになる。承認を待つ時間は取れるが、承認の依頼の準備（[Q3] の A）が U1・U2 の待ち時間で進むので、U4・U5 の後でも間に合う見込みと判断した（arc の答え）。
- U6 を U7 の後に置く案: 承認が来ていなければ Bolt 8 の手前で初めて Owner に伺うことになり、判断が遅れる。選ばなかった。
- U3 を先頭にする案（[Q1] の B）: 最小の版の確認が網羅率の門そのものに付くが、S10 を最初に置く範囲の順序および arc の答えと食い違い、kit の版を待つ取り組みが遅れる。選ばなかった。

## リスクの台帳（順に関わるもの）

| リスク | 確からしさ | 影響 | 対応 | 位置 |
|---|---|---|---|---|
| 子プロセスの計測が実現できない（R1） | 中 | 高 | Bolt 3 の最初に実測する。数えられない組み合わせは使わず、独自の計測器は作らない。実現できなければ範囲の見直しを Owner に諮る | Bolt 3 |
| 新しい依存の承認が来ない（R2） | 中 | 高 | 候補と導入範囲を最小にして、U1・U2 の待ち時間で準備して arc に渡す。承認なしに導入しない。来ていなければ Bolt 6 を脇へ置いて進む。来なければ初版の範囲を Owner に諮る | Bolt 6 |
| TypeScript の測定対象の定義で「行 100%」の意味が変わる（R3） | 中 | 高 | 定義を設計で選び、出力に書く。読み込まれない TS file が分母から落ちる負例と、定義の変更の検出の負例を持つ | Bolt 6 |
| 閾値や除外を下げられる抜け道が残る（R4） | 中 | 高 | 入力の検査で拒否し、下げる・広げる試みを負例にする | Bolt 4・5 |
| 割合の丸め・skip・空の記録が成功に見える（R5） | 中 | 高 | 件数・各 file の記録・分母との突合で判定する | Bolt 3 |
| 公開の Shirube に非公開の土台の内容が混ざる（R6） | 低〜中 | 高 | 一般化して書き直す。独立監査の項目と既存の機械検査で確かめる。公開の試験データは架空だけ | 全 Bolt |
| 共有 workflow の変更の承認が得られない（R7） | 中 | 中 | 設計の段で承認が要る変更を分けて示し、承認が得られるまで着手しない | Bolt 1・2・7 |
| 呼ぶ側の版の違いで数値が変わる（R9） | 中 | 中 | 保証する環境は既存の GitHub Actions の Linux に限り、版と固定方法を設計で明示する | Bolt 3・7 |
| 判定の規則が二重に書かれ食い違う（R10） | 低〜中 | 中 | 規則を 1 か所に置き、他はそこを参照する（S3） | Bolt 3〜7 |
| kit の版を待つ後続の取り組みが止まる | 中 | 中 | U1・U2 を最初に置く。版を出したら arc に知らせる | Bolt 2 |

## 最も気になる点（この取り組みで早く手を付ける物）

- 子プロセスの行を数えられるか（R1）。Bolt 3 の最初の実測で確かめる。
- 新しい依存の承認（R2）。待ち時間を使って準備し、arc に渡す。
- U2 の `labeled`・`unlabeled`。ラベルが判定に効くかは実読で確かめ、効くなら残す（記録した事実の誤りとして arc に伝える）。

## Assumptions & Open Questions

### Assumptions

- [assumption] 点数づけの方法を使わないのは、範囲の文書の順序が既に決めているため。順の根拠は上の表と台帳で足りる。
- [assumption] 承認の依頼の準備を U1・U2 の待ち時間で進められる（監査・統合の返却を待つ間は、承認済みの範囲のほかの作業を進めてよい）。1 単位 = 1 PR と、設計監査の PASS の前に code を書かない決まりは変えない。
