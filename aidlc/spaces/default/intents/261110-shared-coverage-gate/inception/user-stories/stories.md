## グループ1 門を呼んで測る（P1 導入担当）

### US1.1 Node 組込みの試験の形を測る

As a 導入担当, I want 自分の repo の Node 組込みの試験（`node --test`）の行の網羅率を門で測りたい, so that 自前の測り方を持たずに、他の repo と同じ基準で値が出る。

- 優先: Must。依存: US1.4（分母の宣言）。
- INVEST: 小さく独立して試験できる。測定の道具は既存の物だけ（FR1.3）。

- **AC1.1.1** Given 架空の repo に Node 組込みの試験があり、分母が宣言されている, When 門を呼ぶ, Then 宣言された各 file の行の網羅率が、観測した記録から出る。
- **AC1.1.2** Given 同じ repo, When 門の中に自前の計測の仕組みが無いことを確かめる, Then 測定は既存の道具だけで行われている（自前の instrument が無い）。
- **AC1.1.3** Given 試験が1本も流れない構成, When 門を呼ぶ, Then 結果は成功にならず、流れていないことが出力に書かれる。

### US1.2 TypeScript と vitest の試験の形を測る

As a 導入担当, I want TypeScript の ESM と vitest（`vitest run`、tsc でビルド）の試験の行の網羅率も同じ門で測りたい, so that 言語や試験の道具が違っても、同じ基準で値が出る。

- 優先: Must。依存: US8.2（新しい依存の確認）、US1.4。
- INVEST: 測定の定義を出力に残す点で試験できる。

- **AC1.2.1** Given 架空の TypeScript の repo と vitest の試験がある, When 門を呼ぶ, Then 行の網羅率が出る。
- **AC1.2.2** Given 同じ repo, When 結果を読む, Then 何を測ったか（ビルド後の JS か、source map 越しの TS か）の定義が出力に書かれている。
- **AC1.2.3** Given 測定の定義を切り替えた同じ repo, When 結果を読む, Then 値の意味が変わったことが手引きと出力から分かる。
- **AC1.2.4** Given 測定の道具の確認が得られていない, When この形を検証しようとする, Then 検証できないことが明示され、成功とは扱われず、Owner に伺う手順に進む。

### US1.3 試験が起動した子プロセスの行も数える

As a 導入担当, I want 試験が子プロセスとして起動したコードの行も測りたい, so that 子プロセスを使う試験の網羅率が実際より低く出たり、測れていないのに成功したりしない。

- 優先: Must。依存: US1.1。
- INVEST: 子プロセスを使う小さな架空の例で試験できる。

- **AC1.3.1** Given 試験が子プロセスで実行する file を持つ架空の repo, When 門を呼ぶ, Then その file の行が記録に含まれる。
- **AC1.3.2** Given 使う道具の組み合わせが子プロセスの行を数えられない, When 門を呼ぶ, Then その組み合わせは測定に使われず、数えられないことが出力に書かれる。
- **AC1.3.3** Given 子プロセスの行が記録に無いのに値だけが高く出ている入力, When 門を呼ぶ, Then 未計測として扱われ、成功にならない。

### US1.4 測る対象を自分の repo で宣言する

As a 導入担当, I want 測る file の集合（分母）を自分の呼び出しで宣言したい, so that 門の中に対象が直書きされず、測れていない file があれば名前つきで知らされる。

- 優先: Must。依存: なし（US1.1・US1.2 の前提）。
- INVEST: 入力の宣言と未計測の検出だけで独立して試験できる。

- **AC1.4.1** Given 呼び出しが測る file の一覧を入力で宣言している, When 門を呼ぶ, Then 判定の分母はその一覧になり、門の中の固定の対象は使われない。
- **AC1.4.2** Given 宣言された file のうち1本に測定の記録が無い, When 門を呼ぶ, Then その file の名前を出して失敗する（未計測）。
- **AC1.4.3** Given 分母の宣言が無い呼び出し, When 門を呼ぶ, Then 成功とは扱われず、宣言が無いことが出力に書かれる。

### US1.5 commit を固定して、通常の CI と DB の job から呼ぶ

As a 導入担当, I want Shirube の commit（40桁）を固定した再利用 workflow として門を呼び、通常の CI の job からも DB の job からも同じ形で呼びたい, so that 呼んだ版が変わらず、DB の試験も同じ基準で測れる。

- 優先: Must。依存: US1.4。保護対象（FR7.5、US8.1）。
- INVEST: 先例の hygiene の呼び出しと同じ形に合わせる。

- **AC1.5.1** Given 利用先の `ci.yml`, When 門を commit の40桁で固定して呼ぶ, Then 呼ばれた版が固定され、ブランチ名や短い指定では呼べない。
- **AC1.5.2** Given DB を起動する job, When 同じ門を呼ぶ, Then 通常の job と同じ入力と出力で呼べる。
- **AC1.5.3** Given 固定が40桁でない呼び出しの例, When 手引きの試験を流す, Then その例は不合格になる。

## グループ2 結果を読む（P1 導入担当）

### US2.1 成功にならない条件を、成功と書かれずに知る

As a 導入担当, I want 測れていない・流れていない・閾値に届かない場合に、成功と表示されずに理由が分かってほしい, so that 緑の表示を信じて、測れていない所を見落とさない。

- 優先: Must。依存: US1.4。
- INVEST: 条件ごとに正例・負例で試験できる。

- **AC2.1.1** Given 未計測の file がある, When 判定する, Then 成功にならない。
- **AC2.1.2** Given 必須の試験が流れていない（NOT_RUN）, When 判定する, Then 成功にならない。
- **AC2.1.3** Given 測定の道具が失敗した・時間切れ・測定の記録が出ない, When 判定する, Then 結果は「観測できず」になり、成功と数えられない。
- **AC2.1.4** Given 行の割合が閾値に満たない, When 判定する, Then 成功にならない。
- **AC2.1.5** Given 追跡されている試験 file が1本増えたが、除外にも流れた試験にも無い, When 判定する, Then 必須の試験として扱われ、NOT_RUN になる（黙って必須から外れない）。
- **AC2.1.6** Given 結果の3値（一致・不一致・観測できず）, When 結果を読む, Then 観測できずが一致に読み替えられていない。

### US2.2 測定に期限と総予算を持たせる

As a 導入担当, I want 測定の実行に期限と総予算があり、超えたら「観測できず」になってほしい, so that 測定が止まらずに CI が長引いたり、時間切れが成功に見えたりしない。

- 優先: Must。依存: US2.1。
- INVEST: 小さな架空の遅い測定で試験できる。

- **AC2.2.1** Given 期限と総予算が宣言されている, When 測定が予算を使い切る, Then 結果は「観測できず」になる。
- **AC2.2.2** Given 予算内で測定が終わる, When 判定する, Then 通常の判定になる。
- **AC2.2.3** Given 予算超過の入力, When 結果を読む, Then 超過したことが出力に書かれ、成功とは書かれない。

### US2.3 notice と job summary で値を読む

As a 導入担当, I want 測った行の割合、閾値、動作（落とす・記録だけ）、除外の件数が notice と job summary に出てほしい, so that CI の画面を開くだけで、何が測られ、どう判定されたか分かる。

- 優先: Must。依存: US2.1。
- INVEST: 出力の文面を架空の結果で試験できる。

- **AC2.3.1** Given 成功した結果, When job summary を読む, Then 行の割合、閾値、動作、除外の件数が書かれている。
- **AC2.3.2** Given 観測できず・不一致の結果, When job summary を読む, Then 理由が書かれ、成功とは書かれていない。
- **AC2.3.3** Given 同じ結果, When notice を読む, Then job summary と食い違わない。

### US2.4 決まった形の JSON と出力値を受け取る

As a 導入担当, I want 結果が決まった形の JSON の file（CI の成果物）と、呼んだ workflow が受け取れる出力値の両方で返ってほしい, so that 別の席や後の工程が、文章でなく機械で結果を読める。

- 優先: Must。依存: US2.1。JSON の項目と出力値の名前は設計の段で決める（Open Question）。
- INVEST: 形が決まっていれば試験できる。

- **AC2.4.1** Given 判定が終わった, When CI の成果物を見る, Then 決まった形の JSON の file が残っている。
- **AC2.4.2** Given 同じ判定, When 呼んだ workflow が出力値を受け取る, Then 結果の区分、値、閾値、動作が受け取れる。
- **AC2.4.3** Given JSON と出力値, When 突き合わせる, Then 食い違わない。
- **AC2.4.4** Given 観測した記録が無い（測れていない）, When JSON を読む, Then 値は空または観測できずで、申告された値や前回の値は入っていない。

## グループ3 除外と DB の試験（P1 導入担当）

### US3.1 DB の試験を DB の job で測る

As a 導入担当, I want DB を要する試験を、版または指紋を固定した PostgreSQL を起動する job で測りたい, so that 通常の CI で流せない試験も、分母から外さずに測れる。

- 優先: Must。依存: US1.5。DB の構造は変えない（前提）。
- INVEST: 架空の DB を要する試験で試験できる。

- **AC3.1.1** Given 版または指紋を固定した PostgreSQL を起動する job, When 門を呼ぶ, Then DB を要する試験の行も測定に含まれる。
- **AC3.1.2** Given 版も指紋も固定されていない DB の job, When 手引きの試験を流す, Then その構成は不合格になる。
- **AC3.1.3** Given DB の job で試験が流れなかった, When 判定する, Then NOT_RUN になり成功にならない。

### US3.2 測れない file を理由つきで1本ずつ除外する

As a 導入担当, I want DB の job で測れない file を、理由をつけて1本ずつ名指しで除外したい, so that 除外した物と理由が残り、除外が増えたことが差分で見える。

- 優先: Must。依存: US1.4。
- INVEST: 入力の形の検査として独立して試験できる。

- **AC3.2.1** Given 理由つきで file が1本ずつ名指しされている, When 門を呼ぶ, Then その file は分母から外れ、名前と理由と除外の件数が出力に残る。
- **AC3.2.2** Given ディレクトリ名またはワイルドカードで除外を指定した, When 門を呼ぶ, Then 入力として受け付けられず失敗する。
- **AC3.2.3** Given 理由が書かれていない除外, When 門を呼ぶ, Then 受け付けられず失敗する。
- **AC3.2.4** Given 除外の件数が前回より増えた呼び出し, When 差分を読む, Then 増えた分が呼び出しの入力の差分として見える。

### US3.3 除外を呼ぶ側の上書きで広げられない

As a 保守担当, I want 呼ぶ側が上書きで除外を広げられないようにしたい, so that 除外が黙って増えて、分母が小さくなる状態を作らない。

- 優先: Must。依存: US3.2。
- INVEST: 上書きの試みを負例として試験できる。

- **AC3.3.1** Given 呼ぶ側が宣言した除外の一覧, When 別の入力や環境で除外を追加しようとする, Then 追加は反映されず、拒否が出力に書かれる。
- **AC3.3.2** Given 除外を宣言しない呼び出し, When 門を呼ぶ, Then 除外は0件で、分母は宣言された全 file になる。

## グループ4 閾値と例外（P1 導入担当、P4 Owner）

### US4.1 既定の100%で判定される

As a 導入担当, I want 何も指定しなければ行100%で判定されてほしい, so that 低い基準を黙って選ぶことができない。

- 優先: Must。依存: US2.1。
- INVEST: 既定の値を1つの正例と1つの負例で試験できる。

- **AC4.1.1** Given 閾値の指定が無い呼び出し, When 判定する, Then 閾値は行100%である。
- **AC4.1.2** Given 行の割合が99.9%の結果, When 判定する, Then 閾値100%に満たず成功にならない。
- **AC4.1.3** Given 行の割合が100%で、ほかの失敗の条件が無い, When 判定する, Then 成功になる。

### US4.2 Owner の決定の URL を名指して閾値を下げる

As a 導入担当, I want Owner の決定の URL と下げる値と根拠をそろえて入力することで、閾値を100%より低くしたい, so that 例外が決定に結び付き、根拠なしには下げられない。

- 優先: Must。依存: US4.1。
- INVEST: 形の確かめだけ（実在の確認は独立監査）として独立して試験できる。

- **AC4.2.1** Given 決定の URL の形が正しく、下げる値と根拠がそろっている, When 門を呼ぶ, Then 下げた値で判定される。
- **AC4.2.2** Given 閾値を下げるが URL が無い, When 門を呼ぶ, Then 下げた値は受け付けられず失敗する。
- **AC4.2.3** Given URL の形が正しくない・根拠が空・下げる値が数として読めない, When 門を呼ぶ, Then 受け付けられず失敗する。
- **AC4.2.4** Given 門の実行環境, When 資格情報を確かめる, Then 門は GitHub を読む資格情報を持たない（実在の確認は行わない）。

### US4.3 閾値を下げた事実が目立つ

As a 導入担当, I want 閾値を100%より低く使ったことが、成功の表示に隠れずに出力の目立つ位置に書かれてほしい, so that 例外で通っていることを、結果を読む誰もが見落とさない。

- 優先: Must。依存: US4.2。
- INVEST: 出力の位置と文面で試験できる。

- **AC4.3.1** Given 閾値を下げた呼び出しが成功した, When job summary を読む, Then 閾値が100%より低いことが成功の表示より前または同じ強さで書かれている。
- **AC4.3.2** Given 同じ結果, When notice を読む, Then 実際の閾値が書かれている。
- **AC4.3.3** Given 閾値を下げていない成功, When 出力を読む, Then 例外の記述は出ない。

## グループ5 記録だけから落とすへの段階導入（P1 導入担当）

### US5.1 「記録だけ」で始める

As a 導入担当, I want 導入の初日は数値を出すだけで CI を落とさない動作で始めたい, so that 導入の担当が戸惑わずに測定を始められ、100% に届いた repo から落とす動作へ移れる。

- 優先: Must。依存: US2.1。FR6.4 は前提（記録だけの間は閾値未満・未計測・NOT_RUN も落とさない）。
- INVEST: 動作ごとに試験できる。

- **AC5.1.1** Given 動作に「記録だけ」を明示した, When 行の割合が閾値に満たない, Then CI は落ちず、値と不足が出力に書かれる。
- **AC5.1.2** Given 動作が「記録だけ」で、測定の道具が失敗した, When 判定する, Then CI は落ちず、notice と job summary に「計測不能」と明記され、成功とは書かれない。
- **AC5.1.3** Given 動作が「記録だけ」で、未計測または NOT_RUN がある, When 判定する, Then CI は落ちず、それぞれが出力に書かれる。
- **AC5.1.4** Given 動作が「記録だけ」, When JSON と出力値を読む, Then 動作が「記録だけ」であることが残っている。

### US5.2 入力1つで「落とす」に切り替える。何も指定しなければ「落とす」

As a 導入担当, I want 動作を入力1つで「落とす」に切り替えたい。何も指定しなければ「落とす」であってほしい, so that 書き忘れで門が効かないまま残らず、切り替えが1箇所の差分で見える。

- 優先: Must。依存: US5.1。
- INVEST: 切り替えの入力1つで試験できる。

- **AC5.2.1** Given 動作を指定しない呼び出し, When 失敗の条件に当たる, Then CI は落ちる。
- **AC5.2.2** Given 動作を「記録だけ」から「落とす」に1つの入力で変えた, When 同じ結果を判定する, Then CI が落ちる。
- **AC5.2.3** Given 動作の入力が「落とす」でも「記録だけ」でもない値, When 門を呼ぶ, Then 受け付けられず失敗する。

## グループ6 独立監査席が照らす（P2 独立監査席）

### US6.1 観測した記録から値を再計算して照らす

As a 独立監査席, I want 結果の値が観測した行ごとの記録から再計算でき、申告された値や道具が最後に出した数字を信じていないことを確かめたい, so that 宣言を写しただけの「一致」を見抜ける。

- 優先: Must。依存: US2.4。
- INVEST: 中身を変えた入力で試験できる。

- **AC6.1.1** Given 行ごとの記録がある結果, When 記録から値を再計算する, Then JSON の値と一致する。
- **AC6.1.2** Given 記録の中身を書き換えた入力, When 門を呼ぶ, Then 不一致または観測できずになり、一致にならない。
- **AC6.1.3** Given 分母の件数と記録の件数が食い違う入力, When 門を呼ぶ, Then 食い違いが出力に書かれ、成功にならない。
- **AC6.1.4** Given 道具が最後に出した割合の数字だけが残り、行ごとの記録が無い入力, When 門を呼ぶ, Then その数字は根拠にされず、観測できずになる。

### US6.2 閾値の例外の根拠を出力から照らす

As a 独立監査席, I want 閾値を下げた呼び出しの出力に、名指された URL、主張された値、根拠、実際の閾値が必ず残っていてほしい, so that 決定の実在と本文の一致を GitHub の公開記録と照らして確かめられる。

- 優先: Must。依存: US4.2。
- INVEST: 出力の項目の有無で試験できる。

- **AC6.2.1** Given 閾値を下げた結果, When JSON を読む, Then URL、主張された値、根拠、実際の閾値の4つが残っている。
- **AC6.2.2** Given 同じ結果, When 主張された値と実際の閾値を比べる, Then 一致している（食い違う場合は不一致になる）。
- **AC6.2.3** Given 閾値を下げていない結果, When JSON を読む, Then 例外の項目は空であることが分かる。

### US6.3 測定の定義・除外・動作を出力から読む

As a 独立監査席, I want 出力に、使った測定の定義、除外の一覧と理由、閾値の例外、動作が含まれてほしい, so that 利用先の門や監査が、この JSON を根拠にして読める。

- INVEST: 項目の有無で試験できる。

- **AC6.3.1** Given 判定が終わった, When JSON を読む, Then 測定の定義、除外の一覧と理由、閾値の例外、動作が含まれている。
- **AC6.3.2** Given JSON の内容, When 申告値の写しが無いことを確かめる, Then 値は観測した記録だけから作られている。
- **AC6.3.3** Given この取り組みの範囲, When 門と監査の入力への組み込みを確かめる, Then 組み込みは行われておらず、読める形で出すところまでである。

## グループ7 CI の実行を減らす（P3 保守担当）。順序の最初

### US7.1 門の起動を監査に関わるコメントに絞る

As a 保守担当, I want kit の門の呼び出しの起動を、監査に関わるコメント（`sds-audit-request/1`、`sds-audit-review/1`、作者の受領）に絞りたい, so that 関係のないコメントや更新で門が走り、CI の費用が増えることを防ぐ。

- **AC7.1.2** Given 関係のないコメントが投稿された, When 起動の条件を評価する, Then 門は起動しない。
- **AC7.1.3** Given 起動の定義, When 絞った後の種類を調べる, Then 監査に関わるコメントに必要な種類が残っている。

### US7.2 ラベルが判定に効くかを確かめてから、起動の種類を外す

As a 保守担当, I want `labeled` と `unlabeled` の起動を外す前に、`scripts/sds/gate.mjs` を読み、risk:R0〜R4 のラベルが判定に効くかを確かめたい, so that 古い判定が残る状態を作らず、必須の検査を弱めない。

- 優先: Must。依存: US7.1。
- INVEST: ラベルを付け替える負例で試験できる。

- **AC7.2.1** Given ラベルが判定に効くと確かめられた, When 起動の種類を決める, Then `labeled` と `unlabeled` は残される。
- **AC7.2.2** Given ラベルが判定に効かないと確かめられた, When 起動の種類を決める, Then `labeled` と `unlabeled` は外される。
- **AC7.2.3** Given ラベルを付け替えた PR, When 判定を読む, Then 古い判定が残っていない（残るなら不合格）。
- **AC7.2.4** Given 確かめた結果, When 記録を読む, Then 結果が arc に知らされ、Owner の決定の括弧書きの事実の食い違いがあれば、その旨が伝えられる。

### US7.3 同じ PR の古い実行を取り消す

As a 保守担当, I want Shirube 自身の `ci.yml` に、同じ PR の古い実行を取り消す仕組み（concurrency）を置きたい, so that 続けて push した時に、古い実行が資源を使い続けない。

- 優先: Must。依存: なし。保護対象（US8.1）。
- INVEST: workflow の定義を試験できる。

- **AC7.3.1** Given 同じ PR に続けて push した, When 実行が重なる, Then 古い実行が取り消される。
- **AC7.3.2** Given 既定の branch への push, When 実行が重なる, Then 実行は取り消されない。
- **AC7.3.3** Given 別の PR の実行, When 実行が重なる, Then 互いを取り消さない。

### US7.4 必須の検査を弱めない

As a 保守担当, I want CI を絞る変更が、必須の検査の名前・数・内容と branch protection を変えないことを確かめたい, so that 費用を減らす変更が、検査を弱める変更にならない。

- 優先: Must。依存: US7.1、US7.3。
- INVEST: 差分と既存の検査の結果で試験できる。

- **AC7.4.1** Given 変更の差分, When 必須の検査の名前と数を比べる, Then 変更前と同じである。
- **AC7.4.2** Given 変更後の CI, When 既存の試験を流す, Then 試験の中身は減っておらず、結果は変更前と同じ基準で通る。
- **AC7.4.3** Given 変更の差分, When branch protection の設定を探す, Then 変更が含まれていない。

## グループ9 手引き・検証・公開の安全

### US9.1 九つの項目を正例と負例で検証する（P3 保守担当）

As a 保守担当, I want 指定の九つの項目それぞれを、架空の利用例で正例と負例の両方で検証したい, so that 完了を項目ごとの観測で言え、負例が不一致または観測できずになることを示せる。

- **AC9.1.2** Given 負例の試験, When 流す, Then 中身を変えた入力が不一致または観測できずになる。
- **AC9.1.3** Given 予算超過の入力, When 流す, Then 観測できずになる。
- **AC9.1.4** Given 試験の結果, When skip や todo を数える, Then それらは合格に数えられていない。

### US9.2 利用の手引きを読んで導入する（P1 導入担当）

- 優先: Must。依存: US5.2、US4.2、US3.2、US1.2。
- INVEST: 手引きの内容を項目の有無で試験できる。

- **AC9.2.2** Given 手引き, When 内容を読む, Then 記録だけから落とすへの切り替え、除外の書き方、閾値の例外の書き方がある。

- **AC9.2.4** Given 手引きの呼び出しの例, When 試験で読み取る, Then 例は固定が40桁でない場合に不合格になる。

### US9.3 公開に載る物は架空の例だけで、非公開の土台を写さない（P3 保守担当、P2 独立監査席）

As a 独立監査席, I want 公開の試験データと出力が架空の例だけで、非公開の土台の識別子・コード・製品固有の名前が写されていないことを確かめたい, so that 公開に載せてはいけない物が載らない。

- INVEST: 差分の検査で試験できる。

- **AC9.3.1** Given 公開に載る試験データと出力の例, When 内容を調べる, Then 架空の repo 名と値だけである。
- **AC9.3.2** Given 公開に載る差分, When 非公開の土台の識別子やコードを探す, Then 見つからない。
- **AC9.3.3** Given 非公開の土台を参考にした部分, When 書き直しの記録を読む, Then 構造を一般化した所見だけが書かれている。

### US9.4 導入件数を成功の数に入れない（P4 Owner）

As a Owner, I want この取り組みの成功が自社で観測できる指標だけで言われ、実在のプロダクトへの導入件数を数に入れないようにしたい, so that 利用先の結果に左右されない判断ができる。

## グループ10 失敗を隠さない・同じ入力で同じ出力・新旧の同居

- **AC10.2.1** Given 時刻・識別子を呼ぶ側が固定した入力, When 2回実行する, Then 出力がバイトまで一致する。
- **AC10.2.2** Given 判定の核, When 現在時刻・乱数・識別子の取得を探す, Then 見つからない（呼ぶ側から入力として受ける）。
- **AC10.2.3** Given 入力の1つを変えた実行, When 出力を比べる, Then 出力が変わる。

### US10.3 既存の呼び出し側を壊さない（P3 保守担当）

As a 保守担当, I want 門を追加しても、既存の呼び出し側が壊れないことを確かめたい, so that 追加の途中で、旧い呼び出しと新しい呼び出しが同じ状態の上で動く。

- **AC10.3.3** Given 削除や拒否を含む変更, When 記録を読む, Then 新旧が同居する期間が宣言されている。
