## 計画（決まっている事。問いではない）

### 立場（人物像）の作り方

利用者の画面は無いため、「この門に触れて次の行動を決める立場」を人物像にする。案は4つ。

| 人物像 | 立場 | この門に触れる目的 |
|---|---|---|
| 導入担当 | 利用先の repo の CI を書く人（や席） | 自分の repo の試験を、同じ基準で測り、結果を読んで直す |
| 独立監査席 | 変更を独立に確かめる席 | 出力に残った URL・主張された値・除外を、実物と照らす |
| 保守担当 | この門と Shirube の CI を作り、直す席 | 門を作り、CI の費用を減らし、手引きを書く |
| Owner | 保護対象と閾値の例外を決める人 | 閾値を下げる決定を出し、workflow の変更を承認する |

### ストーリーの形

「<人物像>として、<したいこと>。そうすれば<得られること>」の形。1本ずつに `US{グループ}.{番号}` の ID を付け、受入条件には `AC{グループ}.{ストーリー}.{番号}` を付ける。受入条件は Given/When/Then で、3〜6件。正例だけでなく、失敗の例（観測できない、名指しの無い除外、URL が無い閾値の例外など）を必ず入れる。ストーリーは INVEST（独立・交渉可能・価値・見積もれる・小さい・試験できる）に照らして書く。

### 優先

範囲の文書は、指定9項目と追加の1つをすべて Must とし、優先は区分でなく順序（S10 を最初、次にリスクの高い依存の確認と子プロセスの実測、続けて判定と出力、DB、呼び出し、手引き）で付けると定めている。ストーリーも同じく、すべて Must とし、Should 以下を新しく作らない。MVP の境目と単位への分け方は、後の段（Units Generation、Delivery Planning）で決める。

## Q1. [分け方] ストーリーを何の単位で切るか

ストーリーの切り方で、後の段で単位に分けるときの扱いやすさが変わります。たとえば、導入担当の目的で切ると「門を呼んで結果を読む」という一続きの流れが1本に見えます。要件の群で切ると、FR3（閾値と例外）のように、1つの要件が1〜2本のストーリーに素直に対応します。

- A. 立場の目的ごとに切る（導入担当が呼ぶ、結果を読む、除外と例外を宣言する、段階導入する。独立監査席が照らす。保守担当が CI を絞る、など）。要件との対応は追跡表で結ぶ

## Q2. [範囲] 手順や環境の要件をストーリーにするか

要件には、利用者が結果として観測できる物のほかに、作り方や環境を縛る物があります（Node の版、新しい依存の承認、構造の大きさ、費用、評価の指標の取り方、保護対象の承認の手順など）。たとえば「新しい有料サービスを足さない」を、ストーリーにして受入条件を書くのか、設計の段に回して追跡表で「後の段へ回した」と記録するのかで、ストーリーの数と、後の段で受ける物が変わります。

- A. 観測できる物と、Owner や独立監査席の判断が要る手順（保護対象の承認、新しい依存の確認）はストーリーにする。環境・規約・費用・構造の大きさなどの縛りは、後の段（機能以外の要件など）へ回す
- B. すべてストーリーにする（縛りも、Owner や保守担当の立場から受入条件を書く）
- C. 設計の段で決める
