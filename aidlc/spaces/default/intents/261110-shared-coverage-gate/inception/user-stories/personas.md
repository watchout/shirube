## 人物像

### P1 導入担当

- **立場**: 利用先の repo で CI の設定を書き、試験の結果を読んで直す人（または席）。
- **目的**: 自分の repo の試験を、他の repo と同じ基準で測り、測れていない所を成功と言われずに知る。呼び出しの設定を最小の手間で書く。
- **困りごと**: repo ごとに網羅率の測り方が違い、何が分母か分からない。CI は緑なのに、測れていない file がある。導入の初日に網羅率の道具が動かず、CI が落ちて戸惑う。
- **文脈**: GitHub Actions の Linux 上の CI。Node 組込みの試験か、TypeScript と vitest の試験を使う。DB を要する試験を持つ repo もある。
- **この門との関わり**: 呼び出しを書く。入力で対象・除外・閾値・動作を宣言する。notice、job summary、JSON と出力値を読む。

### P2 独立監査席

- **立場**: 作る席から独立して変更を確かめる席。
- **目的**: 出力に残った URL・主張された値・除外・測定の定義を、実物と照らす。申告された値ではなく、観測した記録から値を再計算できることを確かめる。
- **困りごと**: 結果が文章でしか残らないと、照らす根拠にできない。閾値の例外の根拠が出力から消えると、実在の確認ができない。
- **文脈**: GitHub の公開記録だけを読む。門は GitHub を読む資格情報を持たないため、決定の実在と本文の一致の確認はこの席の仕事になる（FR3.3）。
- **この門との関わり**: 出力の JSON を読み、実際の記録と照合する。中身を変えた入力で不一致または観測できずになることを確かめる。

### P3 保守担当

- **立場**: この門と Shirube の CI を作り、直し、手引きを書く席（作る席）。統合する席も、結果の表示を読む点で近い立場に含める。
- **目的**: 門を作り、既存の呼び出し側を壊さずに配る。CI の実行を減らして費用を下げる。必須の検査は弱めない。
- **困りごと**: 門の起動が多すぎて CI の費用が増える。ラベルが判定に効くかを確かめずに起動を外すと、古い判定が残る。非公開の土台の構造を、識別子ごと公開に写してしまう恐れがある。
- **文脈**: 1単位1PR、TDD、独立監査と作者以外の統合を通す。保護対象（workflow など）の変更は Owner の承認が別に要る。
- **この門との関わり**: 再利用 workflow、kit の呼び出し、`ci.yml` を変更する。正例と負例の検証を整え、手引きを書く。

### P4 Owner

- **立場**: 閾値の例外と保護対象の変更を決める人。
- **目的**: 閾値を下げる例外を、根拠つきの決定として出す。再利用 workflow と CI の変更を、対象の head で承認する。新しい依存の採用を決める。
- **困りごと**: 例外が黙って増えると、100% の既定が崩れる。承認の対象が曖昧だと、何を許したか分からなくなる。
- **文脈**: 判断は GitHub に公開された決定として残る。この取り組みの成功は、自社で観測できる指標だけで見る。
- **この門との関わり**: 閾値の例外の決定 URL を出す。workflow の変更の対象 head を承認する。新しい依存の確認の後に決める。

## 関係と優先

- P1 が日常の利用者で、数の上でも多い。P2 は P1 の出力を照らす。P3 は P1 と P2 が使う面を作る。P4 は P1 の例外申請と P3 の保護対象の変更を受けて決める。
- 優先は範囲の文書に従い、人物像の間に差をつけない（すべて Must、優先は順序で付ける）。順序の最初は P3 の CI の絞り（S10）。
- 関係の流れ: P3 が門を作る → P1 が呼ぶ → 結果を P1 が読み、P2 が照らす → 例外が要るとき P1 が P4 の決定を名指す。
