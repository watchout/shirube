## 決まっている事（問いではない）

- **部品は「書く code」だけ**。試験の道具（Node 組込みの網羅率、c8、vitest など）、GitHub Actions、PostgreSQL は部品が使う外の依存で、部品に数えない。
- **意味の核と I/O を分ける**（S2・S4・S5、NFR2）。判定は呼ぶ側が渡した入力だけから決まる純粋な部品にし、時計・乱数・識別子・子プロセス・ファイルの読み書きは外側の部品が受け持つ。
- **規則は1か所**（NFR3）。閾値の既定、理由コード、結果の3値は判定の部品だけが持つ。
- **S10 は新しい部品を作らない**。kit の呼び出し口と Shirube 自身の CI は既存の部品の変更として扱う。
- **作業場の手元だけにある `ci-record-*` などは、統合されるまで部品に数えない**（component-inventory の注記どおり）。

## Q1. [境目] 入力の形の検査と、判定の核を分けるか

入力の形の検査とは、閾値の例外の URL の形・下げる値・根拠がそろっているか、除外が1本ずつの名指しで理由つきか、動作の値が「落とす」「記録だけ」のどちらかか、などを確かめることです（実在の確認は独立監査の仕事で、ここではしません）。判定の核は、その入力と観測した記録から、一致・不一致・観測できずを決めます。

たとえば除外に理由が書かれていないとき、「入力が受け付けられない」という失敗は入口で止まるのか、判定の核が理由コードの1つとして返すのかで、理由コードの置き場と試験の分け方が変わります。

- A. 分ける。入力の検査は入口の部品、判定の核は入力が正しい前提で値だけを判定する。理由コードは判定の部品が全部持ち、入口の失敗もその集合の1つとして返す
- B. 1つにする。入力の検査も判定の核の中で行う
- C. 設計の段で決める
- X. Other (please specify)

## Q2. [境目] 2つの試験の形の測定を、形ごとの部品にするか

Node 組込みの試験と、TypeScript と vitest の試験とでは、測る道具と記録の出方が違います。判定の核が読む「行ごとの記録」は、どちらの形でも同じ形にそろえる必要があります。範囲の文書は、2つの形のほか、利用先が増えたら形を増やす見込みは書いていません（S2: 抽象は3例目）。

たとえば将来 3 つ目の形が出たとき、形ごとの部品なら新しい部品を1つ足すだけで済みますが、今は2つなので、共通の記録の形を決める手間のほうが先に要ります。

- A. 形ごとに部品を分ける（Node 組込み用、TypeScript と vitest 用）。どちらも同じ「行ごとの記録」の形を出し、判定の核はそれだけを読む
- B. 測定の部品を1つにして、中で2つの形を扱う
- C. 設計の段で決める
- X. Other (please specify)

[Answer]: A（arc の答え。Owner の委任 iyasaka-arc#49 6762288830。Owner の言葉ではない。形ごとの部品が同じ「行ごとの記録」の形を出し、判定の核はそれだけを読む。S2 = adapter は形の変換だけで、判定の意味を持たない）

## Q3. [再利用] 分母（測る file の集合）の解決に、衛生の検査の共通部品を使うか

衛生の検査の共通部品（hygiene-lib）には、追跡されている file を取り、宣言された対象と除外を解決する部品があります。今は行数・重複・言語の被覆の検査だけが使っています。分母の宣言（FR2.1）を解決するのに同じ部品を使えば、同じ判断を2か所で下す状態を避けられますが、網羅率の門が衛生の検査の共通部品に依存することになります。一方、新しく書けば依存は増えませんが、対象の解決の規則が2つに分かれます（S3）。

- A. 使う。網羅率の門が衛生の共通部品の対象解決を呼ぶ（依存は Node 組込みだけのまま）
- B. 使わない。網羅率の門が分母の解決を自前で持つ
- C. 設計の段で決める
- X. Other (please specify)

[Answer]: A（arc の答え。Owner の委任 iyasaka-arc#49 6762288830。Owner の言葉ではない。hygiene-lib の対象解決を使う。S3 = 同じ判断を 2 か所で下さない。同じ repo の中の依存で、外の依存は増えない）
