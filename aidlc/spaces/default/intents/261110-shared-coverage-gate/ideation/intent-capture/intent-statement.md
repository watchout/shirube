# 共有の網羅率の門 — 目的

## Problem Statement

社内の各製品で試験の網羅率を測る仕組みや判定を重複して作らず、共有の門を利用できるようにする。測られていないソース、必須試験の未実施、計測不能を成功として扱わず、測定の対象と結果を利用者が確認できる状態を目指す。[Q1]

## Target Customer

利用者は社内製品の開発・CI担当である。各製品の試験の形やDBの試験の置き方に合わせて共有の門を使い、同じ判定の仕組みを製品ごとに作り直さずに済むことが価値となる。[Q1] [Q5]

## Success Metrics

完成の条件は、指定された9項目について、架空の利用例による正例・負例と利用手順に沿ったcommit固定の呼出しを検証できることである。実製品への導入件数や全社の網羅率向上を、この初版の完成条件にはしない。[Q1] [Q2] [Q3] [Q4]

| 確認する項目 | 完成時に必要な確認 | Source |
|---|---|---|
| 二つの試験方式 | Node組込み試験とTypeScript・vitestの利用例で測定と判定を確認できる | [Q1] [Q2] [Q3] |
| 子プロセス | 子プロセスを含む測定を既製の道具で確認でき、独自の計測器を作らない | [Q1] [Q3] [Q4] |
| TypeScriptの測定対象 | JSを測るかTSへ対応付けるかを設計で決め、値の意味が変わる場合を記録できる | [Q1] [Q3] |
| DBの試験 | DB別jobの呼出し、または入力で名指し・理由を出力・呼出側から拡大不能な除外を確認できる | [Q1] [Q2] [Q3] |
| 閾値 | 行100%を既定とし、下げる例外ではOwner決定URLと値・根拠を確認でき、不正な閾値変更を検出できる | [Q1] [Q3] |
| 未計測・未実施・計測不能 | 未計測src、必須試験のNOT_RUN、道具の失敗等による計測不能を成功にしないことを負例で確認できる | [Q1] [Q3] |
| 段階的な導入 | 記録だけ／失敗させる運用の切替を入力一つで確認できる | [Q1] [Q3] |
| 呼出しと結果 | 通常CIとDBのjobからcommit固定で呼べ、noticeとjob summaryの結果を確認できる | [Q1] [Q2] [Q3] |
| 非公開の土台と公開安全 | 非公開コードを転載せず一般化して書き直し、公開の試験データは架空だけにする | [desc] [Q1] |

上記は受入の目標であり、試験実行済み・実装済み・配布済みという報告ではない。実製品への適用は、初版の検証とは別の判断と承認で扱う。[Q2] [Q3] [Q4]

## Initiative Trigger

Ownerから、共有の網羅率の門をShirubeの新しいAI-DLCの取り組みとして始める依頼を受けた。既存U1の作業を止めず、別の取り組みとして扱う。[desc]

開始依頼が参照する公開指示は、[Ownerの指示](https://github.com/watchout/iyasaka-arc/issues/49#issuecomment-6759071065)、本文SHA-256 `c5d9ccc3510ff46e5d6661bc8c528cafb7e08d4ce2c86f39f049782eaf7e524b`。指定要件は、[共有の網羅率の門の要件](https://github.com/watchout/shirube/issues/6#issuecomment-6759206975)、本文SHA-256 `c1952c809e8a2d0e09d68e2e1cf4e2040607408d4b8598cccc68eb1c3af991c0`。この段ではQ1〜Q6の回答と要約確認により目的・初版の境界を整理し、これらの参照だけで新依存やworkflow変更の個別承認を済ませない。[desc] [Q1] [Q4] [Q5]

## Initial Scope Signal

workflow-selected scopeは`feature`である。これは開発の進め方の選択を表すもので、製品の初版の境界は次の回答に従う。[scope] [Q4]

- 指定9項目すべてを今回の目的とし、Shirube内の架空の利用例でNode・TypeScript・子プロセス・DB別jobの呼び方と判定を検証する。[Q1] [Q2]
- 初版には、全repoへの一括導入、社内の網羅率基準や既存80%の扱いの変更、独自の計測器、既存U1への取り込みを含めない。利用先への実適用は別承認の範囲で扱う。[Q4]
- 新しい依存は導入前にarc-secの安全確認とOwnerの決定を通す。workflow変更・利用先CI変更などの保護対象は必要な別承認を維持する。[Q1] [Q4] [Q5]
- 非公開の土台は読み取りの参考にし、公開repoには転載せず一般化して書き直す。公開の試験データは架空のものだけにする。[desc] [Q1]
- 既存U1の作業を、この取り組みの開始を理由に中止・変更しない。[desc] [Q4]
