# 共有の網羅率の門 — 制約の一覧

## Sources

- 承認済みの目的: [intent-statement.md](../intent-capture/intent-statement.md)。関係者: [stakeholder-map.md](../intent-capture/stakeholder-map.md)。実現性の評価: [feasibility-assessment.md](./feasibility-assessment.md)。
- この段の回答: [Q1] 実証環境は既存のGitHub ActionsのLinuxのみ。[Q2] 新たな有料サービス・常設クラウド資源は導入せず既存CIで実証する。[Q3] 今回固有の追加条件はなく、採択済みの社内基準に従う。
- 採択済みの社内の規則（作業場の記録）: 設計・実装の標準S1〜S9、AI-DLCの決まり、保護対象のOwner承認、1単位1PR、独立監査。Shirubeのteam・projectの記録にある試験・コードの規約。
- 手元の観測: Shirubeの`package.json`（Node 22以上、実行時の依存なし）、`ci.yml`、`hygiene.yml`。

制約の「種別」は、技術・組織・規制・方針の4つに分ける。[Q3]で今回固有の法令・契約上の追加条件は指定されていないため、規制の欄は空ではなく、「追加条件なし。採択済みの社内基準を維持する」と記す。

## 技術の制約

| ID | 制約 | 影響 | Source |
|---|---|---|---|
| T1 | 初版で動作を保証する環境は、既存のGitHub ActionsのLinux環境だけ。macOS・Windows・self-hosted runner・他のCIの対応は保証しない。 | 他の環境の動作を、対応済みと書かない。Node・計測道具・DBの版と固定方法は設計で明示する。 | [Q1] |
| T2 | Shirubeの実行環境はNode 22以上。CIはNode 22。 | 計測の機能は、Node 22で動くことを確かめる。手元の別の版での動作を保証の根拠にしない。 | 手元の観測 |
| T3 | 網羅率は既製の道具で測り、独自の計測器は作らない。 | 道具が測れないものは、独自の計測で補わず、範囲の見直しをOwnerに諮る。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| T4 | 成功を道具の終了コードや割合の表示だけで判定しない。観測した件数・各ファイルの記録・分母との突合で判定し、「一致」「不一致」「観測できず」を区別する。観測できずを成功に読み替えない。 | 未計測・NOT_RUN・計測不能・skip・TODOを、成功に数えない設計が要る。 | 社内標準S5・S8 |
| T5 | 時刻・乱数・識別子は、判定の中心部が自分で取得せず、呼出し側から明示の入力で受け取る。 | 判定は同じ入力で同じ結果になる形にする。時刻などを使う部分は、入力と出力の端に置く。 | 社内標準S4 |
| T6 | 判断の規則（閾値、除外の規則、結果の分類の集合）は1か所にだけ置き、他はそこを参照する。 | 通常CIとDB別jobで同じ判定を再定義しない。同じ判断を2か所で下せる状態にしない。 | 社内標準S3 |
| T7 | 呼出しはcommitで固定する（40桁）。ブランチ名や浮動の参照で固定したことにしない。 | 利用手順とその試験で、固定の形を確かめる。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| T8 | 閾値は行100%を既定とし、呼出し側の環境や入力で下げられない。下げる例外は、Owner決定のURL・値・根拠が揃う入力でだけ有効にする。除外は、呼出し側から拡大できない。 | 不正な閾値・除外の拡大は、負例として必ず検出する。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| T9 | 資格情報は用途ごとに最小にする。書ける資格情報を、試験や汎用の工程に渡さない。 | 共有workflowが受け取る資格情報を宣言し、必要最小限にする。 | 社内標準S9 |
| T10 | 検査コードは、読めない・壊れている時に失敗にする。必須工程の失敗を隠す書き方（失敗を無視する指定など）を置かない。 | 計測不能は成功ではなく失敗または観測不能として扱う。 | 社内標準S8、Shirubeの規約 |

## 組織の制約

| ID | 制約 | 影響 | Source |
|---|---|---|---|
| O1 | 新しい依存は、導入前にarc-secの安全確認とOwnerの決定を通す。 | TypeScript・vitestの利用例など、新依存が要る項目は、承認が得られるまで実装できない。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| O2 | workflowの追加・変更、必須の検査、利用先のCI変更などの保護対象は、別のOwner承認が要る。段の承認は、それらの実行許可ではない。 | 共有workflowの追加は、承認が得られるまで着手しない。 | 保護対象の規則 |
| O3 | 1つの単位は1つのPRで扱う。各PRは独立監査（devauditor）と作者の受領、必須の検査を通し、作者以外の担当（suite-lead）が統合する。 | 単位の分け方は後の段で決まる。作った本人が自分の作業を監査・統合したことにしない。 | team・projectの記録 |
| O4 | DBの構造・権限・契約・セキュリティに触れる単位は、設計記録だけのPRで先に独立の設計監査を受け、その後にコードを書く。 | 本取り組みがこれらに触れるかは、設計の段で判定する。触れる場合は設計監査が先に入る。 | team・projectの記録 |
| O5 | 既存U1の作業を、この取り組みの開始を理由に中止・変更しない。 | 非公開の土台や既存U1の成果を、この取り組みの都合で変更しない。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| O6 | 新たな有料サービス・常設クラウド資源は導入しない。必要になった場合は内容を示して別に判断する。既存CIの利用も費用ゼロとは断定しない。 | 追加の資源が要る設計は、承認なしに採らない。 | [Q2] |
| O7 | 実製品への適用、全repoへの一括導入、社内の網羅率基準や既存80%の変更は初版に含めない。 | 利用先への適用は、別の判断・承認で扱う。 | [intent-statement.md](../intent-capture/intent-statement.md) |

## 方針の制約

| ID | 制約 | 影響 | Source |
|---|---|---|---|
| P1 | 非公開の土台は、読み取りの参考にとどめ、公開のrepoには転載せず、一般化して書き直す。 | 非公開の識別子・コード・製品固有の名前を、公開側の成果物に出さない。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| P2 | 公開のrepoの試験データ・出力・ログは、架空のデータだけにする。 | 負例や利用例の入力は、架空の名前・値で作る。 | [intent-statement.md](../intent-capture/intent-statement.md) |
| P3 | 検査コードの実行時に、npmの依存を足さない（Shirubeの`scripts/hygiene`の既存規約）。試験は`node:test`、行の網羅率は100%、TDD。 | 検査の置き場所と依存の持ち方を設計で決める。計測のための既製の道具は、開発・CI側の依存の扱いとして、O1の承認を通す。 | Shirubeのteam・projectの記録 |
| P4 | 成功の指標は自社が管理できる範囲に限る。市場・他社・利用先製品の結果は成功の判定に使わない。 | 成功の判定は、自社で観測できる試験結果・記録に限る。 | team・projectの記録 |
| P5 | 評価の基準は、設計・実装の標準S1〜S9と採択済みの基準の項目に照らす。外れるときは、採った判断と採らなかった代替を1行ずつ書く。 | 見直しの記録に、照らした項目のIDを書く。 | team・projectの記録 |

## Assumptions & Open Questions

- [assumption] 本取り組みはDBの構造・権限・契約・セキュリティに直接触れない（DB別jobは呼出しの形の検証で、DBのスキーマは作らない）。設計の段で、触れると分かった場合はO4を適用する。
- [assumption] 検査コードの置き場所（既存の検査の下か、別の場所か）は、P3の依存規約に影響する。設計の段で決める。
- Open: 新依存の候補ごとの、arc-secの確認とOwnerの決定（O1）。
- Open: 共有workflowの追加の承認（O2）。承認の対象と条件はOwnerが決める。
