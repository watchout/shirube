## Q1. [網羅率の測り方] 行の網羅率 100% の床を、checker の file のどこまでに当てるか

背景: 受付の checker（`scripts/hygiene/audit-admission.mjs`、180 行）の今の行の網羅率を、今ある試験 2 本（`tests/audit-admission.test.mjs`・`tests/audit-counterexamples.test.mjs`）で実測しました（公開 main の同じ版。計測は Node 24 の組込みの網羅率）。結果は 96.11%（行）で、試験が通らない行は 7 行です。

- 13〜16 行目: 実際に `gh api` を呼ぶ関数（今の試験は、`gh` を呼ばずに差し込みの `api` を使うので通らない）
- 178〜180 行目: 命令行から起動された時の入口（今の試験は `verifyAudit` を直接呼ぶので通らない）

チームの決まりは「行の網羅率の床は 100%。計測から除外する行が必要なら PR に理由を書き、独立監査で確認する」です。この 7 行は、この取り組みで足す・変える行ではありません。

たとえば、受付で 1 行でも新しく試験が通らない行があれば、それは「新しい宣言の判定の行が、どの試験でも確かめられていない」ことになります。一方、既にある 7 行まで 100% にするには、偽の `gh` を PATH に置く試験と、子の process で入口を起動する試験が要り、取り組みの範囲が広がります。

- A. この取り組みで足す・変える行だけを 100% にし、既にある通らない 7 行（13〜16 行目、178〜180 行目に当たる行。内容の SHA-256 で名指す）は、PR に理由を書いて除外として独立監査に確認してもらう。実測の記録に、通らない行が「その 7 行と同じ内容の行」だけであることを含める（1 行でも増えれば失敗）
- B. file 全体を 100% にする。偽の `gh`（PATH に置く）で 13〜16 行目を、子の process で 178〜180 行目を通す試験を足す（この取り組みの試験の範囲が広がり、子の process が網羅率に数えられるかの確かめも要る）
