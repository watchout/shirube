## Owner 指定の順序と、確認できる成果

Bolt は、対象の単位を設計から実装・確認まで通し、動く成果を得るひとまとまりである。この取り組みでは1単位ずつ扱う既定を維持する。下表は今回 Owner が指定した価値の優先順であり、既存の7辺をすべて満たす。ただし、現行 AI-DLC 2.11.1 が実際に解決する単位順への反映は未成立であり、本書の並びだけで実行順を変えるものではない。

| 順 | 対象 | その成果で確かめること |
|---|---|---|
| 1 | U1 CI の記録照合 | 最初の最小統合版として、実 PR の4条件が通る正例と、欠落・不一致・観測不能で実 CI が止まる負例。今回の R-01/R-02 を設計と試験へ組み込む |
| 2 | U4 信頼版の CI 再検査 | traceability と upstream-coverage を信頼する版から実 PR に再実行し、未実行や自己弱体化でも門を止める。U1 と合わせて4つの確かめを先にそろえる |
| 3 | U2 実状態と設定の対話 | 実ファイル・版・設定・規格を観測し、不足と観測不能を区別して説明する。開始の効果は出さない |
| 4 | U3 正規開始・停止・照会 | 明示開始から正式 AI-DLC の現対象へ接続し、人待ち・失敗で停止、結果不明時は照会する |
| 5 | U5 安全な配布と初回実ゴール | 実導入・再読・設定のずれ・復旧を確認し、U1〜U5 の導入相談から最初の実機能の完成までつなぐ |
| 6 | U7 AUN の実受入 | 既存担当へ対象版を渡し、AUN の実適用・実 PR の正負・実設定のずれと復旧を確認する。継続開発中の受け手へ、U6 の追加開発より先に届ける |
| 7 | U6 初回後の実際の追加変更 | 初回完了後の新要求から、選択→現状態の再照合→案内切替を本当の新差分として完成させる。AUN の受入済み版に影響する変更なら対象版を再検証する |

順序の理由は、Owner 指定のとおり U1 と U4 の4つの確かめを先にそろえ、ベースの初回利用経路が完成した後、開発を続けている AUN へ U6 より先に届けるためである。U1 だけで初回実ゴール、U1〜U5 だけで全体完了とはしない。先に確認した AUN の版へ U6 の差分が影響すれば、影響する実 PR・実設定・規格と対象の最終版を再検証する。古い AUN の成功を新しい版へ無条件に流用しない。複雑さの相対評価は既存単位のものを保持し、根拠のない点数・期限・稼働可能性を補わない。

依存の上で無理な入れ替えはない。U4 は U1 の後、U3 は U1/U2 の後、U5 は U3/U4 の後、U7 と U6 はどちらも U5 の後となり、7辺すべてを満たす。U2 と U4、U6 と U7 の間に、順序変更のための偽の辺を加えない。

実行上は、正規の設計担当による現行 AI-DLC 2.11.1 の読取り確認で、computeBatches が依存階層ごとの名前順へ並べ、batches.flat() の順を用いるため、従来の U1→U2→U3→U4→U5→U6→U7 が解決されるとの報告を受けた。priority/order 属性や YAML の記載順による正式な優先順指定は確認できていない。再開用の --unit 指定、到達していない単位の開始や別のチーム運用も、今回の順序変更が成立した根拠にしない。

したがって「DAG 上は実行可能だが、現在の runtime の単位順への反映は未成立」を実行上の未解決事項として残す。U1 の後に U4 へ進む境目までに、Owner 指定順と正式な経路の適合を確認する。bolt-plan.md の行だけの変更、単位の改名、偽の辺、state/cache の編集、段の jump による迂回で実現したとはしない。この計画では新道具・engine の変更・別取り組み・外部提案の設計へ広げない。
