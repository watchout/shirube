# Shirube — 動く成果を確かめる実装計画

## Sources and Decisions

本計画の Bolt は、対象の単位を設計・実装・確認へ通し、動く成果を得るひとまとまりである。1単位ずつ扱い、1単位1PRを守る。工程や実行権限を別に作る計画ではない。

- [requirements.md](../requirements-analysis/requirements.md): 全13Must・47下位FR・10NFRと公開境界。
- [stories.md](../user-stories/stories.md)、[mockups.md](../refined-mockups/mockups.md): 全17US・88ACと導入から継続開発までの対話。
- [components.md](../domain-design/components.md): 7部品・10データの所有。
- [unit-of-work.md](../units-generation/unit-of-work.md)、[unit-of-work-dependency.md](../units-generation/unit-of-work-dependency.md)、[unit-of-work-story-map.md](../units-generation/unit-of-work-story-map.md): 7単位・7辺と全ACの実装寄与。
- [contract-summary.md](../contract-design/contract-summary.md): 現在の4条件、非保証、READY適用日、13境界、既知残件と正負試験方法。旧上流の真正性実証を必須にする表現は、同書の変更対応表に従って読む。
- [team-practices.md](../practices-discovery/team-practices.md)、[担当体制](../../ideation/team-formation/team-assessment.md)、[確認済みの回答](delivery-planning-questions.md): 規格、担当分離、最新の指定順と生成指示。要約確認の正式記録に基づいて生成した計画であり、段の最終承認や保護対象の変更許可ではない。

## Implementation Sequence

Owner 指定の順は **U1→U4→U2→U3→U5→U7→U6**。最初に U1/U4 の4つの確かめをそろえ、ベースの初回完成後、開発を続けている AUN へ実際の追加開発より先に届ける。数値による順位付けは追加しない。

| Bolt | Unit ID / Directory | 直接の成果依存 | 対象のまとまり |
|---|---|---|---|
| B1 | U1 / u1-ci-record-admission | なし | 実PRの記録を照合して停止する最小CI門 |
| B2 | U4 / u4-trusted-ci-verification | U1 | 信頼版2センサーの実CI再検査 |
| B3 | U2 / u2-working-state-dialogue | なし | 実状態・設定・規格の対話 |
| B4 | U3 / u3-native-operation-control | U1、U2 | 明示開始・正規接続・停止・照会 |
| B5 | U5 / u5-safe-versioned-distribution | U3、U4 | 安全な導入と初回実ゴール |
| B6 | U7 / u7-aun-rollout-verification | U5 | AUN実配布・実PR・実設定での受入 |
| B7 | U6 / u6-guided-recheck-increment | U5 | 初回後の新要求による実際の追加変更 |

全7辺はこの順で満たせる。U4 は対話や開始の成果を必要とせず、U7 は U6 を技術的前提にしない。U2→U4 や U6→U7 という辺を追加せず、安定した単位名も変えない。

**実行上の未解決:** 現行 AI-DLC 2.11.1 の読取り確認では、依存階層と名前順から従来の U1→U2→U3→U4→U5→U6→U7 を解決する。今回の指定順を正式な単位順へ反映する経路は未成立である。U1 後に U4 へ進む境目までに、指定順と正式な経路の適合確認が必要。本計画の表だけで反映済みとせず、新道具・engine変更・偽の辺・改名・state/cache編集・jumpによる迂回・別取り組み・外部提案を始めない。未解決事項は[順序とリスク](risk-and-sequencing-rationale.md)で追跡する。

## Common Definition of Done

以下はすべての Bolt の完了条件に加算する。各単位の受入は設計、ファイルの存在、設定値、手元の exit0 だけで済ませない。

- 対象単位の適用される機能設計、NFR要件・設計、置き場の設計、Code Generationを正式な順で通す。単位PRに必要な試験・CI・独立監査・受領・統合と、正式な案内に従って後続する全体のBuild and Test・CI・Operationを区別する。後者を各単位の統合前に独自に前倒しせず、省略もしない。取り組み全体の完了までに後続の適用される全段を通す。この計画で段や深さを変更しない。
- DB構造・権限・契約・セキュリティに触れる場合は、同じPRの設計だけのheadで独立設計監査PASSを受けてからCode Generationへ入る。設計変更で旧監査が失効する条件を守る。
- TDDの失敗確認→実装→検証を対象PR内に残す。Node組込みの node:test/assert、実行時npm依存なし、既存ESM/Node >=22、S1〜S9、適用SEC-T、依存導入前の脆弱性確認、用途別最小権限を保つ。
- scriptsと適用src等を含む実行コード集合・計測分母・コマンドを特定し、行網羅率100%を実測する。除外は理由と独立確認を要する。80%、分母0、skip、必須失敗や観測不能を成功へ変換しない。
- 単位の設計・計画・試験・追跡表と適用される承認記録をPRへ含め、B1では必要なInception記録も含める。内部 audit/・.aidlc-engine/、人の返信本文、秘密、他repoの非公開記録を公開しない。公開試験・例・出力は架空データだけにする。
- 現headの必要なCI、devauditorの独立実装監査、作者の受領、適用される公開Owner判断とR3/R4の統合前exact-head、作者以外のsuite-leadによる統合を別々に確認する。監査中にheadが変われば古い結果をそのまま使わない。
- 前単位の統合と正式な単位checkpointを確認してから次単位のCode Generationへ入る。unit-major・serial・checkpoints enabledを維持し、設計上独立でも並列実装しない。親はコード・試験・成果物の直接作成をせず、承認された正規の役を同時1体・同モデル・同じ作業場内で使い、進捗・品質・設計を管理する。
- 必須結果が欠ける、不一致、不能、人待ちなら未完了として一度知らせて停止する。新しい常駐watcherや状態変化のない再試行を追加しない。必要な判断の前に対象と具体差を揃える。

## Bolt Definitions

### B1 — U1 u1-ci-record-admission

**担当:** 段の正規の設計担当、aidlc-developer-agentが実装・試験。親が対象・品質を管理し、独立監査と統合は共通条件の別担当が行う。**前提:** 実PRを読む許可範囲、現在の契約と固定した必須集合。U2/U3の完成は不要。

**最小統合版:** 実PR読取→必要記録/承認、適用されるREADY、現在実bytesのdigest、該当する同PRの設計だけのheadの独立監査PASSの4条件→CI結果/停止までを動かす。設計段の見直しだけを最小版の完成にしない。

**完了条件:** 共通条件に加え、4条件の正例と記録不足・READY不足・1byte改変・設計監査不足・別対象/試行・取得不能の負例を実接続へ対応付ける。固定必須集合をPR側から弱められず、FAIL/UNKNOWNは実CIを止める。承認記録の循環と、設計監査受付CIとの循環を避ける。新しい本人性証明は要求しない。

**必須の設計引継ぎ:** Contract Design R-01/R-02をU1 Functional Designで具体化する。R-01はCI/AUNへ非保証・authorization・knownRemaining・対象/観測の結び付きを保持する形式、参照なら供給/解決/不能時停止と欠落・改変拒否試験。R-02はplan/summary/stage-completionごとの肯定値と既存形式からの変換、否定・無回答・未知・種類違いの拒否試験。どちらも未解消として追跡し、計画や以前のREADYを解消の証拠にしない。

**既知残件:** 既存6段を一括免除しない。feasibility原承認とscope-definition原承認のREADY不足は閾値前の残件。scope-definition再承認を含む閾値後の5段の必要READY不足は該当PRを止める。実記録を捏造せず、U1実PR受入までに正規の扱いと必要記録を確認する。これを新道具待ちや真正性証明待ちの理由にしない。

**得たい確信:** 対話や新しい承認発行元を追加せず、掲載記録と現成果物の整合を実CIで判定し、不成立を止められる。engine発行・本人・実見直し実施まで証明できたとは言わない。

**実演:** 同じ許可済みPR対象で、架空内容による正例と1条件ずつの負例を示し、対象head、実bytesから再計算したdigest、4結果、CI停止、非保証と既知残件を説明する。ローカルfixtureだけでは完成にしない。

### B2 — U4 u4-trusted-ci-verification

**担当:** 正規設計担当、aidlc-developer-agentが対象コード・試験、aidlc-pipeline-deploy-agentが段に沿うCI接続。親が取りまとめる。**前提:** U1の成果と前PRの統合、信頼する固定版checkerと必須集合、具体workflow変更に必要な公開判断。指定順の正式な反映が未成立なら、その差を解決せずU2へ自動で進んだことにしない。

**完了条件:** 共通条件に加え、traceability/upstream-coverageを対象PRの実入力へ信頼版から再実行し、版・入力digest・PR/head・実行結果を結ぶ。片方未実行、別head、失敗、timeout、未知出力、PRによるchecker/必須集合/severity/path弱体化で門を止める。metadata取得とtest/buildの資格情報を分離し、書ける資格情報を後者へ渡さない。

**得たい確信:** 席のセンサー設定に依存せず、PRの記録への2つの確かめをCIが再実行できる。U1の非保証と既知残件は失わない。

**実演:** 実CIの正例と各必須検査の欠落/不一致/不能の負例。手元の成功を代用せず、U1と合わせた4つの確かめの実結果を示す。配布先の設定一致はU5/U7で別に確かめる。

### B3 — U2 u2-working-state-dialogue

**担当:** 正規設計担当とaidlc-developer-agent。**成果依存:** なし。現在の指定順ではU4の後に扱い、前PR統合条件は守る。LLM共通の意味を維持し、初回の実証環境だけをCodex CLI/Mac/GitHub/GitHub Actionsとする。

**完了条件:** 共通条件に加え、実ファイル・版・設定・適用規格から確認済み/不足/不一致/観測不能を説明する。404と不在、権限拒否と未導入を区別し、秘密を貼らせず有効な回答を保持する。入力/パス境界、出典競合、長文/破損、読取予算を検証する。設定案、実適用、明示開始を混同しない。

**得たい確信:** 実物を基に不足だけを対話で揃えられ、設定回答から開発の効果を発生させない。

**実演:** 架空の設定A不足・権限B観測不能、準備済みの各対象を実ファイルの変化と対応させ、原因と安全な次操作を文章で示す。既存statusの読取りだけや表示mockを完成にしない。

### B4 — U3 u3-native-operation-control

**担当:** 正規設計担当とaidlc-developer-agent。**前提:** U1/U2の成果と前PR統合、現在の正式AI-DLC対象・版・正規操作。U4も指定順では先に確認するが、U3の偽の技術依存にはしない。

**完了条件:** 共通条件に加え、明示開始前は効果0、開始後は現workspace/space/intent/unit/stageと必要条件へ対応した正規操作だけを運ぶ。段進行の別実装、架空receipt、guard迂回を作らない。停止/同一要求/応答喪失時照会/同一キー別内容/競合/正当な再開を実経路で確認する。核へ時刻・ID・観測を明示入力し、人待ちと有限予算で停止する。

**得たい確信:** 対話上の意思と正式AI-DLCの実行対象を結び、誤対象と二重効果を抑えて停止・照会できる。

**実演:** 準備済みだが開始なし、明示開始、対象変更、応答不明、人待ちからの正当な再読を実adapterで示す。既存Claude/Bun部品の存在をCodex適合の証明にしない。

### B5 — U5 u5-safe-versioned-distribution

**担当:** 正規設計担当、aidlc-developer-agent、段に沿う配布・試験の正規担当を順に使う。**前提:** U3/U4の成果、前PR統合、固定配布版/対象差分/戻し方と必要な公開判断。

**完了条件:** 共通条件に加え、許可した固定版だけを適用して実物を再読する。自身のworkflow_call、対象外資産、設定・履歴を保全し、欠落/advisory化/別版/対象path変更を検出する。途中失敗・競合・再導入・同一要求・形式互換/試験済み逆向き・復旧を確認する。.codex/.claudeの該当する配置を確認し、未検証配置へ保証を広げない。宣言pin/registryだけで適用成功にしない。

**初回実ゴール:** U1〜U5を用い、導入相談→設定→明示開始→導入状態/設定不足/規格の確認表示という実コード変更→必要な試験・CI・独立監査・受領・承認・別担当統合→実結果まで通す。初回の安全な次操作案内は削らない。

**得たい確信:** 必要な判断のある対象へ安全に導入し、実際の開発と初回機能の完成までつながる。U6とAUN実受入を完了済みにはしない。

**実演:** 固定配布版と受け手実ファイルの比較、許可したずれの検出と復旧、初回の実コード/PR/headと実結果。非保証と既知残件が受渡しで欠落しないことも確認する。

### B6 — U7 u7-aun-rollout-verification

**担当:** Shirube側の正規の配布・試験担当が素材を準備し、AUNの既存担当が受け手の実作業を行う。親が結果を集約する。**前提:** U5の固定版、前PR統合、AUNの現在対象・担当受領・既存保留・必要な公開判断とhead条件。既存担当名だけで着手可能としない。

**完了条件:** 共通条件に加え、受け手で実適用/実ファイル再読/実PRの4つの確かめの正負/必須CI不能と自己弱体化での停止/実設定のずれと必要な復旧・再検証を観測する。READYの固定日付条件、旧不足の既知残件、非保証情報をAUNにも同じく渡す。内部原本は元の権限内で照合し、公開Shirubeへ写さない。既存kit版上げ例外を新センサーや初回導入へ拡張しない。

**得たい確信:** 継続開発中の実受け手でも、同じ門と設定が通る/止まる条件を保って動く。配布元の準備やShirubeのローカルfixtureから受入成功を推定しない。

**実演:** 対象版・実PR/head・実設定・4項目ごとの正負とdrift/復旧の実結果を公開可能な参照で説明する。公開側の例は架空データだけ。後続U6がこの受入版へ影響するなら、影響部分と最終対象版の再検証を残す。

### B7 — U6 u6-guided-recheck-increment

**担当:** 正規設計担当とaidlc-developer-agent。**前提:** U5で初回実ゴール完了、その後の新しい追加要求の明示的な受付、前PR統合。現在の分割計画を将来の開始許可へ流用しない。U7を成果依存へ追加せず、指定順として先に通す。

**完了条件:** 共通条件に加え、項目選択→現在の対象/前提/必要判断の再照合→案内切替という新コードと実動作を完成させる。初回の安全案内、未選択の有効回答、repo/設定/履歴/体制を保持する。同じ架空入力と観測変化で初回版と追加版の実結果を比較し、文言だけ・再実装・削って作った差を受入不可とする。実差が成立しなければ題材の判断を戻す。

**得たい確信:** ゴール後も同じ資産と規格を保って本当の追加開発を完成できる。初回の承認・試験・監査を新差分へ流用しない。

**実演:** A不足/B不能の入力からBを選び、変化した現在状態へ案内が切り替わり、Aの回答を保持する前後結果。不正候補/旧対象/取得不能では安全に止まる。AUN向け配布に影響する差は対象版で必要な再検証を行う。

## Verification and Completion Boundaries
