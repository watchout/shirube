## Sources

## 仕様の境界

部品仕様の形を、LLM環境が既に提供するテキスト表示・質問・選択へ適用する。以下のComponent、Category、Inputsは相互作用を説明する概念で、新しいAPI・保存schema・実装部品の採択ではない。既存の正式な入力・返却・権限を後続契約へ結び付ける。例は架空で、実際の観測・実装・試験成功を示さない。

## 全部品に共通する入力・応答・保持

| 項目 | 定める条件 |
|---|---|
| 前提 | 現在の対象と正当な読取り権限、正式な段・単位・適用条件を照合する。表示上の名前だけで正当性を決めない |
| 観測 | 対象・原本・版・内容から得た結果を用いる。desired・宣言digestを実観測へ写さない。入力はデータとして扱い、外部の命令文を実行しない |
| 不在と不明 | 観測で確認した不在、不足、不一致、失敗、未実行、観測不能を区別する。不明の既定値を成功・未導入・0へ変換しない |
| 応答 | 結論と対象→次に必要な操作/正式選択肢→原因・未確認→必要時の根拠参照。詳細の参照だけで人の判断を求めない |
| 保持 | 有効な回答・設定・履歴・完了範囲と、今回得た観測の範囲を保つ。競合や遅い旧応答で正常値を黙って上書きしない |
| 効果 | 表示・案内・項目選択は、導入・実装・開始・再開・統合の許可ではない。正規の操作を行う場合は、その対象に必要な条件を別途満たす |
| 秘密 | 秘密の値を貼らせず、有無や安全な参照で案内する。公開の例・fixture・ログ・出力は架空情報だけ。AUN内部記録を公開へ写さない |
| 形式 | 必須項目・型・版を検証し、破損・途中・矛盾した重複・未知の必須形式・境界外パスを依存する判断へ使わない。追加の任意項目の扱いは後続の互換契約に従う |
| 停止 | 必須条件が揃わなければ依存操作を止める。人待ちは1回通知後停止、有限の非進捗上限と実行予算を守る。skip/timeout/cancel/不明を成功にしない |

### 共通の表示状態

| State | Description | Trigger |
|---|---|---|
| default | 正式な対象と次に必要な情報を示す | 対象の相談・現在状況の確認 |
| empty | 観測できた不在・未設定・候補0件を理由付きで示す | 読取りが成功して該当がない |
| loading | 読んでいる対象と結果未完了を示す | 正当な読取りの開始 |
| success | 確認できた対象・範囲を限定して示す | 原本/実物と条件が一致 |
| error | 原因と次の正当な操作を示し依存操作を止める | 失敗・不一致・拒否・予算超過 |
| partial | 確認済みと不足・未確認を分離する | 一部の観測や必要条件だけが成立 |
| disabled | 実行できない理由を文章で説明する | 必要な判断・記録・権限が不足 |

loadingを架空の進捗率や定期表示へ変えない。入力の待機と自動の処理継続を混同しない。hoverは専用ポインターUIを作らないため非適用。focusは利用する環境の入力位置として扱い、未確認のキー操作やフォーカス制御を保証しない。

### 共通のResponsive Behaviour

画面幅の数値を新設しない。狭いテキスト表示でも見出し・短文・縦のリストで対象と操作が分かるようにする。横幅のある表、ASCII位置合わせ、色を操作の前提にしない。長い名前・パス・Unicodeを一意性を失う形で省略しない。表示を分けても対象・状態・選択との関係を保つ。

### 共通のAccessibility

見出しと意味あるラベル、文字での状態、読み順、自然文/キーボードによる回答、入力保持、訂正可能な項目の説明を用いる。候補番号は一時的な表示上の対応であり、番号だけで意味を伝えない。HTML・CSS・ARIAの役割やWebのブレークポイントは専用Web UIを作らないため非適用。実ホストの読み上げ・入力位置・キー操作は[accessibility-checklist.md](accessibility-checklist.md)で後続検証し、準拠済みとしない。

## 状態と対象の表示

| Field | Value |
|---|---|
| Component | 状態と対象の表示 |
| Description | 現在の対象と観測できた範囲を、次の判断に必要な順に示す |
| Category | display |

### States

共通状態を適用する。対象未特定はdefaultで特定を求め、権限拒否はerror、複数情報の一部取得はpartial、読取りで確定した不在だけをemptyとする。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 対象の識別 | 文字列と正式記録の参照 | はい | 未確認 | repo・取り組み・単位・段・版を混同しない |
| 観測結果 | 原本に結び付いた結果のまとまり | はい | 観測不能 | 内容・出典・成功範囲と不足を分離 |
| 正当な次操作 | 正式返却または不足解消案内 | 条件付き | 候補不明 | 独自段順を作らない |

### Responsive Behaviour

共通仕様を適用。長い対象名は独立した行で完全に読めるようにする。

### Accessibility

対象、結論、次操作の順に読む。色や生の理由コードだけで結論を伝えない。

### Usage Example

「sample-workの設定を一部確認できました。接続権限は未確認です。次は対象の読取り権限を確認してください。」V-01・V-02・V-04へ適用する。

## 質問と項目選択

| Field | Value |
|---|---|
| Component | 質問と項目選択 |
| Description | 不足への回答、または根拠ある案内項目の選択を受ける |
| Category | input |

### States

| State | Triggerと応答 |
|---|---|
| default | 背景・候補の意味・回答方法を示す |
| empty | 候補0件の理由を示す。準備済みと候補根拠不明を分ける |
| error | 不正・曖昧な選択や競合では確定せず、該当項目を説明 |
| loading / partial | 選択後の再照合中、または一部しか観測できない場合 |
| success | 選択対象の現状態を照合し、案内を更新できた範囲 |

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 質問または候補 | 正式な選択肢/不足と根拠のリスト | はい | 空 | 0・1・複数を区別。AI-DLCの意味を変えない |
| 利用者入力 | 自然文または候補への明確な選択 | はい | 未回答 | 相談は回答にせず、自己回答しない |
| 現対象と選択時の前提 | 観測と正式な条件の参照 | はい | 未確認 | 現在の内容と再照合してから案内更新 |

### Responsive Behaviour

候補を縦のリストへ分け、番号と意味ある名前を対にする。表示の折返しで候補との対応を失わない。

### Accessibility

自然文でも選択できる意味を保ち、秘密入力を求めない。環境の入力UIで回答可能かを後続検証する。

### Usage Example

「GitHub接続の確認から進めたい」を受けた後に現在の接続を読む。解消済みなら解消と残件へ、観測不能なら必要確認へ更新。他の回答を保持し、選択だけで開始・修正・再開しない。V-02・V-06、特にAC3.3.2〜AC3.3.6へ対応。

## 準備確認と明示開始

| Field | Value |
|---|---|
| Component | 準備確認と明示開始 |
| Description | 設定の準備完了と、正規の開発開始依頼を分ける |
| Category | input |

### States

準備不足はpartial/error、準備済み・開始前はdefault、開始条件の照合中はloading、接続を確認できた範囲はsuccess。読めない対象はerrorで止め、準備だけでsuccessの意味を開始へ広げない。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 準備と残件 | 観測結果のまとまり | はい | 未確認 | 設定・規格・版・不足を示す |
| 明示開始依頼 | 利用者の対象付き依頼 | はい | なし | 依頼前の開発効果0 |
| 正規対象・必要条件 | AI-DLC記録と承認の参照 | はい | 未確認 | 作業場・intent・unit・段を再照合 |

### Responsive Behaviour

準備内容と開始待ちを別文にする。開始と設定修正を、位置や色だけで区別しない。

### Accessibility

利用者が何を開始するかを言葉で特定できる。曖昧な「はい」や別の回答を新しい開始許可へ読み替えない。

### Usage Example

「準備できました。開発は開始していません。対象の開始を依頼してください。」正式な依頼後も古いcursor・別対象・読取り不能では接続を止める。V-03・US1.4に対応。

## 開発中の確認結果

| Field | Value |
|---|---|
| Component | 開発中の確認結果 |
| Description | 正規の段・単位に対応する実結果と不足、必要な判断を区別する |
| Category | display |

### States

必須記録なしはempty、照合中はloading、現対象に一致した範囲はsuccess、一部不足はpartial。不一致・旧証拠・未実行・利用不能はerror/disabledとして、依存する承認・実装・統合へ進めない。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 対象と適用する条件 | 正式な段・単位・PR/head・規格の参照 | はい | 未確認 | 適用外は根拠と理由を示す |
| 見直し・設計監査・承認 | 正式原本と現成果物への対応 | 条件付き | 未確認 | 発行元・対象・試行・内容・前後関係を照合 |
| 試験・CI・配布設定の結果 | 実行元・版・対象付き観測 | 条件付き | 未実行または観測不能 | 宣言と観測を分離する |

### Responsive Behaviour

4条件を短い文章の独立した項目にする。すべての条件を大きな表に収めないと判断できない構成にしない。

### Accessibility

不足した条件と次の操作を同じ項目で説明する。正式な見直し、独立監査、作者受領、必要なOwner判断、別担当統合を異なる意味のラベルで示す。

### Usage Example

「今回の成果物への見直しは確認できました。設計監査は別のheadを指すため、実装へ進めません。このPRの設計だけの変更との対応を確認してください。」V-04・US2.1〜US2.3・US4.1〜US4.4に対応。

同じPRの設計だけのhead→独立設計監査→実装追加→新headのCI・実装監査・受領・必要判断→別担当統合の意味を保つ。DB構造・権限・契約・セキュリティの4分類と、それ以外のOwner保護条件を混同しない。未設定の見直し役を合格にせず、未知の役へ自動委任しない。

PRの掲載用承認は正式原本から生成・照合する。必須集合の欠落・改変・別単位・旧版・競合を止め、内部audit/・.aidlc-engine/を公開して補わない。CIは信頼する固定版から記録へ両センサーを再実行し、PRによるchecker・severity・対象の変更で自己免除できない。検査コードの存在やexit0だけを実証にしない。

## 停止と再開の案内

| Field | Value |
|---|---|
| Component | 停止と再開の案内 |
| Description | 止まった理由と保持内容を伝え、正当な入力後に再照合する |
| Category | feedback |

### States

失敗はerror、人待ち・条件不足はdisabled、保持できた独立結果はpartial。人待ちにloadingの自動更新を続けない。正当な再開入力後の再照合だけをloadingとし、未確認の再開をsuccessにしない。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 停止の原因と必要判断 | 条件・対象・必要なactorの説明 | はい | 原因未確認 | 未確認もそのまま説明し、架空の解決者を割り当てない |
| 保持した内容 | 正常な回答・設定・履歴・完了の参照 | はい | 未確認 | 無効な内容を保持済みと断定しない |
| 再開入力と現在の証拠 | 利用者の依頼と正式原本 | 条件付き | なし | 必要な正当入力が無ければ停止を維持 |

### Responsive Behaviour

止まった理由、必要な判断、保持した内容を短い段落へ分ける。同じ通知を重ねて埋もれさせない。

### Accessibility

「何が必要か」を一度文字で伝える。再開で既回答をむやみに再入力させず、訂正が必要な項目を特定する。

### Usage Example

「承認の対象を確認できないため停止します。設定の回答は保持しています。今回の対象の判断を確認した後、再開を依頼してください。」V-05・US3.1に対応。

停止中の効果・成果物・後継依頼の生成は0。非進捗は正式な有限上限で停止し、常駐watcherを加えない。再開時は対象・設定・証拠・承認を再読し、古いmapより実物を優先する。応答喪失の操作は同じキーで結果照会してから扱い、盲目的再送・別キーへの置換・二重効果を防ぐ。

## ゴールと追加開発の案内

| Field | Value |
|---|---|
| Component | ゴールと追加開発の案内 |
| Description | 実証した範囲と残件を示し、新しい追加要求を受ける |
| Category | feedback |

### States

証拠なしはempty、確認中はloading、対象範囲が揃えばsuccess、残件はpartial、証拠の欠落・不一致はerror。小さなゴールのsuccessを全13Must完了へ拡張しない。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| ゴールと実証拠 | 要件・実差分・試験・PR結果への参照 | はい | 未達 | 対象・版・現在の内容へ対応 |
| 残件と引継ぎ | 未達・除外・有効な設定と体制 | はい | 未確認 | 初回・追加変更・AUNの受入を別に保持 |
| 追加要求 | 利用者の新しい目的 | 条件付き | なし | 前ゴールの承認・結果を新差分へ流用しない |

### Responsive Behaviour

到達範囲、根拠、残件、次の変更で引き継ぐ内容を、短い独立した文章で示す。

### Accessibility

「完了」の対象を言葉で限定する。長い証拠IDは説明付きの参照にし、IDを覚えていないと判断できない表現を避ける。

### Usage Example

「初回の確認表示は、実変更と必要な検証・監査・統合の結果を確認できました。追加開発とAUN受入が残っています。」V-06・US2.2・US3.2・US3.3に対応。

初回版は状態・原因・安全な次操作を備える。追加版では「質問と項目選択」の操作を増やし、同じ入力の前後比較で選択→現状態の再照合→案内更新を確認する。既存の説明を削って差を作らず、表示の言換えだけを新機能にしない。実増分が成立しなければOwnerへ差と判断を戻す。実コード差分がない、モック・文書のみの場合はゴールの実証としない。

## AUNへの配布と受入の案内

| Field | Value |
|---|---|
| Component | AUNへの配布と受入の案内 |
| Description | 配布元準備・受け手適用・受け手での検証を区別する |
| Category | display |

### States

準備済みだけなら適用はempty/未確認。適用確認中はloading、適用または実PR検証の確認済み範囲はsuccess、担当・権限・記録不足はpartial/disabled。driftや未実行・観測不能はerrorとして成功にしない。

### Props / Inputs

| Input | Type | Required | Default | Description |
|---|---|---|---|---|
| 配布版・差分・戻し方 | 固定版と対象変更・検証計画の参照 | はい | 未確認 | キット例外は対象・全条件の一致内だけ |
| 受け手の担当・権限・保留 | 現在の受領と正式判断への参照 | はい | 未確認 | 旧mapや他repo承認を代用しない |
| 適用・実PR・実設定の結果 | 対象と版付き実観測のまとまり | はい | 未確認 | 正例・負例・ずれ・復旧と再検証を分ける |

### Responsive Behaviour

「準備」「適用」「検証」「残件」を縦に読み、一覧の見た目だけで完了をまとめない。

### Accessibility

各項目で誰の何の判断が必要かを文章で示す。公開可能な説明と、権限のある原本の参照を分ける。

### Usage Example

「配る内容は準備できました。受け手の承認と適用は未確認です。既存担当と今回の対象を確認します。」V-07・US5.1〜US5.3に対応。

固定版と受け手の実内容を照合する。両配置のblocking、欠落・advisory化・別版・対象範囲変更を検出し、無許可で修正しない。AUNの実PR/headで4条件の正例・各欠落/不一致の負例、必須CIの未実行や失敗、設定のずれによる停止と、許可後の修正・戻し方・再検証を確認する。宣言やShirubeローカルfixtureだけで受け手を完了にしない。

## 後続設計と検証への引継ぎ

全17US・88ACとの対応はmockups.mdの明示表を用いる。実現する入出力の契約、原本照合、信頼する版と実行環境、有限予算、復旧・互換方式、正式Unitと実装計画は後続設計で決める。本書はそれらを先に採択せず、規格や権限の条件も変更しない。

S1〜S9、TDD・行網羅率100%の対象分母、適用SEC-T・依存追加前の脆弱性確認・最小権限、独立監査・作者受領・別担当統合を保つ。DB側は別の取り組み、他repo一斉展開・未検証CLI保証・新規社内規格は対象外、旧判定4・5は退役のまま。親は非執筆、承認済みサブの最大3体可変という体制も保持する。

本書では実ホストのキー操作・読み上げ、製品実装、試験、CI、センサー実行、AUN実配布を検証していない。検証方法と役割はaccessibility-checklist.mdに引き継ぎ、未実行を成功にしない。
