## 対象と読み方

専用Web画面を新設せず、LLMとのテキスト対話を詳細化する。以下のrepo名・設定・権限・検査結果はすべて架空の説明で、実際のGitHub接続や製品の実行結果ではない。初回の実証環境は社内のCodex CLI・Mac・GitHub・GitHub Actionsとし、別環境の成功は個別に検証する。

表示例の見出しは利用者に伝える情報の順であり、新しいAI-DLCの段・状態・承認ではない。API、コマンド名、保存schema、正式Unit、実装順は後続設計で定める。短い結論と対象、次に必要な操作または正式な選択肢を先に示し、原因・未確認・根拠を続ける。利用者がmdを開けなくても判断できる説明を会話に含める。

## 共通の状態表示

| 表示の分類 | 文章で伝える内容 | 進む条件と保持 |
|---|---|---|
| Empty | 観測により確認した未導入・未設定・該当記録なし。何を確認したかも示す | 必須の不足を埋める。取得失敗を不在にせず、既存回答を保つ |
| Loading | 「対象の設定を確認しています」など対象と未完了を示す | 結果が届く前に成功としない。有限予算内に確認できなければError/Partialとして止める |
| Success | 「この対象について確認できました」と範囲を限定する | 必須の残件・判断があれば次へ進めない。検査成功と権限・監査・統合を別に確認する |
| Error | 原因、影響する対象、安全な次の操作、必要な判断を示す | 依存する操作を停止。設定・回答・履歴を失わず、無制限に再試行しない |
| Partial | 確認できた内容と、未確認・不一致・不足を別々に示す | 部分的成功を全体完了にしない。独立した有効な回答を保つ |

各場面で成立する状態だけを使う。読取りが無い場面にLoadingを捏造せず、状態名をそのまま利用者に覚えさせない。文字だけで結論と操作が分かり、色・絵文字・表の横幅だけに依存しない。

## V-01 導入の相談と安全な適用

**対象:** US1.1・US1.2。利用者は導入対象を伝え、Shirubeは実際の対象・版・不足・差分を読む。

```text
利用者: このリポジトリにShirubeを導入したい。
Shirube: 対象は sample-work です。AI-DLCは確認できました。
         Shirubeの設定はまだ確認できていません。
         次に、読み取れる設定と不足を確認します。

Shirube: 導入に必要な変更を確認しました。
         既存の設定と履歴は保持します。変更する内容はこちらです。
         この変更に必要な承認が揃うまでは適用しません。
利用者: 必要な判断が揃った対象への適用を依頼する。
Shirube: 適用後の実ファイルを確認しています。
         設定の配置を確認できました。開発の開始はまだ行っていません。
```

| 状態・入力 | 応答と次の操作 | 進む条件・保持 |
|---|---|---|
| 未導入を実物から確認 | 「この対象には未導入です。必要な追加はこちらです」 | 読取りが可能で不在を確定できる。既存履歴を保つ |
| 404、権限拒否、取得不能 | 「導入の有無を確認できません。対象と読取り権限を確認してください」 | 未導入と断定しない。書ける資格情報を読取経路へ求めない |
| 道具の欠落・非対応版・起動不能 | 足りない道具と対応条件を説明し、開始を停止 | manifestの宣言だけで対応済みとしない |
| 適用差分に自身のworkflow_callの破損・対象外書込み・無許可の保護変更 | 「この変更は適用できません」と具体的な差を示す | 安全な自己導入の保護を外して通さない。必要な公開判断を保つ |
| 部分適用・容量不足・読取専用・中断 | 完了した範囲と未完了、前の正常状態を説明 | 半分の状態を有効にせず、回答・設定・履歴を保持 |
| 同じ操作の再送、応答喪失、形式の変更 | 元の結果を照会してから扱い、版と保全結果を説明 | 同一キー同内容は効果1回、別内容は衝突。形式変更は旧新同居と試験した逆向きを確認 |
| 空白・日本語・別表記のパス、境界外symlink・循環 | 対象を一意に説明し、境界外参照は拒否 | 同じ実体を重複計上せず、対象外の読書き0。入力を命令として扱わない |

適用前は差分と必要な判断、適用後は実物との照合結果を示す。準備への回答だけを新しい実装や保護設定の許可にしない。有限予算を使い切った読取りは観測不能として止める。

## V-02 不足だけを設定の対話で揃える

**対象:** US1.3。確認済みの内容は読み上げ直すだけにし、同じ回答を求めない。

```text
Shirube: 対象と導入する版は確認できました。
         開発の検証方法が1件未設定です。この項目だけ確認します。
         ここで必要なのは確認方法の指定です。秘密の値は貼らないでください。
利用者: 検証方法を指定する、または質問の意味を相談する。
Shirube: 回答を保持しました。実際の設定への反映結果を確認します。
         反映を確認できた項目と、まだ確認できない項目はこちらです。
```

| 状態・入力 | 応答と次の操作 | 保持・停止 |
|---|---|---|
| 設定済み／不足1件／観測不能 | それぞれ「確認済み」「この項目が不足」「読み取れず未確認」と区別 | 未確認を既定値やOwnerの回答で埋めない |
| 設定出典の競合・別対象・無効値 | 出典と食い違い、必要な判断だけを説明 | 優先関係は正式契約に従い、勝手に上書きしない。他の回答を保持 |
| 回答の保存・適用に失敗、確認後の変更 | 「回答は受け取りましたが、設定完了を確認できません」 | 回答、採用、適用、観測結果を分け、未適用を完了にしない |
| 秘密や非公開内容が含まれ得る | 値を求めず、有無や安全な参照先で確認する方法を説明 | 公開の会話・記録へ転記しない。読めないことを成功で補わない |
| 空白・Unicode・区切り文字・制御文字・長文・破損入力 | 入力をデータとして安全に表示し、直す項目を特定 | 必須形式不備や過大入力は依存判定に使わず、無言の切捨てをしない |

質問の背景と選択肢の違いを文章で説明する。利用者が相談した場合は回答を推定せず、意味を説明してから決まった内容を記録する。選択番号だけに頼らず、自然文で何を選んだか分かる構成にする。

## V-03 準備の確認と明示的な開発開始

**対象:** US1.4。準備が揃っていることと、開発開始の許可を分ける。

```text
Shirube: sample-workの導入と設定を確認できました。
         適用する規格と残件はこちらです。現在は開発開始待ちです。
利用者: この対象で開発を開始してください。
Shirube: 現在の対象とAI-DLCの記録を確認します。
         正式な開始または継続の条件に従って進めます。
```

| 状態・入力 | 表示・判断 | 進む条件 |
|---|---|---|
| 準備済み・開始依頼なし | 「準備できました。開始の依頼をお待ちしています」 | 開発の効果0。準備の回答を開始依頼にしない |
| 明示開始と正しい現対象 | 作業場・取り組み・単位・段を利用者に分かる名前で示す | 実際の正式記録と必要条件を照合して接続する |
| 古いcursor・別対象・記録の読取不能 | 不足を説明して停止 | 独自に別intentの作成・切替・再開をしない |
| 導入承認・前ゴールの完了だけがある | 新しい開始・計画・保護対象に必要な判断を区別 | 一括の実行許可に流用しない |

初回に実証した道具と版を説明し、LLM共通の入口と、別CLIで動作確認済みかを分ける。正式な問い・選択肢・承認は意味を保って利用者の言語で伝える。

## V-04 開発中の結果・必要な判断・4つの確かめ

**対象:** US2.1〜US2.3・US4.1〜US4.4。表示する順は情報の読み順であり、実行順を新設しない。

```text
Shirube: 今回の単位の実装には、先に設計監査の確認が必要です。
         対象は sample-work の今回の設計です。
         現在の成果物への見直し: 確認できました。
         実装前の設計監査: 対象との対応が未確認です。
         次は、このPRの設計だけの変更と監査結果の対応を確認します。
         対応が確認できるまでは実装へ進みません。
```

| 確認する内容 | 正しく確認できた表示 | 不足・不一致・観測不能の表示と停止 |
|---|---|---|
| 正式な見直し | 現作業場・intent・unit・段・試行・現成果物に対応する実際のREADYを確認した範囲 | 別対象、旧試行、修正前、改変、発行元不明、自己生成、NOT-READY、未設定、実行不能、未実施は条件未達。READYの文字だけで通さない |
| 実装前の設計監査 | DB構造・権限・契約・セキュリティの該当分類、同じPRの設計だけのhead、独立監査との対応と前後関係 | 自己申告で対象外にせず不明は確認待ち。未監査、別PR/単位、実装入りhead、順序不明は実装へ進めない。設計変更時は現設計の監査確認へ戻る |
| 単位PRの記録と承認 | 必須の設計・計画・試験・追跡表と原本に対応する承認、初回単位のInceptionを確認した結果 | 0件/1件不足、別単位、古い承認、任意JSON、改変、矛盾する重複、壊れた/途中の記録、照合中の変更を検出して停止。内部audit/・.aidlc-engine/や秘密を掲載して補わない |
| CIによる再検査 | 信頼する検査元と固定版から、対象PR/headの記録へtraceabilityとupstream-coverageを再実行した両方の実結果 | 未実行、片方欠落、別head、旧run、不一致、利用不能、timeout、skip、壊れた出力では門を止める。手元の成功やexit0だけを代用しない |

```text
Shirube: このPRでは、必要な承認記録が1件不足しています。
         次は、今回の対象に対応する承認記録を確認してPRへ含めてください。
         以前の成果物に対する承認は、今回の承認として使えません。
         内部ログを公開する必要はありません。
```

**受渡しと品質の案内:**

- 正式な段・単位と適用検査を実記録で照合する。1単位1PRとし、前の単位の統合を観測するまで次単位のCode Generationへ進まない。複数単位を混在させない。
- 作者による監査依頼、独立監査、作者の受領、作者以外の統合、必要な公開Owner判断を分けて伝える。headが変わった後に以前のCI・監査を有効と表示しない。設計監査後の実装にも新headの確認と実装監査が必要である。
- 証拠は要件・設計・受入・試験・PRと現対象・版へ双方向に対応付ける。欠落・改変・別対象・旧版・発行元不明・本人性不明・矛盾・不正な時刻や順序では未達とする。入力中の命令を実行しない。
- desiredや宣言digestを観測結果へコピーしない。実物だけを変えた負例で不一致になることを確認する。判定の核には時刻・識別子・乱数を明示入力とし、同義のadapter入力で意味が揃う条件を保持する。
- 採択規格の項目ID・版・出典・適用対象・検証方法・証拠・合否を要約し、適用外は理由を示す。TDD、Node組込み試験、scriptsと該当srcを含む分母での行網羅率100%、適用SEC-T、依存追加前の脆弱性確認を保持する。80%・分母0・未計測・勝手な除外を合格にしない。
- metadata読取経路の読取専用権限、test/buildへ書ける資格情報を配らない条件を表示の説明で弱めない。PRが検査元・必須集合・severity・対象pathを変更しても、信頼する正本からの検査を自己免除できない。
- 見直し役は承認済みの同時1体・親と同モデル・段の見直しという条件を保ち、PRの独立監査を代替しない。未設定を合格例外にせず、未知の役へ自動委任しない。自動の初期化へ新しい人承認を加えない。
- S1〜S9と既存のESM・依存方向・ソース構造・秘密・各CLIの結果契約を保持する。必須失敗の隠蔽、無条件PASS、退役した道筋・判定4・5・独自予算を成功経路にしない。規格や版の変更では影響する証拠を再確認し、自動採択・適用の権限にしない。

## V-05 失敗・人待ち・中断と正当な再開

**対象:** US3.1。失敗と観測不能を成功から分け、必要な人の判断がある場合は1回知らせて停止する。

```text
Shirube: 対象の承認を確認できないため、ここで停止します。
         保持している内容: 設定への回答と、確認できた結果。
         必要なこと: 今回の対象についてのOwner判断の確認。
         条件が変わった後、再開を依頼してください。
利用者: 必要な判断が揃ったので再開してください。
Shirube: 現在の対象・設定・証拠・承認を読み直します。
         変わっていない回答は保持し、未完了の箇所から進めます。
```

| 分岐 | 説明・操作・保持 |
|---|---|
| 失敗、未実行、timeout、skip、cancel | 原因と依存する停止範囲を示す。任意または正式適用外は理由を付け、必須の未実行と分ける |
| 人待ち | 必要な判断を一度伝え、効果・成果物・後継記録を生成し続けない。待機を自動再開の許可にしない |
| 連続非進捗 | 正式な有限上限（既定3回）で停止。常駐watcherや状態変化なしの再試行を追加しない |
| 中断後の設定・対象・承認変更 | 古いmapや記憶で進めず、実物を再照合する。有効な回答と履歴を保つ |
| 効果の応答喪失 | 「結果は未確認です。再送前に元の操作を照会します」と説明。同じキーの同内容は効果1回、別内容は拒否 |
| 同時更新・遅い旧応答 | 競合と現在との差を示し、正常設定を黙って上書きしない |
| 照会・subprocessの予算超過 | 観測不能と必要な判断を示し、成功・自動再試行へ変換しない |

## V-06 初回の完成、実際の追加開発、案内更新

**対象:** US2.2・US3.2・US3.3。実際の初回完了後、新しい要求として追加変更を受け付ける。設定・記録・規格・体制を引き継ぎ、追加差分の試験・CI・監査・受領・承認・別担当統合と実結果を改めて確認する。

```text
Shirube: 初回の確認表示の機能について、実コードの変更と必要な検証、
         監査・承認・統合、実行結果を確認できました。
         追加開発とAUNでの検証は、まだ全体の残件です。
利用者: 項目を選んだら、現在の状態を再確認して案内を更新する機能を追加したい。
Shirube: 新しい変更の目的として受け付けます。
         初回の設定と記録を保持し、必要な段と判断に従って進めます。
```

**同じ入力での対比（架空の例）:** 初回にも安全な原因・次操作の説明を備える。追加後は、利用者の項目選択を受けた再照合と案内の切替を実行して示す。

| 入力・利用者の操作 | 初回にも必要な説明 | 追加後に観測する動作と応答 |
|---|---|---|
| GitHub接続を確認できず、検証方法も未設定 | 「GitHubの読取り権限を確認してください。検証方法も未設定です」 | 根拠のある候補から「GitHubの接続確認」を選べる。独自の開発段や実行権限を足さない |
| 利用者が「GitHub接続の確認から進めたい」。その間に読取可能へ変化 | 再観測した結果があれば古い状態を流用しない | 選択した対象と前提を再照合し、「今は読み取れます。接続の問題は解消しています。検証方法の設定が残っています」と案内を更新する |
| 同じ選択だが今も読取不能 | 未確認を成功や未導入にしない | 「まだ接続を確認できません。読取り権限の確認が必要です」と停止を案内し、他の回答を保持 |
| 取得はできるが選択した項目の不足が未解消 | 不足を不足として説明 | 現在の不足と次の正当な確認操作へ更新。選択しただけで不足を解消済みにしない |
| 選択中に対象・設定・必要判断が変わる | 古い証拠で進めない | 旧候補を無効な前提のまま使わず、現在の根拠ある候補へ切替。観測不能なら停止 |
| 候補0件 | 準備状態や未確認を区別 | 候補なしの理由を示す。準備済みなら明示開始待ち、根拠不明なら停止。候補を捏造しない |
| 候補1件／複数 | 正式な操作の意味を説明 | 意味ある名前で選べ、対象を再照合する。不正・曖昧な選択を勝手に確定しない。未選択の状態と回答を保持 |

```text
利用者: GitHubの接続確認から進めたい。
Shirube: 現在の対象の接続を確認しました。今は読み取れます。
         残っているのは検証方法の設定です。
         開発はまだ開始していません。
```

この例は実際の接続確認の報告ではない。実証では同じ架空入力と観測変化を初回版・追加版に与え、新しい選択→再照合→案内更新の実結果と新コード差分を並べる。文言変更、必須案内の再実装、既存機能を削って作った差は合格にしない。既に同じ機能があれば取り除かず、実増分が成立しなければ差を示してOwnerへ判断を戻す。

初回や追加変更のゴールを、モック・文書・既存statusの読取りだけで完了にしない。要件・設計・受入・試験・PRと結果の対応を示し、初回の合格を追加差分へ流用しない。2つのゴールだけで全13MustやAUNの受入まで完了としない。

## V-07 AUNへの版付き配布と実PRでの確認

**対象:** US5.1〜US5.3。配布元の準備、受け手の適用、受け手での検証を別々に示す。

```text
Shirube: AUNへ渡す版と差分、確認方法と戻し方を準備しました。
         AUNの現在の担当者の受領と、必要な判断はまだ未確認です。
         次は既存担当と対象・保留・必要な承認を確認します。
         準備だけで適用済みとは扱いません。

Shirube: 受け手の実ファイルへの適用を確認しました。
         実際のPRでの検証は未完了です。
         次は許可された正例・負例と設定のずれを確認します。
```

| 確認 | 通る場合の案内 | 未確認・負例の案内と停止 |
|---|---|---|
| 受渡しと権限 | 固定版・差分・確認方法・戻し方・実担当の受領・対象head条件を示す | mapの担当名だけで着手せず、既存保留と必要な公開判断を保つ。不足は一度説明して停止 |
| 適用 | 受け手の実ファイルと版を配布内容と比較した結果 | pinやregistryの宣言だけ、欠落・途中失敗・対象外書込みでは成功にしない |
| 設定のずれ | 観測した実内容から一致を確認 | 1項目欠落・advisory化・別版・対象範囲変更を検出。観測不能は一致でない。無許可で修正しない |
| 更新と戻し方 | 該当する.claude/.codex両配置のblocking、固定版と必要な再検証を示す | 未検証配置へ保証を広げない。復旧・修正・受け手の再検証も必要な判断後に確認 |
| AUNの実PRの正例 | 現PR/head、受け手の版、4条件、CIと門の実結果を対応付ける | Shirubeのローカルfixtureや別PRで代用しない |
| 4条件の負例 | 欠落・不一致・別対象・古い記録を各条件へ1つずつ与え、止まった実結果を示す | READY文字列、自己申告、旧CI、未実行・失敗・利用不能、PR側の弱体化で通さない |
| 実設定の負例 | 許可されたずれを作り、比較と門の停止、修正・戻し方・再検証を示す | 負例は架空入力と承認された対象だけ。設定を無許可で変えない |
| 公開する結果 | 公開可能な結果と架空例、権限ある原本の参照を分ける | AUN内部記録・秘密を公開側へ転記しない。原本が読めなければ観測不能 |

既存キット版上げの例外は全条件・対象の一致する範囲だけに限る。初回導入・新センサー・保護設定へ広げない。AUNの結果にも採択規格と必要な試験・100%分母・安全確認を保ち、初回・追加変更・AUNそれぞれの実結果と残件から全体を判断する。
