# Shirube — 既存の対話表示への対応

## Sources

- [wireframes.md](../../ideation/rough-mockups/wireframes.md)・[user-flow.md](../../ideation/rough-mockups/user-flow.md): 専用Web画面を加えず、LLMとの対話を入口にする既存の案。
- [stories.md](../user-stories/stories.md)・[requirements.md](../requirements-analysis/requirements.md): 案内・入力・状態・権限・公開範囲と実証条件。
- [team-practices.md](../practices-discovery/team-practices.md)・[refined-mockups-questions.md](refined-mockups-questions.md): 採択済みの実践と確認済みの詳細化方針。
- [mockups.md](mockups.md)・[interaction-spec.md](interaction-spec.md): 具体的な対話と相互作用の対応先。

## 対応の方針

新しいデザインシステム、テーマ、CSS、画面、フォントや色の規格を策定しない。LLM環境が提供する見出し・本文・リスト・質問・選択・参照を利用し、使えない表示能力を前提にしない。以下は採用する表現の意味と確認方法の対応であり、特定ホストで動作を検証済みという表ではない。

見た目より、同じ結果が同じ意味で伝わることを優先する。AI-DLCの正式な問い・選択肢・承認の意味は保持し、表示形式だけを環境に合わせる。初回のCodex環境での結果を他CLIの保証へ広げない。

## 対話要素との対応

| Shirubeの情報 | 利用する既存表現 | 内容と一貫性 | 確認方法 |
|---|---|---|---|
| 対象 | 見出しと短い本文 | repo・取り組み・単位・段のうち判断に必要なものを名前で示す。長いIDは必要時の詳細へ | 別対象の入力でも混同せず、全文から一意に特定できるか |
| 結論 | 冒頭の短い文章 | 「確認できました」「不足しています」「確認できません」「一致しません」の意味を分離 | 観測済み不在・権限拒否・不一致を異なる結論にできるか |
| 既知と不足 | 縦の短いリスト | 既知の設定を再質問せず、不足・競合・未確認だけを質問へ | 1項目変更で他の回答を失わないか |
| 次の操作 | 動詞を含む文章または正式な選択肢 | 対象と必要な操作を示す。正式返却と不足解消の根拠内に限る | 独自段順や無許可の実行を導かないか |
| 入力 | 環境標準の質問/選択、または意味が明確なテキスト回答 | 背景・選択肢の差・相談の入口を説明。番号だけで意味を伝えない | キーボードと自然文で同じ選択の意味を伝えられるか |
| 処理中 | 対象付きの未完了の説明 | 架空の進捗率・定期更新・先行した成功表示をしない | 遅延・予算超過で未確認と停止を示せるか |
| エラー・停止 | 原因と必要な判断を近接した文章で示す | 生エラーや色だけにせず、誰の何が必要かを1回伝える | 人待ち中に同じ通知や効果を生産し続けないか |
| 保持した内容 | 設定・回答・履歴・完了範囲の短い要約 | 確認できた保持と未確認を区別 | 中断・競合の後も内容と対象が対応するか |
| 根拠 | 内容が分かるラベルの参照と会話での説明 | 読取り権限のある原本と公開可能な説明を区別。参照だけに判断を委ねない | mdを開かずに必要な判断を説明できるか、秘密を表示しないか |
| 完了 | 対象範囲・実結果・残件を別々の文章にする | 部品の存在、初回の成功、適用済みを全体の完了へ拡張しない | 初回・追加変更・AUNの結果を区別できるか |

## 表示する状態の意味

| 表示分類 | 意味 | 避ける表現 |
|---|---|---|
| Empty | 正常に観測でき、該当する設定・記録・候補が無い | 「読み取れないので未導入です」 |
| Loading | 対象の観測中で、結果がまだ確定していない | 架空の完了率、既に成功したような先行表示 |
| Success | 特定の対象・版・条件について結果を確認した | 「すべて完了」と対象や残件を省く表現 |
| Error | 失敗・拒否・不一致・予算超過で、依存操作を止める | 生のstack traceのみ、観測不能を合格とする表現 |
| Partial | 確認した範囲と不足・未確認が混在する | 一部の確認を全体の成功としてまとめる表現 |

状態名は内部の表示整理に用いる。利用者には具体的な日本語の内容で伝え、AI-DLCの実行状態や承認を置き換えない。初回と追加後でも意味は同じにし、追加で変わるのは選択→現在の再照合→案内更新の実動作である。

## 既存環境への適応と適用外

| 要素 | 扱いと理由 |
|---|---|
| 専用ナビゲーション・ボタン・モーダル・hover | 新しいWeb UIを作らないため専用部品を設けない。利用環境の正式な質問UIがあれば意味を保持して利用する |
| CSS tokens・色・フォント・余白・Web breakpoints | ホストの見た目はShirubeが所有しない。数値やテーマを新規規格として追加しない |
| HTMLの見出し・ARIA属性 | 専用HTMLを生成しないため直接実装は非適用。テキストの情報階層は保持し、読み上げや入力の到達性は実機で別途検証 |
| 狭い表示・長い内容 | 見出しと縦リストを用いる。必要な対象・選択肢が折返しや表示分割で失われないことを確認する |
| Unicode・特殊文字・制御文字 | 日本語・区切り文字を壊さず、表示先の形式へ安全に扱う。不可視文字や制御命令で対象を偽装・実行させない |
| 図・画像・装飾 | 操作の理解に必須にしない。本段では画像生成や専用のHTMLデモを要求しない |
| host固有のキー・入力位置・読み上げ | 未検証。使えることを設定や文書だけから断定しない。利用できなければ不足と代替の条件を説明し、対応済みにしない |

## 環境の差を扱う条件

- 同じ対象・観測入力なら、LLM環境が変わっても判定・理由・権限の意味を再定義しない。表や質問UIを使えない場合にも、文章で同じ判断材料を伝える。
- 長い名前やパスは対象の同一性を保って表示する。必要なら対象名と詳細を分けるが、無言の切捨てや別表記の重複計上をしない。
- 正式な質問UIが使えるか、文字入力で同じ意味を扱えるか、読み順と表示更新を認識できるかは、指定した実証環境で確認する。未実行や観測不能は未検証として残す。
- 新しいLLM・CLIへの対応は個別の観測と試験が必要。初回の成功をW-02の対象外環境へ自動適用しない。
- 既存設定・履歴・規格、4つの確認、独立監査と担当分離を表示の簡略化で省略しない。必要な権限が不足する場合は、見た目の操作可能性より停止条件を優先する。

## 対応と検証への引継ぎ

mockups.mdのV-01〜V-07と17US・88ACの対応表、interaction-spec.mdの7部品を照合する。実装担当は対象版の表示・入力を実物で検証し、品質担当はaccessibility-checklist.mdの期待結果と比較する。新しい担当の起動や規格の採択は、本書だけで行わない。

本書の対応表は利用環境への実装、キー操作、読み上げ、製品試験・CI・実配布の合格を意味しない。全13Must、採択済みの技術・セキュリティ規格と100%の対象分母、AUN・DB側の境界、既存担当・保留・承認、公開の架空データ条件を保持する。
