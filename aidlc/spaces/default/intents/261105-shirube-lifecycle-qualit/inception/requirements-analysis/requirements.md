## Intent Analysis

Shirube を導入すると AI-DLC も利用でき、LLM との対話で必要な設定を揃え、利用者の明示的な開始から正規の開発・確認・実際のゴールまで一貫して進められるようにする。ゴール後も同じリポジトリ、設定、記録、規格と体制で実際の追加開発を完成できることが目的である。Shirube は AI-DLC の順序や承認を置き換えず、不足する接続・証拠収集・検査・停止・配布を補う。根拠: IC、Scope、[Q1]。

利用者は導入・開発を行う社内の担当と Owner。独立監査は既存の devauditor、作者の受領を経た統合は作者以外の suite-lead が担う。AUN では既存担当・取り組み・保留・承認を保持する。担当名の存在だけを、稼働・受領・権限の証拠にしない。根拠: C-06〜C-09、M1。

最初は端から端まで動く最小の流れを通すが、M-01〜M-13 はすべて必須である。初回と追加変更の2つの題材だけで全体を完了にしない。以下の FR / NFR の ID は恒久的な追跡キーとし、後続の設計・単位・試験で再採番しない。各行の正例・負例は「前提を用意→対象操作→記載結果を観測」で試験する。負例の合格とは、問題を検出して安全に拒否・停止し、成功を報告しないことである。

### FR7 — 失敗・人待ち・再開（M-07）

| ID | 必要な振る舞い | 正例の合格条件 | 負例・境界の合格条件 | 出典 |

## Constraints

- 初回の実証は現在の社内体制と Codex CLI・Mac・GitHub・GitHub Actions を使う。製品の入口を Codex 専用にしない。既存製品の Node `>=22` という宣言と、特定の版で実測した対応を区別する。根拠: C-01、Scope W-02、RE。
- AI-DLC の段・単位・正式な設定に従い、Guard Policy strict・Learnings on と適用される Build and Test・CI・Operation を保持する。本書を既存の状態や工程を直接変更する指示にしない。根拠: C-05、P1、M1。
- DB構造・資格情報・workflow・必須検査・保護設定・本番・料金・契約等の保護対象には、該当する公開 Owner 決定と必要な対象 head の承認を確認する。ローカルの写しは権限の正本ではない。P6 の例外は既存キット版上げの全条件に一致する範囲だけで、新規導入・新センサー配布・保護設定の変更へ拡張しない。根拠: C-08、M1、P1・P6。
- PR の監査依頼は作る席が対象 head の CI と必要な証拠を揃えて行い、独立監査結果を作者が受領し、作者以外が統合する。監査中に head が変われば古い依頼・結果をそのまま使わない。既存の受付手順と役割を保持する。根拠: C-09、M1。
- AI-DLC の履歴と承認は元の作業場で保持し、実装担当へ複製して承認を作り直さない。親は管理・品質確認・設計に専念し、成果物の作成は承認されたサブに任せる。配下は最大3体を可変にし、見直し役は同時1体、親と同じモデル、段の見直しのみ。対象・人数・モデル・所有範囲を超える委任はしない。根拠: C-06・C-07、[Q1]要約、M1。
- 公開 Shirube の試験入力・fixture・例・ログ・出力は架空情報だけにする。AUN を含む他 repo の非公開記録・実データ・秘密を持ち込まない。根拠: C-04、Scope M-13。
- DB 固有の規格・検証は別 intent `261105-db-design-security` の範囲と承認を保つ。ベースへ無断移管せず、必要な接続だけを要件・契約で結ぶ。本書は DB の表・migration を新設する設計ではない。DB設計が必要になれば、M1 の固定版正本を執筆前に読んで SHA-256 を照合する。根拠: C-14、Scope「DB側・既存担当との関係」。
- 旧 `261021-dev-speedup-automation` は履歴を保持して archive 済み。有効な残作業は [legacy-work-transfer.md](../../ideation/scope-definition/legacy-work-transfer.md) の対応で引き継ぐ。旧 unit ID・80%の受入・道筋受付・判定4・5・旧承認を新しい要求の合格に流用しない。根拠: Scope、P1。
