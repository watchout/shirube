# Shirube — User Stories の適用判断

## Decision

Execute

## Rationale

今回の対象は、LLM との対話による導入・設定・明示開始、AI-DLC に沿った実開発と実物による完了、継続開発、AUN への実配布である。導入者、Owner、独立監査者、統合担当、AUN の既存担当の行動と受渡しが関わる。内部の開発道具だけの改修、孤立した不具合修正、純粋なリファクタリングではないため、利用者と場面に分けたストーリーが必要である。

各場面の価値と Given/When/Then の合格条件を対応付け、同じ入力でも初回と追加開発後に何が変わるかを明示する。要件段から引き継いだ初回・追加変更の区別は、実装の題材を勝手に変えず、Owner の判断を伴う具体化として扱う。

## Factors Considered

| 観点 | 入力から確認したこと | 本段の価値 |
|---|---|---|
| 製品の種類 | 既存部品を使う brownfield。13分野・47下位FR・10NFRがある | 既存部品の存在と利用者が実際に得る結果を区別する |
| 利用者に見える機能 | 導入、設定の対話、明示開始、確認結果、不足・失敗・次の操作の案内 | 正常・不足・観測不能・人待ちを利用者の場面で検証する |
| 役割と受渡し | 作る席、Owner、独立監査、作者以外の統合、AUN既存担当 | 誰が何を行い、どの証拠を確認するかを分ける |
| 複雑な条件 | 正式なREADY、実装前の設計監査、PR記録、CI再検査、配布設定のずれ | 正例・負例と対象違い・旧証拠等の境界を受入条件へ落とす |
| 継続開発 | 初回完了後に実際の追加要求と新しい実装を通す | 初回の必須案内の再実装を追加変更の達成と混同しない |
| 運用と配布 | AUNの実配布と実PRの正例・負例・drift、既存の担当・保留 | 配布元の準備と受け手での成功を区別する |

## Areas Where Stories Add Value

- 導入・設定・明示開始から、検証と統合を伴う実際の開発結果までの連続した体験。
- 失敗・中断・人待ち・再開で、失わない内容と止める効果の区別。
- 段の見直し・設計監査・PRの記録と承認・CI・配布先の実物との対応。
- 初回完成時と追加変更後の同一入力の対比、および実際に増えた機能の証明。
- 初回・追加変更・AUNの実証それぞれと、全13Mustの完了との対応。

ストーリーは正式な Unit 分割、DAG、PR の順序や実装計画を決めるものではない。全Mustと既存の権限・監査・技術・セキュリティ規格を保持する。サポート担当は今回の正式な対象にいないため、他役割の参加や貢献は記録しない。

## 成果物との対応

- [personas.md](personas.md) は、確認済みの5役割の目標・利用場面・関係を定める。
- [stories.md](stories.md) は、17ストーリーを利用の流れに沿って記述し、正例・負例と初回/追加後の同じ入力の差を受入条件にする。
- [traceability.json](traceability.json) は、47下位FRと10NFRの全57項目を実在するストーリーへ対応付ける。
- [user-stories-questions.md](user-stories-questions.md) の回答と確認済み要約に基づく。要件の範囲・既存の判断を変更せず、具体的な実装・試験・配布を完了済みとはしない。
