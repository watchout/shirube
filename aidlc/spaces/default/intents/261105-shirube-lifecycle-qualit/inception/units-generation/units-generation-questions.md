## 回答済み事項と分割方針

- 製品はLLMとの対話を入口にする。初回の実証はCodex CLI・Mac・GitHub・GitHub Actions。設定は実物から不足と矛盾だけを聞き、設定回答・導入承認・前ゴール完了を開始や他の許可へ流用しない。
- 正式AI-DLCが段・単位・承認・進行を決める。Shirubeは観測、接続、照合、停止、配布を担う。外部原本を新しい所有entityや別の段状態へ複製しない。
- 7論理部品を7個の独立サービスへ配置しない。既存の製品repo、CLI、共有する判定核、固定版のCI実行とkitを使う一つの製品へ、利用価値ごとの増分を加える。ここでは技術stackや新API/コマンドを決めない。
- **現在は7単位案**とする。Owner指定に従い、最初はPR記録を読み、正式READY・設計監査・必要な単位PR記録の3条件を照合し、不成立ならCI門を止める実動作の統合sliceとする。開始/停止/結果照会は別単位へ分ける。論理部品の所有境界や判定核は増やさず、specだけの単位や新サービスの導入を作らない。
- 1単位=1PR。守る4分類に該当する単位は同じPRの設計だけのheadで独立設計監査を通してからCode Generationへ進み、実装headには新しいCI・独立実装監査・作者受領・必要な公開Owner判断・作者以外の統合を必要とする。前単位の統合前に次単位の作る段へ入らない。

## 単位案とkind・配置

IDとdirectoryはこの計画の候補であり、確認後の最終成果物でも同じ識別子を使う。規模は依存接続と扱う失敗条件から見た相対的な設計上の目安で、工数や期限ではない。

| Unit ID | Directory | 実際に届けるもの・境界 | Kind | 配置 | 相対規模 |
|---|---|---|---|---|---|
| U1 | u1-ci-record-admission | 実PRの原本由来記録をCIから読み、正式READY・4分類の設計先行監査・必要な単位PR記録の3条件を照合し、不成立ならCI門を止める。後続対話を使わない | service | shared | L |
| U2 | u2-working-state-dialogue | 対話から実対象/設定/適用規格を読み、不足・矛盾・観測不能と安全な次操作を説明する実機能。門の実行前提にはしない | service | embedded | M |
| U3 | u3-native-operation-control | 現対象の明示開始/正式AI-DLC接続、正当な停止・再開・同一要求・結果照会を実接続し、U1の必要条件を使う | service | shared | L |
| U4 | u4-trusted-ci-verification | U1の対象PR記録へ信頼版traceability/upstream-coverageをCIで実再検査する4項目目。実行元/版/入力/結果と自己弱体化不可、規格の実測を門へ結ぶ | service | shared | L |
| U5 | u5-safe-versioned-distribution | 許可差分だけでShirube/AI-DLCとセンサー設定を導入/再導入し、既存資産保持と受け手実設定drift/復旧を確かめ、初回の実ゴールを統合確認する | service | shared | L |
| U6 | u6-guided-recheck-increment | 初回実ゴール後の新要求として、案内を選ぶ→現対象/前提/必要判断を再照合→案内を切り替える新コードと実動作を追加する | service | embedded | M |
| U7 | u7-aun-rollout-verification | U5の固定版の受け手向け配布物/設定/受入素材を整え、AUNの既存担当と必要判断の下で実適用、実PRの4項目正負/CI停止、実drift/復旧を実証する | packaging | shared | L |

### kindと配置をこの形にする理由

- U1はPR読取/原本照合/CI判定を実行するためservice。sharedは同じ判定核をCI・手元・配布から使う意味であり、外部公開HTTPサービスではない。
- U2/U3/U6も文書や純粋libraryだけではなく、実対象の読取、対話、正規操作、結果照会を動かすためservice。U2/U6のembeddedは既存の対話/CLI入口への組込みである。U3は停止/同一要求の同じ意味を接続と配布へ共有する。
- U4は実検査元と入力を解決し、2センサーの実行結果を門へ結ぶ実行プログラムを含むためservice。U1の判定核と正式センサーの検査意味を複製しない。3項目の最小門と4項目目の実再検査は分ける。
- U5はkitの実適用/照合/復旧を動かすためservice、同じ固定版を利用先へ配るためsharedとする。
- U7はU1〜U5の実行機能を使う受け手向け配布/設定/受入素材を届け、別の業務判定核を作らないためpackaging/shared。kindは安全設計・NFR・試験・CI・独立監査・実受入を省略する根拠にしない。
- library/spec/uiだけの先行単位、standaloneの新常駐サービスは設けない。契約は次のContract Designで全単位間を具体化し、単位内の純粋核やLLM表示を別の無用な単位へ切り出さない。

## 最初のCI門が後続なしで動く条件

U1にCIの実PR読取→認可された原本/発行元/現成果物との照合→3条件の判定→不成立ならCI門停止までを含める。U2の対話やU3の開始接続が完成するのを待たない。既存のsds-gate1〜3/audit-admissionと有効な部品を再利用し、別コピーの判定を作らない。以下の「3条件」は今回の要求の3項目を指し、旧門の判定番号と同一視しない。

1. 人承認段の正式な実READYが現在の作業場/intent/unit/stage/attemptと成果物内容、実発行元へ対応すること。文字列READY、作者自己生成、旧対象、未実施を拒否する。
2. 4分類（DB構造・権限・契約・セキュリティ）の該当根拠と、同じ単位PRの設計だけのheadで独立設計監査が実装より先に成立したこと。設計変更による旧監査の失効や順序不明も扱う。
3. 単位PRに必要な設計/計画/試験/追跡表/正式承認が原本由来で揃うこと。最初の単位のInceptionを含め、audit/と.aidlc-engine/、秘密/非公開記録の掲載を許さない。

U1の正例は、実際の正式AI-DLC生成の対象記録と認可された取得経路、実PR/head、CI実行元を結び、3条件が成立した結果を得ること。各項目を欠落/改変/偽造/別対象/失効/取得不能へ変えた負例は該当条件で止まり、CIの失敗が門へ反映することまで実確認する。適用外は正式な適用根拠を必要とし、不明を適用外へ変えない。PRから検査正本を弱めたり無条件PASSへ変えたりして通す構成にしない。

単なるJSON構文validator、ローカルmock、原本不明の再生成一致、設計文書だけではU1完了にしない。U1に必要な原本と実発行元の契約は未検証のため、次のContract Designで実物試験を先に行ってから方式を決める。成立しなければU1を実装可能/成功と断定せず依存操作を止める。

U4のtraceability/upstream-coverageの信頼版CI再実行は、3条件へ混ぜず4項目目として別単位に保持する。U1で3条件の検査が成立しても、未完成の4項目目や他の必須条件を免除しない。U1の最小sliceはFR8.1/US3.2の初回実ゴールでも全13Must完了でもなく、開始/導入/設定対話/全体受入は後続へ残る。

U1を作る工程自体にも、既存の正式AI-DLC、設計先行監査、TDD/正負試験/100%実分母、適用SEC-T、必要なCI/独立監査/作者受領/別担当統合を適用する。新門が未完成だからという自己免除はしない。

U2の対話は実checkout/版/設定/規格の読取→観測からの不足/不能判定→安全案内を実装する。U1の成功を対話機能の完成へ流用せず、既存status表示だけで済ませない。U2の読取専用の案内はPR門の結果を必須入力にせず実行できるが、正規開始や適用の許可を発行しない。

## 依存DAG案

ここでの `A depends on B` はAの成果がBの成果を必要とするという意味。Owner指定の「最初は門」は実施上の条件として別に保持し、そのためだけの偽のruntime依存を追加しない。経済的な推奨実装順やcritical pathは決めない。

| 単位 | 直接の依存先 | 実際に必要な接続 |
|---|---|---|
| U1 | なし | 実PRと正式原本から3条件をCI判定し、後続なしで不成立を門へ反映する |
| U2 | なし | 読取専用の実状態/設定対話は門や開始機能の成功に依存しない |
| U3 | U1; U2 | U1の原本/必要条件判定とU2の現在対象/明示開始の入口を、正規操作/停止/照会へ接続する |
| U4 | U1 | 原本由来の単位PR記録と同じ門の核へ、4項目目の信頼版2センサー実結果を追加する |
| U5 | U3; U4 | 正規操作/停止/照会と、CI/センサー設定を固定版の安全な適用/再読/復旧へ結ぶ |
| U6 | U5 | U1〜U5の機能と初回実ゴールを保持し、新要求の実追加を行う |
| U7 | U5 | U1〜U5の固定版と4項目の門を受け手AUNへ実適用して検証する |

この7ノード/7辺の案は循環が無い。U1とU2は成果依存の無い根であり、U1へU2の依存を置かない。各根の異なる実読取を、同じEvidenceCollection等の所有境界へ実装する。共通の形式は事前のContract Designで確定し、別コピーの判定を作らない。

現engineの[.codex/tools/aidlc-lib.ts](../../../../../../../.codex/tools/aidlc-lib.ts)のcomputeBatches/parseBoltDagは同一DAG階層を名前順に解決し、[.codex/tools/aidlc-unit.ts](../../../../../../../.codex/tools/aidlc-unit.ts)のopeningStatusFromはbatches[0][0]をskeletonとして扱うことを読み取りで確認した。最終edge blockには上の名前を使うため、最初の階層はu1-ci-record-admission、u2-working-state-dialogueとなり、最初のresolved DAG unitは門のU1になる。これはOwner指定に一致させる識別と解決の確認であり、独立した対話へ偽の技術依存を付けることではない。将来版で解決方法が変わる可能性があるため、正式DAG生成時に実際のresolved first unitがu1-ci-record-admissionであることを再確認し、不一致なら進めず具体差を戻す。この計画でengineを変更しない。

U6とU7の間には、選択案内がAUNの4項目検査の実装前提であるという辺を置かない。両方の受入は全体完了に必要。後から検査/配布内容に影響する版が変われば、受け手の実版と影響範囲を再照合し、旧AUN結果を流用しない。最終実証対象版と再検証条件はDelivery Planning/後続設計へ渡す。

独立性は並列実行の許可ではない。Owner指定のU1先行、unit-major直列checkpoint、1単位1PR、前単位統合後の次Code Generationを保持する。残りの経済的な選択はDelivery Planningへ委ねる。

## 論理部品・entityとの対応

一つの部品を段階的に拡張する単位はあるが、別コピーの部品や共同所有のmutableデータを作らない。entityの所有者は承認済みcomponents.mdのまま。

| 部品と所有データ | 単位ごとの実装範囲 |
|---|---|
| DialogueExperience / ConfigurationDraft・GuidanceSelection | U2で実観測に基づく質問/確認表示/初回の安全案内。U3/U5で正規操作/適用結果を案内へ接続。U6で選択→再照合→切替を実追加。U1のCI判定はこの入口を使わない |
| EvidenceCollection / ObservedSnapshot・PublishedRecordProjection | U1が正式レビュー/承認/監査原本と実PRの観測/公開用記録を実装。U2は異なる実対象/設定/規格の読取を同じ所有境界へ実装。U3〜U5で正規操作/CI/配布の実観測を接続し、U7でAUNへ適用 |
| NativeAIDLCConnection / NativeOperation | U3で正規入口/版/現対象/明示開始と実結果の照会を実装。U1はNativeOperationや開始機能が無くても動く |
| ConformanceGate / ConformanceAssessment | U1が正式READY/設計監査/必要単位PR記録を照合。U2は観測状態の説明に必要な部分を同じ責任へ実装し、U3が正規操作の条件へ接続、U4が4項目目のCI実検査を結ぶ。判定/理由/証拠意味を単位別に複製しない |
| SensorVerification / SensorResult | U4がtraceability/upstream-coverageの信頼版実行元/入力/結果を実装。U1の3条件判定のCI実行と、U4の2センサー再実行を混同しない。U5で設定配布、U7で受け手実CIを検証 |
| KitDistribution / DistributionRevision・DistributionAssessment | U5で固定版の安全な実適用/再導入と実設定drift/復旧を実装し、U7で既存担当/権限/保留の下で受け手向け配布物と実証を届ける |
| SafeOperationControl / OperationAttempt | U1/U2のI/Oも有限予算と安全停止を守る。U3が正規操作の同一要求/照会/競合/再開を実接続し、U5の適用へ同じ意味を使う。読取に不要な冪等キーを強制せず、U1がU3の未実装を成功stubで代用しない |

| U1の外部原本→CI門 | 正式AI-DLC生成原本/実発行元/対象/成果物/試行、原本由来の公開射影、実PR/head、3条件の適用/失効/前後関係、不成立のCI停止 | 実物試験で成立を確認できなければ方式を採択せず依存操作を止める |
| U1/U2→U3 | 同じ原本/必要条件と現在の実対象/設定/有効回答、正規選択肢/明示開始、操作直前の再確認、停止/同一要求/照会 | 別対象へ自動切替せず、未成立の門を通ったとしない |
| U1→U4 | 原本由来のPR記録と同じ照合核へ、信頼版2センサーのchecker/必須集合/severity/path、実行元/対象/head/入力/結果を結ぶ | 手元成功/旧head/PR自己免除で代替せず停止 |
| U3/U4→U5 | 正規接続/停止/照会と信頼版検査/設定、許可差分/監査/受領、途中失敗/競合/復旧/実設定再読 | 半分の適用を有効にせず正常値/履歴を保持 |
| U5→U6 | 初回実ゴールの根拠、その後の新要求受付、現候補/前提/選択後の再観測、未選択回答と前後比較 | 初回未達なら開始せず、実差が無ければ題材の判断を戻す |
| U5→U7 | AUN現対象/担当受領/権限/保留、固定版/差分/確認/戻し方、公開可能な実受入結果と原本参照 | 配布元の準備を受け手成功とせず、人待ちは一度通知して停止 |

### 方式採択より先の実物試験

正式レビュー/承認の原本と実発行元を、内部log公開なしでCIが独立確認する接続は未検証である。後続Contract Designでは、Owner指示に従って**実物で試して観測証拠を得てから方式を決める**。実物試験を実装後の補足へ先送りしない。必要な試験条件は次のとおり。

- 実際に正式AI-DLCが生成した承認/見直しの記録と、認可された原本取得経路/実行元を使う。現在の対象/成果物内容/試行、発行元、取得した原本、PR/head、CI実行の版と結果を対応付ける。
- 内部audit/と.aidlc-engine/のlog、秘密、非公開記録をPRや公開成果物へ載せず、CI側で独立に真正性と対象の対応を確かめられることを正例で観測する。公開Shirube側の実物試験も架空の業務内容だけを使い、正規の実生成記録と合成した記録を区別する。
- 作者による偽造、内容改変、旧対象/旧成果物/旧試行、設計変更等による失効、発行元不明、取得不能を負例として拒否する。失効や不能を過去の成功で補わない。
- 実際のCI実行環境で、必要な認可/読取権限/版適合/公開除外を守った取得と照合が成立するか試す。ローカルmockだけの正例や、任意JSONの再生成一致を方式採択の根拠にしない。mainのidentityCheck:noneでは真正性を証明できない。
- 結果は観測できた証拠と不足を分けて記録する。正例だけでなく各負例が意図した理由で止まる実結果が必要。成立不能なら方式採択/依存操作を止め、影響する要件と具体案を戻す。

この準備では実験、方式選定、資格情報やworkflowの変更を実行しない。追加の信頼元/資格情報/保護workflow/本番等の変更が必要なら、Contract Designで具体的な試験案と必要なOwner判断を示す。今回の修正指示をあらゆる保護対象変更やGitHub投稿の一括許可へ広げない。新しい署名者・台帳・サービス・DB・権限制度を暗黙に追加しない。

U1で人承認段の正式READYが不足すれば停止する。自動初期化に新しい人承認を作らず、未知の役への自動委任や第二の段状態機械を作らない。各単位が届ける実経路の正負結果と、まだ成立していない全体条件を分ける。
