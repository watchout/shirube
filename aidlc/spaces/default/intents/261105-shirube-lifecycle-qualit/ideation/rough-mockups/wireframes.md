# Shirube — LLM との対話による導入・開発のラフ案

## 入力と位置づけ

入力は [intent-statement.md](../intent-capture/intent-statement.md)、[scope-document.md](../scope-definition/scope-document.md)、[intent-backlog.md](../scope-definition/intent-backlog.md)、[rough-mockups-questions.md](rough-mockups-questions.md) の Q1 と今回の確認済みの要約。M-01〜M-13、BL-01〜BL-10 を対象にする。

Shirube の入口は **LLM との対話** である。共通の利用の流れは、特定の LLM・製品・CLI に固定しない。初回の実証には、前段で指定した社内の Codex CLI・Mac・GitHub・GitHub Actions を使う。共通の利用体験を設計することと、各環境で動作を実証済みであることを区別する（Q1、W-02）。

以下は、テキストで表す案内とやり取りの例である。山括弧内は表示項目の説明であり、実行済みの結果や新設済みのコマンドではない。専用の Web 画面を追加せず、利用する LLM 環境の対話表示で扱う案とする。API・保存形式・実装方法は後続の設計で定める。

## 案内の共通構成

利用者が判断するために、対象、観測できた結果、足りないこと、必要な判断、次の操作の順に示す。詳細な証拠は参照先で読めるようにし、同じ説明を毎回繰り返さない。LLM の宣言だけで導入・承認・検査・完了を成功扱いにしない。

| 場面 | 最初に示すこと | 利用者が行うこと | 対応する範囲 |
|---|---|---|---|
| V-01 導入の相談 | 対象、既存の導入状態、必要な追加・変更 | 対象や不足の確認、必要な判断 | M-01・M-02 |
| V-02 設定の対話 | 確認できた設定、不足や食い違い、その理由 | 未決の項目を回答・修正する | M-02 |
| V-03 準備内容の確認 | 対象、設定、適用規格、残っていること | 内容を修正する、または明示的に開始を依頼する | M-02・M-03 |
| V-04 開発中の案内 | 今の対象と段、4つの確かめ、実際の検査・監査の結果、必要な判断 | AI-DLC の問いや承認に答える。足りない条件を確認する | M-04〜M-07・M-09〜M-12 |
| V-05 停止・中断からの再開 | 止まった理由、保持した内容、未確認のこと | 原因を解消する、判断する、再開を依頼する | M-05・M-07 |
| V-06 ゴールと追加変更 | 完了した範囲と証拠、残ること、次の変更で引き継ぐ内容 | 結果を確認し、追加変更の目的を伝える | M-05・M-06・M-08 |
| V-07 AUN への配布と検証 | 配る版と差分、必要な権限、受け手で観測した適用・検証の結果 | 担当者が必要な承認・適用・検証を行い、結果を確認する | M-12・M-13 |

## V-01 導入の相談

```text
利用者: このリポジトリに Shirube を導入したい。

Shirube:
  対象: <観測できたリポジトリ>
  確認できたこと: <既存の AI-DLC・Shirube とその版>
  必要な追加・変更: <既存の内容との差分>
  確認が必要なこと: <読み取れない項目、未決の項目>
  次の操作: <不足への回答、または必要な承認の確認>
```

既に導入済みの内容を先に観測する。読み取れないものを「未導入」と断定しない。変更を適用する前に差分を示し、保護対象に必要な承認を得る。Shirube 自身では、再利用 workflow と既存の承認履歴を保全する。LLM が接続先の状態を観測できない場合は、不明な箇所と確認方法を伝え、観測済みのように話さない。

アクセシビリティ: 「導入の確認」を見出し、対象・確認結果・次の操作を主な本文にする。質問へのテキスト回答をキーボード操作の入口とし、色や図だけで結果を示さない。

## V-02 設定の対話

```text
Shirube:
  確認できた設定: <観測できた値と、その出典>
  不足または食い違い: <設定項目>
  確認する理由: <この項目が導入や開発にどう影響するか>
  質問: <利用者に必要な判断を、既存の選択肢または自然文で示す>

利用者: <回答、または修正したい内容>
```

自動で観測できたことを利用者にもう一度入力させない。判断が必要なことと、単に取得できなかったことを区別する。回答が既存設定や採択済み規格と食い違う場合は、差を示して確認し、黙って上書きしない。入力を修正するときも、それ以外の回答を保持する。

秘密の値は、会話や公開のファイルへ貼らせない。必要な接続については、値を表示せずに確認できた範囲と、不足する権限・設定を案内する。

アクセシビリティ: 設定項目に名前と説明を付け、質問とエラーを同じ項目に結びつける。番号だけでなく、意味のある選択肢や自然文でも回答できるようにする。

## V-03 準備内容の確認と明示的な開始

```text
Shirube:
  対象: <リポジトリと取り組み>
  確認した導入・設定: <実際の結果の要点>
  適用する規格: <採択済み規格と版>
  残っていること: <未完了の項目、なければその旨>
  次の操作: <設定を修正する、または開発の開始を依頼する>

利用者: <この対象で開発を開始する、という明示的な依頼>
```

設定への回答や、導入が終わったというだけで開発を開始しない。開始を依頼されたら AI-DLC の実際の対象と記録に従って進む。すでに進行中の取り組みがある場合は、履歴を確認して扱いを示し、重複して新しい取り組みを作らない。設定の確認を、後の段の承認や保護対象を変更する承認に読み替えない。

アクセシビリティ: 対象・規格・残件を順に読み取れる構成とし、開始と修正を文章で区別する。利用者が明示的に依頼するまで開始しない。

## V-04 開発中の案内

```text
Shirube:
  対象と現在の段: <AI-DLC の実際の記録>
  確認できた結果: <該当する試験・検査・監査の結果>
  残っていること: <未完了・不一致・観測できない項目>
  必要な判断と次の操作: <既存の AI-DLC の問いや承認、修正先>
  詳細: <この結果を裏づける記録への参照>
```

AI-DLC が出す問い・選択肢・承認の意味を変えず、利用者の言語で伝える。Shirube 独自の重複した承認を足さない。機械検査、独立監査、Owner が判断する保護対象の条件を分け、検査の成功だけで他の条件も揃ったように見せない。

4つの確かめは次の順に読めるようにする。これは利用者に見せる情報の順であり、段・単位の実行順を新設するものではない。

| 確かめ | 利用者が最初に読むこと | 詳細で確認できること | 不足・不一致の場合の案内 |
|---|---|---|---|
| 見直し役の確認（M-09） | 今回の成果物について見直しを受けたか | 対象の段・単位・試行・現在の成果物に対応する実際の READY の記録 | 対応する見直しが未確認で、段の承認に進めないことと、確認する対象 |
| 実装前の設計監査（M-10） | 保護対象に触れる設計の監査を受けたか | 同じ PR の設計だけの変更、独立した設計監査、その対象の版。後の実装の監査と区別する | 実装に入れない理由と、先に監査する設計の記録 |
| PR の記録（M-11） | この単位の設計・計画・試験・承認の記録が揃っているか | 単位と記録の対応、承認の対象、最初の単位で必要な Inception の記録。audit/ と .aidlc-engine/ は除く | 足りない記録と置き場所、別単位・古い承認との不一致 |
| CI と設定（M-12） | PR の記録を CI で検査できたか、配布した設定からずれていないか | traceability・upstream-coverage の CI 再実行結果、PR の対象の版、配布元と観測した設定の比較 | 失敗・未実行・観測できずと対象を示し、門を通過させない。設定のずれは差分と直す対象を示す |

例として、利用者には次の程度の短い案内から始め、証拠の識別子や照合の詳細は参照先で示す。

```text
対象: <今回の単位と PR>
見直し役の確認: <現在の成果物について確認できた結果>
実装前の設計監査: <設計だけの変更について確認できた結果>
PR の記録: <必要な記録が揃っているか>
CI と設定: <PR に対する再検査と、設定の比較の結果>
進めない理由: <例: この単位の承認の記録が PR に含まれていない>
次の操作: <対応する承認の記録を確認し、この PR に含めて再検査する>
詳細: <対象と結果を確認できる参照>
```

「READY」という文字、承認の形をしたファイル、手元の設定だけでは確認済みにしない。見直し役が設定されていない段など、適用条件と例外の機械的な扱いは後続の要件・契約で明示し、未定義の条件を合格扱いにしない。自動の初期化に新しい人の承認を足さない。

設計監査を通した後に同じ PR へ実装を追加しても、後の実装の独立監査・作者の受領・別の席による統合・必要な Owner の承認は残る。設計の対象が変わった場合は、以前の監査がその変更も承認したように表示しない。廃止した判定4・5は使わない。

アクセシビリティ: 見出しと本文で対象・結果・次の操作を区別する。進行状況の変化は文字で伝え、色・絵文字・動く表示だけに依存しない。

## V-05 停止・中断からの再開

```text
Shirube:
  止まった理由: <不足、失敗、または人の判断が必要な項目>
  保持している内容: <回答、設定、実際に完了した範囲>
  まだ確認できないこと: <未確認の結果や効果>
  次の操作: <誰が何を確認・修正すれば再開できるか>

利用者: <必要な判断、修正の報告、または再開の依頼>
```

人の判断を待つときは一度知らせて停止し、同じ通知や成果物の生成を続けない。再開時は現在の事実を読み直し、答えた項目と完了した操作をむやみに繰り返さない。外部への操作の結果が不明な場合は、効果を照会して確認する前に再送しない。

アクセシビリティ: 原因と復帰の操作を同じ箇所に文章で示す。入力の誤りは対象項目を特定し、修正できる内容を伝える。生のスタックトレースだけを案内にしない。

## V-06 ゴールと追加変更

```text
Shirube:
  到達したゴール: <実際に完成・確認した範囲>
  証拠: <要件・設計・試験・監査・承認・統合との対応>
  適用した規格: <対象、版、確認した結果>
  残っていること: <このゴールの未完了と、範囲外の項目を区別>
  追加変更へ引き継ぐこと: <設定、規格、必要な記録と体制>

利用者: <次に追加・変更したいこと>
```

未完了がある場合は、そのゴールに到達したと表示しない。初回のゴールだけで追加変更まで完了したとは言わない。次の変更を始める際は、現在の設定・規格の有効性と、前回から変わったことを確認し、必要な段・承認・検証につなぐ。過去の合格を、新しい差分や規格の版での合格に読み替えない。

アクセシビリティ: 完了した範囲、証拠、残件、次の操作を独立した文章で読めるようにする。証拠への参照には、内容が分かる名前を付ける。

## V-07 AUN への配布と検証

```text
Shirube:
  配布先: <観測した AUN の対象>
  配る内容: <Shirube の版、設定、現在との差分>
  必要な判断: <保護対象の承認、既存の保留、担当者の操作>
  準備の結果: <配布する内容と検証方法が揃った範囲>
  適用の結果: <受け手の実際の状態。未適用・未確認も明示>
  検証の結果: <実際の PR で通る例・止まる例と、設定のずれの検出>
  残っていることと次の操作: <誰が何を確認・実施するか>
  証拠: <公開可能な範囲の結果への参照>
```

配布するセンサー設定の版と受け手の実際の内容を比較する。配布元の値を観測結果へ写しただけで「一致」としない。適用済みでも実際の PR の CI と門で検証できていなければ、検証が完了したと表示しない。止まる例が実際に止まったことも確認し、失敗した試験を合格に読み替えない。負例は架空の入力と承認された試験の対象で扱う。

Shirube 側の準備、AUN 側の適用、実際の検証を別々に読めるようにする。AUN の担当・保留・承認を保持し、必要な権限がなければ次の正当な入力を一度案内して停止する。この表示や範囲の採択を、workflow・必須検査・保護設定などの変更許可にしない。AUN 以外への一括配布は含めない（W-01）。

公開の記録には架空の例と公開可能な結果だけを載せる。AUN の非公開の記録や秘密の値を、証拠を揃える目的で公開側へコピーしない。公開可能な証拠の作り方は後続の設計・担当間の引継ぎで具体化し、観測できなかった結果は未確認として残す。

アクセシビリティ: 「AUN への配布」を見出し、準備・適用・検証・残件を本文の小見出しまたは短い文章に分ける。操作は既存の対話でキーボードから回答でき、表の横幅や色だけに依存しない。

## 全場面に共通する表示の分岐

| 状況 | 利用者への表示 | 操作と保持する内容 |
|---|---|---|
| Empty | 未導入、未設定、または該当する記録が無いことを、確認できた範囲で示す | 不足を埋める操作を示す。取得失敗と混同しない |
| Loading | 何を確認しているかを示す | 完了したと先に表示しない。取得できなければ Error または Partial として伝える |
| Success | 実際に確認できた結果と対象を示す | 次に必要な操作だけを案内し、未実施の承認や効果を補わない |
| Error | 原因、対象、修正または確認の操作を示す | 既存の設定・回答・履歴を保ち、失敗を成功に数えない |
| Partial | 確認できた範囲と、未確認・不一致の項目を分けて示す | 全体の成功と表示しない。足りない項目だけを扱う |

これらは表示を整理するための分類であり、AI-DLC の状態や承認を置き換える新しい状態ではない。

## 表示環境と読みやすさ

共通の案内は日本語の文章、見出し、短いリストで表す。狭いテキスト表示でも読めるよう、長い横幅の表や ASCII の位置合わせを操作の必須条件にしない。長い名前やパスがあっても、対象を一意に分かる形で保持する。図や色が使えなくても、質問・結果・次の操作を追えるようにする。

この段では利用する LLM 環境そのものの表示や支援技術への適合を実証していない。キーボードでの回答、読み上げ順、文字だけでの理解は、後続の詳細化と指定環境での検証に含める。
