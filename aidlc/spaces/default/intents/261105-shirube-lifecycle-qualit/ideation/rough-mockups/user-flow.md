# Shirube — LLM との対話を通じた導入から追加開発までの流れ

## 入力と対象

入力は [intent-statement.md](../intent-capture/intent-statement.md)、[scope-document.md](../scope-definition/scope-document.md)、[intent-backlog.md](../scope-definition/intent-backlog.md)、[rough-mockups-questions.md](rough-mockups-questions.md) の回答と要約。各場面の表示は [wireframes.md](wireframes.md) を参照する。

利用者は Shirube を導入して開発する社内の利用者。入口となる **LLM との対話** の流れは共通とし、特定の LLM・製品・CLI に限定しない。初回の実物での検証は、前段で指定した社内環境で行う。以下は設計上の流れであり、製品の実行結果ではない。

## 初回の流れ

```text
利用者が LLM に Shirube の導入を依頼する
  -> 対象と既存の導入・設定・規格を観測する
  -> 必要な追加・変更と、不足や食い違いを示す
  -> 必要な判断・承認を受けて準備を進める
  -> 対象・設定・規格・残件を確認する
  -> 利用者が明示的に開発開始を依頼する
  -> AI-DLC の実際の対象・段・承認に沿って開発する
  -> 各段の承認に対応する見直し役の実際の記録を確認する
  -> 保護対象に触れる単位は、同じ PR の設計だけの変更で独立監査を受ける
  -> 正規の作る段で実装を加え、単位の記録と承認の記録を PR に含める
  -> CI で記録を再検査し、配布したセンサー設定とのずれを確かめる
  -> 必要な Shirube の検査・監査・試験と証拠をつなぐ
  -> 必要な条件が揃った実際の結果で最初のゴールを確認する
```

文章での補足: 既存情報は先に読み、不足だけを対話で揃える。準備の確認と開始を分ける。開始後の段と承認を LLM や Shirube が独自に選ばず、AI-DLC の記録に従う。どの場面でも、失敗や人待ちの分岐があれば、下の回復・停止の流れへ移る。

## 利用者の操作と応答

| 手順 | 利用者の操作・きっかけ | Shirube が確認・案内すること | 次へ進む条件 | 対応 |
|---|---|---|---|---|
| 1 | 導入したい対象を伝える | 対象を確認し、既存の AI-DLC・Shirube・設定・規格を観測する | 対象と観測できた範囲が明確になる | V-01、M-01 |
| 2 | 不足や食い違いに回答する | 導入・設定の差分、判断が必要な理由を示す。観測できた項目は再質問しない | 必要な設定と、該当する導入・変更の承認が揃う | V-01・V-02、M-01・M-02 |
| 3 | 準備内容を確認・修正する | 実際の導入・設定の結果、適用規格、残件を示す | 準備を確認できる。未確認は未確認として残す | V-03、M-02 |
| 4 | 開発開始を明示的に依頼する | AI-DLC の対象と既存の取り組み・記録を確認して、正規の開始または継続につなぐ | 明示的な開始依頼があり、進む条件を満たす | V-03、M-03 |
| 5 | AI-DLC の問い・承認に答える | 実際の段と成果物に必要な判断を案内し、4つの確かめと該当する検査・監査・試験を接続する | その段の条件と必要な承認が揃う。現在の成果物に対応する見直しの記録を確認できる | V-04、M-04・M-06・M-09〜M-12 |
| 6 | 開発結果を確認する | 要件・設計・受入条件・試験・PR の実際の結果と証拠を照合する | 証拠が対象と現在の差分に一致し、必要な条件が揃う | V-04・V-06、M-05・M-06 |
| 7 | 最初のゴールの結果を確認する | 到達した範囲、証拠、規格、残件を示す | 必要な監査・試験・承認・統合を含む実際の結果で確認できる | V-06、M-08、IC-S1・IC-S3 |

具体的な設定項目・ゴール・検証コマンド・unit の分割は後続で定める。この流れは、新しい承認の門や実装順を追加するものではない。

## 開発中の4つの確かめ

以下は AI-DLC の段の中で該当する条件を確認する流れであり、別の開発工程を作らない。

| 確認する場面 | 通る条件 | 通らない場合と次の操作 |
|---|---|---|
| 段を承認する前（M-09） | 対象の段・単位・試行・現在の成果物に対応する見直し役の実際の READY を確認できる | 古い・別対象・未確認の記録では承認へ進めない。対応する見直しを確認する |
| 保護対象に触れる単位を実装する前（M-10） | 同じ PR の設計だけの変更が独立した設計監査を通っている | 先に設計を監査する。実装を加えてから設計監査済みに見せない |
| 単位の PR を検査する時（M-11） | その単位の必要な AI-DLC の記録と承認の記録が含まれる。最初の単位の Inception の記録も含める | 足りない記録と対象を示して補い、再検査する。audit/ と .aidlc-engine/ は PR に含めない |
| PR の CI と配布先の設定を確認する時（M-12） | PR の記録に traceability と upstream-coverage を CI で再実行し、必要な検査が通る。配布した設定との差を観測できる | 失敗・未実行・観測できずでは門を通さない。設定のずれは対象と差分を示し、必要な承認を保って修正・再検証する |

保護対象に触れる単位は「設計の段 → 設計だけの PR の変更 → 独立した設計監査 → 正規の作る段で同じ PR に実装追加 → CI・実装の独立監査・作者の受領・必要な承認 → 別の席による統合」とつなぐ。設計変更や実装追加の後に、以前の対象への合格を現在の変更へ流用しない。次の単位の作る段へ入る条件も既存の AI-DLC と1単位1PRの決まりを保持する。

機械の成功は Owner の承認、独立監査、受領、統合を代替しない。見直し役が設定されていない段などの適用条件は後続の要件・契約で明示し、不明な条件を合格で埋めない。廃止した判定4・5は接続しない。

## 停止・失敗からの回復

| 条件 | 案内 | 再開時に確認すること |
|---|---|---|
| 対象や記録を観測できない | 取得できない対象と不足を示す。未導入・未承認と断定しない | 対象と記録を再取得できたか。別の対象を選んでいないか |
| 必要な設定が足りない、回答が食い違う | 該当する項目と判断が必要な理由を示す | 他の回答を保ったまま、その項目を解消したか |
| 人の判断・承認が必要 | 誰のどの判断が必要かを一度伝えて停止する | 正当な入力・必要な決定が得られたか。待機中に成果物を生成し続けない |
| 試験・検査・監査の条件を満たさない | 失敗した対象と、直す必要があることを示す | 対象の差分に対して修正・再検証され、必要な承認が維持されているか |
| 証拠が欠ける、古い、改変される、別対象を指す | 不足または不一致を示し、ゴールを完了にしない | 現在の対象・規格・差分について正しく観測した証拠があるか |
| 途中で中断する | 保持している設定・回答・完了した範囲を示す | 現在の記録を読み直し、未完了の箇所から再開できるか |
| 外部への操作の結果が不明 | 結果を確認できていないことを示し、盲目的に再送しない | 効果の有無を照会し、二重の効果を起こさず扱えるか |
| 規格や設定が前回から変わった | 変わった項目と、確認が必要な範囲を示す | 必要な承認と、影響を受ける検証が揃ったか。前の合格を流用していないか |
| 見直し・設計監査・承認の記録が現在の対象に結びつかない | どの記録が足りないか、どの変更に対応しないかを示す | 対象の成果物・PR の変更に対する正しい記録を確認できるか |
| CI の検査を実行できない、または手元だけで成功している | PR の CI で未確認であることを示し、門を通さない | 対象の PR の記録に検査が再実行され、必要な結果を観測できるか |
| 配布先のセンサー設定が配布元と異なる | 実際に観測した差分と修正する対象を示す | 必要な承認を保って設定を修正し、再比較・PR の再検査を行えたか |

共通する回復の流れは、「実際の記録を読む → 保持できる内容を保つ → 不足・食い違いを解消する → 必要な承認・検証を受ける → 正しい箇所から再開する」とする。失敗・観測できず・中断を成功に読み替えない（M-05〜M-07）。

## 追加変更の流れ

```text
最初のゴールの実際の結果と証拠を確認する
  -> 利用者が LLM に追加・変更したいことを伝える
  -> 設定・規格・必要な記録と体制を引き継ぎ、変化を観測する
  -> 追加変更の対象とゴールを AI-DLC で定める
  -> 必要な段・承認・検査・監査・試験を通す
  -> 追加差分に対応する実際の結果と証拠で次のゴールを確認する
```

文章での補足: 最初のゴールに続く実際の追加変更を扱う。前のゴールの完了や承認を、新しい変更の完了や承認と扱わない。必要な規格、リポジトリ、記録、体制を維持し、変わった部分は必要な手続きで更新・検証する（M-08、IC-S2・IC-S3）。

## AUN への配布と実際の検証

```text
Shirube 側で配る版・差分・検証方法を準備する
  -> AUN の実際の対象・担当・保留・必要な承認を確認する
  -> 必要な権限がなければ一度知らせて停止する
  -> 権限のある既存の担当が、正規の手順で適用する
  -> 受け手の実際の内容を読み、配布する内容と比較する
  -> AUN の実際の PR の CI と門で通る例・止まる例を検証する
  -> センサー設定のずれを検出できることを検証する
  -> 適用・検証の証拠と残件を確認する
```

文章での補足: 準備が終わったこと、適用したこと、検証を終えたことを分けて伝える（V-07、M-12・M-13、BL-09・BL-10）。宣言した配布内容を、観測した結果として写さない。実際の CI で止まるべき入力が止まらなければ完了にしない。AUN の担当・保留・段の承認・製品差分を保持し、この流れの採択で workflow・必須検査・保護設定などを変更できるとは扱わない。他のリポジトリへの一括配布は含めない。

公開する試験入力は架空のものだけにする。AUN の非公開の記録や秘密を公開側へ複写せず、公開可能な結果と参照の扱いを後続の設計で定める。観測できないものは未確認とし、公開できないことを理由に成功を補わない。

## LLM 環境と機械の確認の関係

利用者が対話する LLM が変わっても、対象、必要な設定、適用規格、明示的な開始、実際の記録と証拠で確認する意味を変えない。LLM が違うことを理由に、判定・理由・権限の条件を別々に作らない。

実際に利用できる読み取り・実行・表示の機能は環境ごとに確認する。利用できない操作は不足として案内し、会話で成功を宣言して埋めない。初回の Codex 環境での実証結果を、ほかの環境の動作保証へ自動的に広げない。

| 価値 | この流れで確認する内容 | 範囲・backlog |
