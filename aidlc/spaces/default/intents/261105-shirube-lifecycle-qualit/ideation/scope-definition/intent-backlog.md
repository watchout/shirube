## 入力と位置づけ

## 最初に届ける価値

最初は BL-01・BL-02 の一部をつなぎ、BL-03 の適用される規格と安全条件を保った、端から端まで通る最小の流れを重視する。これを後続の unit 分割で具体化する。最初の動作確認だけでは、BL-04・BL-05 を含む初版全体の完了を宣言しない。

BL-06〜BL-09 も該当する変更から適用する。Shirube 自身での初回・追加変更と AUN への実配布は両方を必須にし、具体的な実装順・配布順は unit の依存関係と必要な承認に沿って定める。最初の細い流れを優先する方針を維持し、検査部品だけの完成に置き換えない。

既存の配布・指紋照合・判定・試験資産の再利用を先に評価する。ただし、Claude 用の配置を前提とする判定や、現状80%の設定を、そのまま Codex と現行規格への適合証拠に使わない（E-02〜E-05、C-11・C-12）。

## 機能上の関係と確認する依存

- BL-01 の導入・設定・開始と、BL-02 の開発中の確認・完了証拠がつながることで、BL-04 の初回の流れを確認できる。
- BL-05 は、初回のゴールの後に実際の追加変更を行うことで確認する。設定・必要な記録・規格と体制の継続性を含める。
- BL-03 は全体に関わる。適用規格、100%の網羅率、安全の試験、依存追加前の脆弱性確認、最小権限、独立監査を、該当する変更から外さない。
- 対象の選択、段と承認、証拠の読み取り方法は後続の契約・設計で定める。製品固有の独自工程を足して、現行 AI-DLC の進め方と二重にしない。
- DB 側との接続が必要な箇所は、別の取り組みの成果物・版・担当範囲を明示して整合させる。DB 側の範囲承認を、この backlog の実装承認に流用しない。
- BL-06〜BL-08 は、実際の AI-DLC の対象・段・試行、READY、監査と成果物・承認記録の対応が必要。READY の文字やファイルの存在だけを正当な見直し・承認の証拠にしない。具体的な契約と観測方法は後続で定める。
- BL-09 は、PR の設定で弱められない検査の正本・版、実行環境、最小権限、PR の対象記録を必要とする。CI で不合格・実行不能・未実行を成功にしない。
- BL-10 は、配布可能な成果と AUN の既存担当・取り組み・保留・必要な公開決定・exact-head に依存する。今回の範囲採択だけで AUN の workflow や必須検査を変更しない。
- 既存の engine-judge.mjs と approval-record.mjs は適合性を分析する再利用候補。旧 U5・U6 の道筋・判定4・5を復活させず、有効な残作業を新しい要件へ一意に対応付ける。

## 初版に含めない候補

| 項目 | 扱い |
|---|---|
| AUN 以外への実導入・一斉展開 | W-01。AUN への実配布だけ Q4=B で今回に追加 |
| Codex 以外の CLI の動作保証 | W-02。後の拡張で個別に実証 |
| 新しい社内規格そのものの策定・採択 | W-03。必要時は Owner が別途判断。現行規格への適合と検証は BL-03 に含む |

Should Have・Could Have の追加機能は今回指定されていない。優先順位を付けるために、確認済みの Must Have を自動的に次の版へ送らない。

## 実装へ渡す前に具体化すること

要件・受入条件、規格の集合と版・出典・合否、初回と追加変更の具体的なゴール、正式な unit の境界と依存関係、実装計画と試験を具体化する。並行で進める実装は、既存承認の担当範囲で、その unit の実装計画が承認されたものから渡す。

共有規則・workflow・必須検査・保護設定・資格情報などの変更をこの backlog の記載だけで実行せず、該当する承認条件を保つ。記録と承認は元の作業場で保持し、履歴の移送を実装開始の前提にしない。

## 旧取り組みからの引継ぎ

Q2=A の選択に基づき、[legacy-work-transfer.md](legacy-work-transfer.md) の対応表で、U1〜U7 と U1 の残りをすべて扱う。旧 U3 と U1 の承認記録・接続の目的は BL-02・BL-08 の再利用評価へ、旧 U4 の有効な門の接続は BL-06〜BL-09 の新しい要件へ、旧 U6 の有効な配布の目的は BL-10 へ結び付ける。旧 U5 の道筋受付と旧判定4・5は退役として引き継がない。

旧計画の記述だけで実装済み・未実装を断定せず、現在の main と実際の PR を既存実装の分析で照合する。旧取り組みの終了、今回へ移した作業の完成、すでにある成果の再利用を別々に記録し、過去の承認や受入を新しい要件に流用しない。
