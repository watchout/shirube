# Shirube ベース機能 — 初版の開発範囲

## 入力と目的

入力は [intent-statement.md](../intent-capture/intent-statement.md)、[feasibility-assessment.md](../feasibility/feasibility-assessment.md)、[constraint-register.md](../feasibility/constraint-register.md)、および回答・要約確認済みの [scope-definition-questions.md](scope-definition-questions.md) の Q1〜Q4 と追加要求。今回の改めは、4つの設計の確かめを製品の門・CI・配布で守らせ、AUN への実配布を受入に加え、旧取り組みの有効な残作業を移すものとする。前版の成果物と承認履歴は保持し、新しい範囲の承認へ流用しない。

初版の目的は、現在の社内体制で、Shirube 自身の導入から最初のゴールまでを実物で通し、その後の追加変更でも同じ技術・セキュリティ規格、監査、試験を保って次のゴールに到達できる製品にすることである。手順書や部品の存在だけでは完成としない（IC-S1〜IC-S3、Q1）。

共通の入口は LLM との対話であり、Codex 専用にしない。初回の実証環境の指定と、製品の共通の利用の流れを区別する（前段の Rough Mockups の確認済み Q1 と成果物）。

## 対象とする利用環境

最初の実証対象は Shirube 自身。現在の Codex CLI・Mac・GitHub・GitHub Actions と、既存の社内の開発・監査・統合の体制を使う（C-01、Q1）。実際に使う版と必要な権限は後続の要件・設計で特定する。現在の道具の存在を、製品の接続や CI の動作が実証済みだという意味には扱わない。

**Q4 で今回の受入に AUN への実配布を追加した。** AUN の既存担当・取り組み・保留を保ち、必要な公開決定と exact-head の後に適用する。Shirube の側で配布物を作っただけでは完了とせず、AUN の対象 PR でも記録・CI・門と停止条件が働くことを観測する。全社への一斉展開や他製品の自動再開は含めない。

公開リポジトリの試験データは架空のものだけとする。実データ・秘密の値・非公開の記録を fixture・ログ・出力へ入れない（C-04）。

M-09 は人が承認する段を対象とし、自動で済む初期化を人の承認に変えない。見直し役が設定されていない段の扱い、正式な READY と承認記録の形式・対象への結び付け、設計の変更時の再監査条件などは要件・契約・設計で明示する。READY という文字があるだけの自己申告を証拠にせず、AI-DLC の実際の見直し・承認の意味を保つ。M-12 でも PR 側の設定変更で検査を弱められないようにし、検査の正本・版と実行条件を後続で特定する。

## 今回の「維持」と「向上」

**維持**は、採択済みの技術・セキュリティ規格と、既存の監査・試験・権限の条件を、初回と追加変更の双方で適用し続けることとする。

**今回の向上の成果**は、不足している導入・Codex 接続・証拠収集・機械検査を補い、正例と負例および実際の開発で確認できる状態にすることとする。規格の適用を文の指示だけに任せず、該当する検査や機構で確かめる。規格の値そのものを勝手に緩めたり、新しい社内規格を採択したことにしたりしない（Q1、F-01〜F-06）。

要件では、S1〜S9、行網羅率100%、適用される SEC-T、依存追加前の脆弱性確認、保護対象と独立監査の条件について、適用・非適用の理由、版・出典、検証の証拠と合否を特定する。DB に関する設計・実装が生じた場合は、その DB の採択済み規格も適用する。規格の向上を、未採択の規格を追加する一括承認と扱わない（C-03・C-08・C-12・C-13）。

4項目は team.md の文だけで済ませず、門・CI・配布と、欠落・改変・対象違いを含む試験で守らせる。既存の `scripts/sds/engine-judge.mjs` と `scripts/sds/approval-record.mjs` は再利用候補とし、現在の AI-DLC・Codex の配置・承認・見直しの記録に適合するかを分析する。古い判定4・5を呼び戻す形では実現しない。

公開の根拠は [scope-definition-questions.md](scope-definition-questions.md) の追加要求と出典に本文の digest 付きで記録している。見直し役は承認済みの範囲で使い、あらためて一般的な利用承認を求めない。

## 優先する価値と機能の関係

最初は、導入・設定・開始から実際の開発結果までつながる最小の流れを重視する。検査部品だけを先に揃えて、それを製品全体の完成としない。規格、独立監査、保護対象の承認、安全性は、すべての関連する変更に適用する（Q1）。

機能上は、導入と設定が開始を支え、AI-DLC と Shirube の確認が開発中に働き、実際の結果と証拠がゴール到達を裏づける。初回の結果を確認した後、追加変更でも同じ流れを通す。M-06・M-07 は全体に関わる条件であり、最後まで適用を待つ機能ではない。

M-09〜M-12 も該当する変更から横断して適用する。Shirube 自身での初回・追加変更と、AUN の配布先で実際に確かめる結果は区別して記録し、どちらかの証拠だけでもう片方も完成としない。具体的な unit の順序・配布の順序は依存関係と必要な承認を踏まえて後続で定める。

候補となる機能のまとまりは [intent-backlog.md](intent-backlog.md) に記載する。正式な unit の分割・依存関係・順番・実装方法は、後続の AI-DLC の段で定める。この文書だけで実装順を固定しない。

## 旧取り組みの整理

Q2=A により、`261021-dev-speedup-automation` の有効な残作業を今回へ移し、未達・移管の対応を残して旧取り組みを終了する。完成済みの成果と履歴は保持する。全7単位と U1 の残りを [legacy-work-transfer.md](legacy-work-transfer.md) で整理し、旧 U5・U6 の計画をそのまま実行しない。

移管は目的と再利用可能な成果の対応付けであり、古い unit の ID、承認、網羅率80%、退役した工程や旧受入を新しい実装へ持ち込むことではない。旧取り組みを成功・完走済みと読み替えず、正式な終了の状態変更と、今回の残作業の完成を区別する。

## DB 側・既存担当との関係

DB 固有の規格・検証の実装は、既存の `261105-db-design-security` の取り組みで扱う。承認済みの DB 側の範囲を取り消したり、この初版へ無断で移したりしない。ベースに必要な接続と規格の整合は、後続の要件・設計で明示する（Q1、C-14）。

現在の実装担当の承認は、その対象・人数・モデル・範囲で保持する。並行実装は、その担当範囲で、対象 unit の実装計画が承認されたものから行う。作業場所の準備や DB 側の承認だけで、ベース側の実装に着手したことにしない（C-06・C-07、Q1）。

## 初版全体の完了条件

- M-01〜M-13 の要件・設計・実装・試験が対応し、実物の結果で確認されている。
- IC-S1 の初回の流れと、IC-S2 の実際の追加変更の流れの双方が通り、IC-S3 の規格・監査・試験を保った証拠がある。
- F-01〜F-06 の検証が受入条件と試験に対応し、欠落・不一致・観測できず・失敗を成功と扱わない。
- 必要な独立監査、作者の受領、必須検査、保護対象の承認、作者以外の統合の条件が揃っている。
- 段の READY・設計監査・PR の記録と承認・CI のセンサー再検査・設定の配布とずれの検出が、正例・負例で実証され、欠落・失敗・未実行の時に門を通さない。
- AUN に必要な承認の後で実配布し、配布先の対象 PR の実際の結果を確かめた証拠がある。公開の Shirube へ非公開記録を写さない。
- 旧取り組みの各残作業が移管・退役・既存成果の保持に対応付けられ、未達を隠さず旧取り組みの終了が記録されている。

具体的な規格の版・出典、実証する変更内容と合否の詳細は後続の要件・設計・計画で定める。これらは詳細化の作業であり、今回確認した必須範囲や除外範囲を黙って変える理由にはしない。

今回の追加要求は、前段の実現性で未評価だった CI の再実行・配布先の実適用を具体化するもの。F-01〜F-06 の評価だけで追加分の技術的な実現性も実証済みとはしない。既存実装の分析、要件・契約・設計で適合性と依存を確かめ、成立しない条件や範囲を変える必要が出た場合は具体的な差を示して判断を得る。
