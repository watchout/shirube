## Composition and Allocation

固定の3担当を常設しない。親はコードを書かず、設計・作業の分解・進捗と品質・受入を管理する。配下は同時に最大3体とし、ベース、DB、試験、AI-DLC の見直しへの配分を、作業のボリュームと実際の着手条件に合わせて変える。

| 状況 | 配分の例 | 適用する条件 |
|---|---|---|
| ベースに分けられる作業が多い | ベース2体、DB1体 | 対象段と承認に沿い、同じ単位を分ける場合も計画と所有ファイルを明示できる |
| DB に分けられる作業が多い | DB2体、ベース1体 | DB 側の段・設計・計画に沿い、規格と判断を重複定義しない |
| 段の見直しが必要 | 実装・試験を合わせて最大2体、見直し1体 | 見直しは作った担当と分け、公開承認の範囲で同時1体まで |
| 独立した仕事が少ない | 1〜2体 | 人数を満たすための作業や、判断待ちの仕事を作らない |

これらは人数・担当の固定、追加の委任の承認、同時着手の約束ではない。モデルは親と同じモデルを継承し、見直し役の推論設定は AI-DLC の役の設定に従う。既存承認内での配分は親が管理し、同じ承認を使うたびに聞き直さない。目的・人数・モデル・範囲を広げる場合は、その具体的な差の承認を確認する。

## Responsibility Matrix

R は作業を実行する役、A はその結果を取りまとめる責任、C は必要な照会先、I は結果を共有する先。下表は責任の整理であり、公開決定が必要な操作の実行権限を新設しない。

| 作業 | R | A | C | I |
|---|---|---|---|---|
| 要件・設計と unit 間の整合 | 親、段が求める設計の役 | 親 | 該当する AI-DLC の見直し役、DB・AUN の担当 | Owner |
| ベースのコード・試験 | 承認済みのベース実装担当 | 親 | 設計・契約の所有者 | Owner、次に受け取る担当 |
| DB のコード・試験 | DB 側の承認済み実装担当 | 親 | DB の規格と設計の所有者 | Owner、接続するベース担当 |
| 段の見直し | AI-DLC が求める見直し役 | 親が指摘と解消を追跡 | 作った担当 | Owner |
| AUN への適用と対象 PR の実確認 | 既存の AUN 担当 | 親が M-13 の結果を集約 | 配布物を作る担当、必要な判断は Owner | 関係する既存担当 |
| 独立した設計・実装の監査 | devauditor | 作者が指摘対応と受領を取りまとめる | 作った担当、設計の所有者 | Owner、suite-lead |
| 統合 | 作者以外の suite-lead | suite-lead | 作者、必要な判断は Owner | 関係する担当 |
| 段の承認・保護対象の決定 | Owner | Owner | 親が対象と証拠を提示 | 該当する担当 |

親がコードを書かないことと、作者の席として PR の検査・監査依頼・受領を取りまとめることを区別する。配下の見直しは devauditor の独立 PR 監査を代替しない。

## Dispatch and Ownership

担当へ渡す前に、次の内容を揃える。

- 対象の取り組み・unit・段、目的、適用する承認の公開原本 URL と本文の SHA-256。
- 入力の要件・設計・規格と版、必要な受入条件、期待する成果物と検証結果。
- 作業場所、実装する基準 commit、編集してよいファイルと試験の所有範囲。複数担当が同じファイルを編集しないこと。
- 実行してよい操作と、Owner の判断・保護対象の承認が必要な操作。GitHub 投稿や他 repo の変更を含める場合は、その対象と権限を別に確認すること。
- 問題・不一致・観測不能・判断待ちで止める条件と、返す結果の形式。

担当は一人で作業していると考えず、他の担当の変更を戻さない。設計と違う挙動が必要になったら、勝手に実装へ足さず、親に具体的な差を返す。孫への委任は行わない。

記録と承認は元の作業場で保持する。親だけが共通の cursor・state・正式な承認や監査ログを扱い、配下は割り当てられた成果物と試験結果を返す。実装担当の作業場所に履歴を複製して承認を作り直さない。

## Sequence and Readiness

現在は両取り組みとも実装計画の承認前。まず対象段が認める分析・設計入力の整理を行い、正式な要件・unit・契約・計画を具体化する。実装は、その計画と必要な段の承認を得たものから渡す。

1単位1PRを保つ。同じ取り組みで次の単位の作る段へ入るのは、前の単位の PR が監査・受領・必須検査・必要な承認を経て作者以外の席で統合された後。人数を増やすために単位や段の順序を変えない。

守る物に触れる単位は、設計だけの head で独立の設計監査を通し、同じ PR に実装を追加する。その後の実装監査と統合前の必要な Owner の exact-head は維持する。設計の変更により監査対象が変わる場合の再確認条件は、後続の要件・契約・設計で明示する。

## AUN Handoff and Acceptance

Shirube 側から、配布する版、変更と設定の差、必要な承認、検証方法、戻し方を渡す。AUN の既存担当の対象・保留・受領を実際に確認してから、その repo の作業へつなぐ。この席が AUN の現在の余力や着手可能性を推測しない。

受け取る結果は、適用した版・設定、対象の repo・PR・head、4項目と設定のずれの正例・負例、必須検査・監査・受領・必要な承認と統合の確認可能な参照、残った問題。Shirube 側の試験の成功だけで AUN への適用を済ませない。

公開の Shirube の記録には架空データと公開してよい結果だけを載せ、AUN の非公開の設計・監査本文・秘密を写さない。証拠は適切な repo と掲載先で保持し、参照と照合方法を後続の設計で定める。

## Progress and Quality Control

親は成果物・差分・実行結果に基づき、実装前、作成済み、試験済み、監査・承認待ち、統合・受入済みを区別して説明する。これらは説明上の区別であり、AI-DLC に別の状態機構を足すものではない。予定や設定を実行結果に写さず、未実行・skip・timeout・観測不能を成功として数えない。

S1〜S9、TDD、行網羅率100%、適用される安全の試験と依存追加前の脆弱性確認を追跡する。レビューと独立監査の指摘は対象の差分・修正・再検証へ結び付け、適用規格・設計とコードを黙ってずらさない。

監視は作業の節目で結果・不足・次の操作を確認する。新しい常駐 watcher、無制限の試行、判断待ちの成果物生成は行わない。人の判断が必要なら一度知らせて止まり、必要な入力が得られたら現在の事実を読み直す。

## Onboarding Checklist

- 対象 intent・unit・段と所有ファイルが一意であり、同じ作業を重複して渡していない。
- 必要な承認の範囲、入力の設計・規格・版、試験方法、結果の返却先を読める。
- 公開 repo では架空データだけを使い、実データ・秘密・非公開記録を含めない。
- DB の具体的な設計を行う場合は、DB 側の固定版の正本と Codex 用の手引きを読み、digest と適用順を確認する。
- 他の担当の変更を保全し、共通の進行状態と承認を勝手に変更しない。
- 不明・失敗・判断待ちを成功にせず、必要な時点で止めて具体的な不足を返す。
