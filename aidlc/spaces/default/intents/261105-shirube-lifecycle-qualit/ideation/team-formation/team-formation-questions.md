## 既出の回答と未確認事項の扱い

既存の社内体制、役割の分離、承認済みの見直し役、AUN の既存担当の保持、DB 側の別の範囲は前段で確認済みであり、再質問しない。新しい人員・外注・費用はこの段の前提にしない。Owner の追加指示により、この席はコードを書かず設計・進捗・品質の管理と監視に専念し、承認を伴う最大3体のサブエージェントを分担して使う計画へ改める。

AUN 担当の現在の進行状態と余力、個別の unit の担当確定と着手可能な条件は、実際の担当・記録での確認が残る。未確認を「空いている」「受領済み」「実行可能」と記さない。必要な技能は役割ごとに整理するが、役割名だけで技能が実証済みとは評価しない。

この段では、担当の評価（team-assessment.md）、必要な技能と不足の確認（skill-matrix.md）、作業と確認の分担・受渡し・実行の条件（mob-composition.md）にまとめる。正式な unit の分割・依存関係・割当と並行可否は後続の AI-DLC の段で具体化する。

## 追加指示を反映した可変の分担案

| 担当 | 目的・所有範囲 | 着手の条件と境界 |
|---|---|---|
| ベース実装 | Shirube のベース機能、門・CI の接続、配布物と、それらの試験。現在のベース実装担当の承認を有効な範囲で再利用する | 人数を固定しない。対象の AI-DLC の段と承認済みの実装計画に従い、対象ファイルと試験を一意に割り当てる。DB や他の実装担当の所有ファイルを同時に編集しない |
| DB の分析・設計入力・実装 | 別の取り組み 261105-db-design-security の承認済み範囲。規格の照合と後続の設計入力、承認後の DB の検査・試験の実装。初回は PostgreSQL の架空データと使い捨て環境 | 人数を固定しない。5領域と複数 DB・版の扱いを保持する。ベースの範囲に混ぜず、本番 DB・実データへ接続しない。DB の具体的な設計を書く前に固定版の正本を読み、digest を照合する。実装は DB 側の計画承認後 |
| AI-DLC の見直し | 各段で AI-DLC が求める見直しと、要件・設計・規格・試験証拠の照合。見直し結果と指摘を記録する | 常設の枠にせず、該当する段で必要な時に使い、同時に1体まで。作った担当が自分の成果を見直す形にしない。製品コードの編集、GitHub への書き込み、統合、孫への委任はしない。独立 PR 監査の代用にしない |

上限はこの席の配下で同時に3体。役割と人数を固定せず、各作業のボリューム、依存関係、着手可能な承認済み範囲、競合せずに分けられるファイル、必要な見直しに応じて配分する。3体を常に使い切る前提にせず、並行できる仕事が1つなら1体にする。仕事が渡せない担当や人の判断待ちの担当を動かし続けない。モデルはこの席と同じモデルを継承し、別のモデルへの変更をこの案で行わない。見直し役の推論設定は AI-DLC の役の設定に従う。

配分の例は、ベースの独立した作業が多い時はベース2体・DB1体、DB の独立した作業が多い時はDB2体・ベース1体、段の見直しが必要な時は実装・試験を合わせて最大2体と見直し1体。これらは常に同時着手できるという決定ではない。見直しを先に通す必要がある場合は、その対象の実装を先行させない。

同じ取り組みの複数単位の作る段を、人数を増やすために並行させない。1単位1PRと、前の単位の統合後に次の単位の作る段へ入る条件を守る。承認済みの同じ単位の中を複数担当へ分ける場合も、計画に沿った競合しない所有範囲と試験を明示する。役割の配分はこの席が管理するが、AI-DLC の段・単位・進行順や、既存のサブエージェント承認の人数・モデル・範囲を独断で変えない。

この席は、要件・設計、担当への受渡し、実際の差分と実行結果に基づく進捗・品質確認、指摘の対応、必要な Owner の判断の提示を行う。製品コード・試験コードの作成と修正は実装担当へ渡す。コードの実行結果を読み、設計との整合と受入条件を確認することは管理に含める。監視は作業の節目の結果確認として行い、新しい常駐 watcher や無制限の再試行を作ることを意味しない。

両取り組みとも現在は Team Formation であり、承認済みの Code Generation の計画はまだない。今すぐ並行で実装できるとは記さない。AI-DLC が認める範囲の既存実装の分析・設計入力の整理から始め、独立した所有範囲と実装計画が承認されたものを担当へ渡す。親だけがこの作業場の進行状態・承認を正式に記録し、複数の担当が共通の cursor・state・監査ログを書き換えない。

この可変の分担案を無制限な利用許可にしない。既存の承認の対象・目的・人数・モデル・作業範囲内での配分はこの席が管理し、有効な同じ承認を使うたびに求め直さない。その外へ配分や役割を変える場合は、変更する具体的な範囲の承認を確認してから委任する。実際の委任前に適用する公開決定の URL と本文の SHA-256 を確認する。見直し役の既存の公開承認は上記の範囲で再利用し、追加の実装担当へ流用しない。
