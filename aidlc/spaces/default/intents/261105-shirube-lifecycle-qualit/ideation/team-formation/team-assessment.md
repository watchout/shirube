## Assessment

既存の社内体制を使う。親であるこの席は製品コード・試験コードを書かず、要件・設計、担当間の調整、差分・実行結果による進捗と品質の確認、受入結果の取りまとめを担う。実装と試験の作成・修正は、承認された範囲のサブエージェントへ渡す。

配下は同時に最大3体。ベース・DB・見直しを各1体に固定せず、作業量、依存関係、承認済みの着手可能な範囲、競合しないファイル、必要な見直しに応じて配分する。仕事が1つなら1体にする。独立して渡せる仕事がない担当や人の判断待ちの担当を動かし続けない。

これは体制の計画であり、3体を起動済み・実装着手済みという報告ではない。両取り組みとも Team Formation で、承認済みの Code Generation の計画はまだない。人数を確保できることと、AI-DLC の現在の段で実装できることを区別する。

| ベースの実装担当 | M-01〜M-13 のうち割り当てた機能と試験 | ベースの範囲は承認済み。既存担当の承認は元の範囲で保持 | 実際の委任の対象・人数・モデル・範囲を照合し、対象段・計画・所有ファイルを確定する |
| DB の担当 | 別の DB の取り組みの規格・分析・設計入力、承認後の実装と試験 | DB 側の5領域と複数 DB・規格の版の範囲は承認済み | DB 側の段・設計・実装計画に従う。ベースの承認を流用しない |
| AI-DLC の見直し役 | 段で求める見直しの記録と指摘 | 下記の公開承認の範囲で利用可能 | 必要な段で同時1体まで。作った担当とは別にし、対象と出力を明示する |

## Allocation and Capacity

配下のモデルはこの席と同じモデルを継承する。見直し役の推論設定は AI-DLC の役の設定に従う。新しいモデルの採用や全席の設定変更は行わない。

ベースと DB の仕事量を比べ、着手条件を満たす独立した作業だけを配分する。ベース2体とDB1体、DB2体とベース1体、実装・試験を合わせて最大2体と見直し1体などが候補となる。これは実際の稼働の約束や常設の人数ではない。具体的な作業とファイルを割り当てる前に、重複・依存・承認の範囲を確認する。

実際の処理量、各担当の余力や利用率は未計測であり、数字を作らない。配下の人数を増やしても、同じ取り組みの次の単位の作る段は前の単位の PR の統合後に進める。承認済みの同じ単位を複数担当へ分ける場合は、計画に沿った所有範囲と試験を明示する。進行順は AI-DLC の単位と段に従う。

## Existing Work and Dependencies

旧 `261021-dev-speedup-automation` は正式な archive を実行済みで、intents.json の読み取りでも archived を確認した。記録と監査履歴は保持されている。有効な残作業は [legacy-work-transfer.md](../scope-definition/legacy-work-transfer.md) で今回へ対応付け、旧計画の道筋・判定4・5を再開しない。archive を旧取り組みの成功・完走や移管先の完成と扱わない。

DB 側 `261105-db-design-security` は別の取り組みとして維持する。ベースとの接続は、後続の契約・unit の所有範囲で一意にする。同じ作業場の cursor・state・監査ログを複数担当が変更せず、親が正式な進行と承認を記録する。実装担当の作業場所へ承認履歴を複製しない。

AUN への適用は既存担当と分担する。この席から配布版・差分・必要な承認・検証方法・戻し方を渡し、対象 PR の実結果を受け取って M-13 に対応付ける。古い席の map や配布物の作成だけで、担当の受領・適用・成功を確認済みにしない。

## Gaps and Remediation

| 不足・未確認 | 解消する方法 | 解消が必要な場面 |
|---|---|---|
| 正式な unit・所有ファイル・実装計画が未確定 | 要件・設計、Units Generation、Delivery Planning、Code Generation で具体化して承認を受ける | 対象の実装を渡す前 |
| 追加の実装担当に適用する具体的な承認の範囲 | 既存の有効な承認を再利用し、外へ出る具体的な目的・人数・モデル・範囲だけを確認する。公開決定の URL と本文 SHA-256 を照合する | 実際の委任前 |
| AUN 担当の現在の状態と余力、受領 | 現在の担当・対象・保留を読み直し、受渡しと実結果を確認する | AUN の対象作業への割当・適用前 |
| 必要な技能と現在の実装・検証能力 | skill-matrix.md の証拠で確認し、実装や試験で不足が見つかれば修正・追加確認へ戻す | 該当する設計・実装・受入の段 |
| 保護対象の具体的な変更と実行権限 | 対象・head・変更内容を明示し、必要な公開決定・exact-head を確認する | workflow・必須検査・DB の構造・資格情報・配布先設定などの実変更前 |

新しい人員・外注・環境・費用の確保を前提にしない。必要性が判明した場合は、具体的な不足と影響を示して Owner の判断を得る。人待ちでは一度知らせて停止する。
