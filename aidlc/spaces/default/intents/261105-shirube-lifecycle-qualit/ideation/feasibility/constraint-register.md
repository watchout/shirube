# Shirube ベース機能 — 制約の一覧

## 入力と読み方

入力は [intent-statement.md](../intent-capture/intent-statement.md)、回答確認済みの [feasibility-questions.md](feasibility-questions.md)、および [feasibility-assessment.md](feasibility-assessment.md) の観測 E-01〜E-08。製品コードの観測基準は main `7e775afd5b755e51e55e269d8dc35b09d180c33e`。この一覧は制約を記録するもので、実行や設定変更の許可を追加しない。

## 制約

| ID | 分類 | 制約 | 根拠 | 後続で確認すること |
|---|---|---|---|---|
| C-01 | 実証環境 | 最初は現在の社内体制と Codex CLI・Mac・GitHub・GitHub Actions で実証する | Q1 | 実際に使用する版、CI の環境、接続に必要な権限を要件・設計で具体化する |
| C-02 | 完成の範囲 | Shirube 自身で初回と追加変更の2つのゴールを実証する。手順書だけでは完成としない | IC-S1・IC-S2 | 実物の受入条件と証拠を unit と試験に結びつける |
| C-03 | 規格 | 採択済みの技術・セキュリティ規格を維持・向上する | IC-S3、現行の社内規格 | 適用する項目・版・合否条件を特定する。未採択の規格を採択済みと扱わない |
| C-04 | データ | 公開 repo の試験は架空データだけを使う。実データ・秘密の値・非公開記録を入れない | この会話の既出条件、回答確認済みの要約 | fixture・ログ・出力に混入しないことを確認する |
| C-05 | 工程と権限 | 作る物は AI-DLC の unit と段に従う。Guard Policy strict、Learnings on | 現行 AGENTS.md、適用中の team の実践 | 実装計画と必要な段の承認が揃った範囲で作る |
| C-06 | 担当と履歴 | 元の作業場で記録と承認を保持する。実装担当へ履歴を複製して承認を作り直さない | この会話で訂正済みの進め方 | 担当へ必要な成果物を渡し、結果を元の記録へ正式に戻す |
| C-07 | 並行作業 | 既存承認の対象・人数・モデル・範囲を広げない。作業場所だけでは実装開始できない | 現行のサブエージェント承認条件 | 対象 unit の承認済み実装計画と、競合しない所有範囲を確定する |
| C-08 | 保護対象 | DB の構造・資格情報・workflow・必須検査・保護設定・展開・料金・契約変更は、従来の Owner の決定を要する | 現行 AGENTS.md、team の Way of Working | 該当差分を特定し、必要な公開決定と exact-head を統合前に確認する |
| C-09 | 監査と統合 | PR ごとの独立監査、作者の受領、作者以外の統合と必要な検査を維持する | 現行 AGENTS.md、team の Way of Working | 自動判定の成功を Owner 承認や独立監査の代用にしない |
| C-10 | 既存資産 | 既存実装・担当・承認履歴・未統合の変更を保全する。自己導入で再利用 workflow を上書きしない | E-02、元の作業場と main の差 | 実装の基準 commit と変更範囲を計画で明示する |
| C-11 | 接続 | 既存判定部の Claude 配置・Bun・版の前提を、Codex 対応の証拠に流用しない | E-03 | 対象と段を正しく観測できることを確認する |
| C-12 | 試験 | TDD と行網羅率100%を維持する。現状の80%の設定・最低値のまま適合済みにしない | team の Testing Posture、E-05 | 必要な実装・CI の変更を正式に計画し、承認後に検証する |
| C-13 | 安全と依存 | SEC-T と依存追加前の脆弱性確認を維持し、試験・build に不要な資格情報を渡さない | 現行の社内規格 S9、team の Mandated | 実装対象に応じた検査と job ごとの権限を定義する |
| C-14 | DB 側との関係 | DB 固有の規格・検証の取り組みと、ベースの導入・開発の取り組みの担当と承認を混同しない | この会話の並行作業の指定 | 接続が必要な箇所だけを要件・契約で結び、DB 側の範囲承認をベースの実装承認に流用しない |

## 未確定の制約

今回固有の追加環境・追加条件は Q1 で指定されていない。これは社内規格・既存の保留・保護対象の承認条件が無いという意味ではない。

最初の版の除外範囲、規格の向上として今回必須にする内容、実証の具体的なゴールと確認方法は、後続の範囲・要件で確定する。現在の道具の存在を根拠に、追加の有償契約や新しいクラウド環境が必要だとは判断していない。
