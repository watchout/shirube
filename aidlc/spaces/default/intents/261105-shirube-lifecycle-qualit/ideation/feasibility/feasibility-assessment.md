# Shirube ベース機能 — 実現性の評価

## 評価の対象と入力

入力は承認済みの [intent-statement.md](../intent-capture/intent-statement.md) と、[feasibility-questions.md](feasibility-questions.md) の Q1・Consolidated Summary Confirmation。最初は現在の社内体制、Codex CLI、Mac、GitHub、GitHub Actions で実証する。今回固有の追加環境・追加条件は指定されていない。

対象は、Shirube 自身への導入 → 必要な設定の対話 → 明示的な開始 → AI-DLC による開発と必要な Shirube の確認 → 最初のゴール → 同じ規格・監査・試験を保った追加変更のゴール、という製品の流れである。初回だけ、または文書の整備だけで完了とはしない（IC-S1〜IC-S3）。

## 結論

**条件付きで実現可能と評価する。** 社内の開発環境で使える AI-DLC と、再利用候補となる Shirube の部品は存在する。一方、Shirube 自身への安全な導入、Codex での判定との接続、完了証拠の収集、現行規格への適合、初回と追加変更の一貫した動作は、まだ製品として実証されていない。

これは範囲・要件・設計の具体化へ進めるための評価である。実装済み、受入済み、または保護対象の変更を実行してよいという判定ではない。「条件」は下表 F-01〜F-06 の検証であり、既存機能の全面的な作り直しを意味しない。

## 観測した事実

製品コードの参照先は `watchout/shirube` の main `7e775afd5b755e51e55e269d8dc35b09d180c33e`。GitHub API の `repos/watchout/shirube/commits/main` の読み取りと、その commit の Git tree・file 内容を照合した。手元の元の作業場の HEAD は `62ff73db52ce8f29f3b982507b5d2e36578ae60f` であり、この差を無視して製品の現状を判断しない。

| 証拠 | 観測した内容 | 評価上の意味 |
|---|---|---|
| E-01: 上記 commit の `package.json` | JavaScript ESM、Node >=22。既存の試験・構造検査のコマンドがある | 現行の道具を再利用する候補がある。試験の合格は未確認 |
| E-02: `scripts/sds/kit.mjs` の `render`・`apply`・`check`・`status` | 固定 commit からの配布、指紋の照合、既存設定の引継ぎがある。配布内容には Claude 用 skill があり、Shirube 自身の再利用 workflow を対象にした `apply` は拒否する | 既存の配布機能は候補として使えるが、Shirube と AI-DLC の導入全体を実現済みとは言えない |
| E-03: `scripts/sds/engine-judge.mjs` | `.claude` と `aidlc` の配置、`.claude/tools` の読み込み、Bun、AI-DLC 2.11.1 を前提にしている | 現行 Codex 配置で正しい対象と段の判定を取得できることを、別途確かめる必要がある |
| E-04: `scripts/unit-done/` の Git tree と `judge.mjs` | 存在するのは判定の核 `judge.mjs`。抽出・収集・統合入口の file はこの directory にない | 判定部を再利用しても、実際の証拠から完了を確かめる接続は完成したことにならない |
| E-05: `.github/workflows/ci.yml` と `scripts/unit-done/judge.mjs` | CI の行網羅率は80%。判定部の最低値も80%。現在の team の Testing Posture は100% | 現在の社内基準との差がある。80%の成功を100%への適合証拠に使えない |
| E-06: `scripts/sds/gate.mjs` | risk・変更 path・監査受領を確認する機能がある。Owner 承認は機械では確認しない旨も出力する | 既存の独立監査・統合時の承認確認を維持し、機械の成功を実行権限と同一視しない |
| E-07: `tests/` の Git tree | 配布、門、判定部などの試験 file が存在する | 利用できる試験資産の候補である。今回は試験を実行しておらず、合格・網羅率の証明ではない |
| E-08: 実行環境の読み取り | `aidlc --version` は2.11.1、`codex --version` は0.166.0、`node --version` はv26.12.1 | この席で利用できる版の観測。GitHub Actions や他の席での動作保証ではない |

## 実現に必要な条件と検証

| ID | 必要な条件 | 既知の懸念 | 実物で確かめること |
|---|---|---|---|
| F-01 | Shirube 自身に安全に導入できる | E-02 の自己適用拒否は再利用 workflow の破壊を防いでいる | 既存 file・workflow・承認履歴を保ち、設定の対話から開始可能な状態に到達する。再導入や失敗後にも破損・二重適用がない |
| F-02 | Codex と AI-DLC の現在の記録に整合する | E-03 の配置・版・実行条件に依存する | 対象の space・intent・unit・段を正しく読み、別の対象や古い承認で成功にならない。不明な状態は成功にしない |
| F-03 | 完了の判定が実際の証拠につながる | E-04 は判定の核だけである | 設計・要件・受入条件・試験・PR の証拠を照合でき、欠落・改変・不一致の負例を検出する。現行 AI-DLC で不要になった独自工程を復活させない |
| F-04 | 現行の技術・セキュリティ規格に適合する | E-05 の80%と100%の差、適用規格の版・合否条件が未具体化 | 採択済み規格の集合・版・証拠を要件で特定し、100%の行網羅率を含む必要な検査を実行する。規格と実装を黙って乖離させない |
| F-05 | 初回と追加変更の双方で完走する | 部品単位の存在だけでは IC-S1・IC-S2 を満たさない | 社内体制で導入から最初のゴールまで実際に通し、続けて追加変更でも監査・試験・規格を保って次のゴールまで通す |
| F-06 | 失敗時・人待ちでも正しく止まり再開できる | 中断や外部の観測失敗を成功扱いすると一貫性が壊れる | 途中失敗・再実行・人待ちを試し、履歴の破損、二重の効果、承認の省略、非進捗の継続が起きない |

ここでの検証は将来必要な受入の方向を示す。具体的な unit の分割・順番・実装方法・実行コマンドは、後続の AI-DLC の段で定めて承認する。

## 技術・セキュリティ規格との対応

| 規格 | この評価への適用 |
|---|---|
| S1・S6 | 履歴と参照の保全、記録形式を変える場合の互換性・逆向きの確認。DB の構造変更をこの段で決めない |
| S2・S3 | 既存部品の再利用を先に評価し、判定・理由コード・規格の値を複数の場所で別々に定義しない |
| S4・S5 | 判定の核への明示入力、観測した証拠からの再計算、一致・不一致・観測できずの区別 |
| S7・S8 | 再実行時の二重効果を防ぎ、失敗・未実行・観測できずを合格に読み替えない |
| S9 | 読み取り経路は最小権限とし、書ける資格情報を試験・汎用 build に渡さない |
| team の Testing Posture | TDD、Node の `node:test`、行網羅率100%。現在の製品コードとの差 E-05 を追跡する |
| 現行の権限・監査・安全の条件 | Owner が決める保護対象、PR ごとの独立監査と作者の受領、作者以外の統合、SEC-T、依存追加前の脆弱性確認を維持する |
| DB の基準 | DB に関する設計・実装が必要になれば、適用する DB の規格を特定する。別の DB の取り組みの範囲承認を、ベース側の設計・実装承認に流用しない |

規格の出典は、この作業場に適用された `aidlc/spaces/default/memory/team.md` の Way of Working・Testing Posture・Mandated、およびこの席へ提示された現行 AGENTS.md の規則。個別の Owner 決定を引用する場合は、その公開本文を特定する URL と SHA-256 を伴わせる。

## 後続で確定する事項

- 初版から除外する機能と、他リポジトリへの展開を扱う範囲（前段の R-01）。
- 規格の集合・版・証拠・合否条件と、「向上」を今回の必須成果にする項目（前段の R-02）。
- 初回と追加変更で何を実際のゴールとして通すか、その受入条件と検証方法。
- 既存の判定・配布部品をどこまで再利用できるか、現行 AI-DLC の正規の接続で足りる範囲。

## 評価の限界

今回は公開 main のコード・設定・試験 file の存在と、この席の実行環境を読み取った。製品の試験、GitHub Actions の実行、Shirube の自己導入、追加変更の完走は行っていない。外部サービスの新設、資格情報や共有規則・workflow・保護設定の変更も行っていない。これらの未実施を合格に数えない。
