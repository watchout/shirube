## 提案する機能の流れ

1. 対象の指定を受ける。対象（`targetRef`）は呼出側が渡し、席が推測して探さない。
2. 読取り adapter が、対象の実ファイル・版・道具・設定出典を有限の予算で読む。読めた値は `shirube-contracts/1` の Observation（observed / unavailable）の形で出す。読めない・途中で変わった・予算超過は unavailable とし、既定値で埋めない。
3. 観測から設定の下書き（ConfigurationDraft）を組み立てる。各項目の状態は「確認済み・不足・食い違い・観測不能・対象違い・無効」のどれか 1 つ。状態の理由は U1 の理由コードを読むか、U2 固有の項目状態として別に名付ける（理由コードの集合は増やさない）。
4. 質問は「不足」と「食い違い」だけから作る。「観測不能」は質問にせず、確認のしかた（権限・道具・場所）を案内する。
5. 回答はデータとして受ける。型・長さ・path の境界・秘密らしさを検査し、満たさない回答は保持せず、理由を返す。他の回答は失わない。
6. 有効な回答は観測の識別（digest）と結んで保持する。再観測で結びつく観測が変わったら、その回答を無効にして不足に戻す。
7. 結果は E05 の案内文として出す: 結論と対象 → 次の操作 → 原因・未確認 → 証拠参照の順。色や配置に頼らず、同じ観測は LLM の種類が変わっても同じ意味にする。人待ちは 1 回だけ示して止まる。
8. 下書きと選択（draft / selection）を C02 の形で U3 へ渡せる形にする。渡すことは開始の許可にならない。再観測で下書きが変われば、開始の入力は無効になる。

一回の処理は「対象 → 観測 → 下書き → 質問・案内 → 回答の検査・保持 → 再観測での照合」で、失敗時は原因と対象を返して止まる。正式な AI-DLC の段・state を持つ第二の進行機構にはしない。

## 角の確認（corner-checklist）

配置形は「利用者 1 人の Mac 上の対話。外部は GitHub の読取りだけ」と固定する。

- Files and paths: A-04。存在しない path は名指しして続行、権限拒否は path と理由を示して残りを続行、読み途中の file は完全と扱わない（再読する）。
- Formats: pin など JSON の壊れ・未知の項目・重複キーは、読めた分だけ使い、壊れた項目を観測不能として数える。空の入力は「データ無し」と読めなかった場合を区別する。
- Configuration: 出典が食い違う場合は Q1 で決める。第三の道具の欠落・版違い・応答なしは、どの道具かと直し方を示す。初回（何も導入されていない対象）でも動く。
- Storage and state: 保持の寿命は Q2 で決める。保持中の書込みは途中で止まっても半分の有効状態を残さない（NFR4）。
- Concurrency: 同じ対象への二重の対話・古い応答が後から来る場合は、最後の観測の結果だけを使う。
- Time: 観測の時刻は呼出側が渡す。古い観測を新しいものとして示さず、観測時刻を添える。
- Screens: 読込中・空・エラー・部分成功・無効を別の表示にする。二重送信で回答が重複しない。
- AI output: LLM が作る文は命令・権限として扱わない。外から来た文字列は区切って提示し、指示を変えさせない。
- Identity/security: 秘密は A-05。他 repo の非公開本文を転記しない。
