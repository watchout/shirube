# 利用者の物語を作るかの判断（User Stories Assessment）

## 判断

**作る（Execute）。**

## 理由

- この取り組みは開発の道具（Shirube の門・配布・計測）で、段の決まりの「作らない」例（開発の道具）に当たる面がある。
- それでも作るのは、使う人と席が 5 つあり、同じ門と計測に対して、それぞれ違う動き方をするためである。役割ごとの受入の条件を書かないと、完了の条件のうち 2 つが確かめられない。
  - S1-SH-05: 作者の手間は増えない。作者の席から見た受入の条件が要る。
  - S1-SH-07: Owner の手は 1 周 6 回まで。Owner から見た受入の条件が要る。
- 要件（`inception/requirements-analysis/requirements.md`）の FR5 は、監査の席が分類を書く。FR7 は arc が Owner に伺う。どちらも、席どうしの受け渡しで成り立つ。

| 使う人・席 | 門と計測に対する動き | 関係する要件 |
|------------|----------------------|--------------|
| Owner | 切り替えの決定、計測の確認 | FR1、FR7 |
| 作者の席 | 機械向けの block と label を書く | FR2〜FR4、FR6、FR9 |
| 監査の席 | 「誤って止めた」件の分類 | FR5 |
| 統合の席 | 門の結果を見て統合する | FR3 |
| 設計の席（arc） | 切り替えを伺う、決定を記録する | FR5.4、FR7.2 |

## 考えた要素

- 種類: 既存の門の拡張と、計測の新設（brownfield）。画面は無い。
- 使う人: 上の表の 5 つ。
- 複雑さ: 判定の決まり（門の FAIL の分類、切り替えの目安、半分の判定）が多い。
- 部品の状態: 門の判定 3・4・5 と配布キットはすでにあり、計測・分類・橋は無い（`aidlc/spaces/default/codekb/shirube/business-overview.md`・`component-inventory.md`）。
- チームの進め方: 試験が先（`inception/practices-discovery/team-practices.md`）。受入の条件は、そのまま試験の元になる。

## 物語が一番効く所

- 作者の席から見た「書くのは block と label だけ」（FR9）と、止められた時に何が出るか（FR2〜FR4・FR6 の負例）。
- 監査の席の分類の書き方と、それが計測に載るまで（FR5 → FR1.7）。
- Owner が計測を見て切り替えを決めるまで（FR1・FR7）。
