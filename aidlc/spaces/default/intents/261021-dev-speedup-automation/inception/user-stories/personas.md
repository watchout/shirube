# 使う人と席（Personas）

出典: 要件（`inception/requirements-analysis/requirements.md`）、業務の概要（`aidlc/spaces/default/codekb/shirube/business-overview.md`）、チームの進め方（`inception/practices-discovery/team-practices.md`）、物語の作り方の答え（`user-stories-questions.md` の Q1）。

## P1 Owner

- **役割**: 範囲と優先順位の大枠を決める。保護面（必須検査・ruleset・pin・workflow）の決定と、R3・R4 の exact-head の承認をする。AI-DLC の会話を自分で回す。
- **したいこと**:
  - 人を追いかけずに、判断と承認だけに集中する。
  - 開発が速くなったかを、数字で確かめる。
  - 門を止める形に切り替える時期を、材料を見て決める。
- **困っていること**:
  - 判断・承認・手渡しを待つ時間が長い。
  - 設計と実装のずれや、工程の飛ばしによる手戻りが多い。
  - 今の速さが測られていない。
- **道具への慣れ**: GitHub と AI-DLC の会話を使う。script は自分では動かさない。
- **使う頻度**: 計測の報告は 1 日 2 回（04:30・18:00）。決定は 1 周に 6 回まで。

## P2 作者の席（実装の席）

- **役割**: shirube・aun・onza の実装の席。Onza は Onza の席が担う。PR を作り、機械向けの block（`json sds-pr`）を書き、risk の label を 1 つ付ける。R2 以上は監査を依頼する。
- **したいこと**:
  - 書くのは PR の数行と label だけにして、実装に集中する。
  - 止められた時に、何が足りないかがすぐ分かるようにする。
- **困っていること**: 道筋や作業指示を自分で直しに行く手間がある。止められた理由が分からないと、往復が増える。
- **道具への慣れ**: 高い（Claude Code・Codex の席、gh・git）。
- **使う頻度**: PR ごと。

## P3 監査の席（devauditor）

- **役割**: 作者と別の席として、R2 以上の PR を監査し、決まった形（`sds-audit-review/1`）で返却を書く。門が FAIL を出した PR を「門の不備」か「PR の不備」かに分類して書く（新しい役。Owner の決定を記録してから始める）。
- **したいこと**: 決まった形で書くだけで、計測に正しく載るようにする。
- **困っていること**: 分類の形が無いと、同じ判断を毎回文章で書くことになる。
- **道具への慣れ**: 高い（Codex の席）。
- **使う頻度**: 監査の依頼ごと、門の FAIL ごと。

## P4 統合の席（suite-lead）

- **役割**: 作者・監査と別の席として、門の結果と監査の受領と Owner の決定を確かめて統合する。キットの版上げの PR も、決まりのとおり統合する。
- **したいこと**: 門の status を見るだけで、統合してよいかが分かるようにする。
- **困っていること**: 監査なしで統合できてしまう形だと、自分の目だけが頼りになる。
- **道具への慣れ**: 高い（Claude の席）。
- **使う頻度**: PR の統合ごと。

## P5 設計の席（arc）

- **役割**: 設計を書き、道筋と作業指示を出す。Owner の決定を #49 に記録する。門を止める形に切り替える時期が来たら、Owner に伺う。
- **したいこと**:
  - 切り替えを伺ってよい repo を、計測から機械的に知る。
  - Inception を採択していない製品で、道筋が先に進まないようにする。
- **困っていること**: 切り替えの材料を自分で集めて数えると、Owner への伺いが遅れる。
- **道具への慣れ**: 高い（Claude の席）。
- **使う頻度**: 設計・道筋ごと、計測の報告ごと。

## 関係と優先

| 順 | 人・席 | 理由 |
|----|--------|------|
| 1 | P1 Owner | 一番得をする人で、成功の指標の多くが Owner の手と判断に関わる |
| 2 | P2 作者の席 | 門を一番多く通る。作者の手間を増やさないこと（S1-SH-05）が完了の条件に入る |
| 3 | P3 監査の席 | 「誤って止めた回数 0」を数える元の記録を書く |
| 4 | P4 統合の席 | 門の結果を最後に使う |
| 5 | P5 設計の席 | 切り替えの伺いと決定の記録で、Owner の判断をつなぐ |

- P2 が書いた PR を、P3 が監査し、P4 が統合する。3 つは別の席で、作者が自分の作業を監査・承認・統合しない。
- P3 の分類と門の結果から計測が数え、P1 と P5 が読む。P5 が P1 に切り替えを伺い、P1 が決める。
