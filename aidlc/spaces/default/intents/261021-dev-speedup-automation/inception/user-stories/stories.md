# 利用者の物語（User Stories）

出典:
- 要件: `inception/requirements-analysis/requirements.md`（FR1〜FR10・NFR1〜NFR13）
- 人と席: `personas.md`
- 部品の状態: `aidlc/spaces/default/codekb/shirube/component-inventory.md`
- 試験の進め方: `inception/practices-discovery/team-practices.md`
- 作り方: `user-stories-questions.md`（Q1〜Q4）

決まり:
- 3 つのまとまり（計測・門・配布）に分け、その中は仕事の流れの順に並べる。
- 優先度はすべて Must。
- 受入の条件は Given / When / Then で書き、止められる場合（負例）を必ず入れる。試験が先なので、受入の条件がそのまま試験の元になる。

INVEST の見方（全物語に共通）:
- 各物語は 1 つの判定か 1 つの計測を受け持つので、ほかの物語を待たずに試験できる。
- 依存は各物語に書き、依存の先がまだ無い間は、試験の入力（fixture）で代える。

## まとまり 1: 計測

### US1.1 今の値を固定して測る

- **主語**: P1 Owner
- **物語**: Owner として、AI-DLC を入れる前の 30 日の今の値を、PR の番号の一覧つきで一度だけ測りたい。それは、後で「半分になったか」を同じ物差しで比べるためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR1.1・FR1.3・FR1.4・FR1.5・FR1.8、NFR2・NFR9・NFR12

受入の条件:
- **AC1.1.1** Given 2026-09-21〜2026-10-20（日本時間）に統合された shirube・aun・onza の PR、When 今の値を測る、Then 対象の PR の番号の一覧と、時間（PR を開いてから統合まで）の中央値と 90 パーセンタイル、手戻りの回数と PR 1 件あたりの率が出る。
- **AC1.1.2** Given 同じ PR の一覧と同じ時刻の引数、When 2 回測る、Then 出力は同じ bytes になる。
- **AC1.1.3** Given 2026-10-20 23:59（日本時間）に統合された PR と、2026-10-21 00:00 に統合された PR、When 今の値を測る、Then 前の 1 件だけが対象に入る。
- **AC1.1.4** Given 計測が読む API の一覧、When 確かめる、Then 読むのは PR の時刻・label・監査の返却・commit status などの開発の記録だけで、製品のデータは読まない。

### US1.2 4 つの指標を W2 の報告でいつでも見る

- **主語**: P1 Owner
- **物語**: Owner として、4 つの指標を、いつも見ている W2 の報告（iyasaka-arc#53）で見たい。それは、新しい置き場を探さずに速さを確かめるためだ。
- **優先度**: Must
- **依存**: US1.1
- **要件**: FR1.10、NFR1・NFR3・NFR10・NFR11・NFR13

受入の条件:
- **AC1.2.1** Given この Mac の W2 の測定（04:30・18:00）、When 測定が動く、Then #53 の報告に 4 つの指標が並ぶ。各指標には値・対象の PR の件数・期間・最後に測った時刻が付く。
- **AC1.2.2** Given 3 repo のうち 1 つで GitHub が応答しない、When 測定が動く、Then 問い合わせは時間の上限で打ち切られる。読めた repo の値と「aun は観測できず」が載り、合計は「一部」と示される。
- **AC1.2.3** Given 測定が重なって 2 回動く、When 両方が終わる、Then #53 の報告は 1 つに置き換わり、2 つ並ばない。
- **AC1.2.4** Given 計測の script、When 書込みの API を確かめる、Then 書くのは #53 の報告の置き換えだけである。

### US1.3 1 周の Owner の手を URL つきで見る

- **主語**: P1 Owner
- **物語**: Owner として、この 1 周（S1 を作り終えるまで）で自分の手が何回要ったかを、1 件ごとの URL つきで見たい。それは、6 回を超えそうな時に設計の誤りに早く気づくためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR1.6

受入の条件:
- **AC1.3.1** Given この 1 周に属する #49 の決定・exact-head・保護面の設定・指示ボードのカード、When 計測を動かす、Then 回数と、1 件ごとの URL が並ぶ。
- **AC1.3.2** Given AI-DLC の会話での段の承認と要約の確認、When 計測を動かす、Then それは 6 回に数えず、別の回数として並ぶ。
- **AC1.3.3** Given Owner の手が 7 回目になった、When 計測を動かす、Then 「上限 6 回を超えた」と示される。

### US1.4 「半分になったか」を判定する

- **主語**: P1 Owner
- **物語**: Owner として、S1 を終えた後の 30 日の値を今の値と比べ、半分になったかの判定を見たい。それは、取り組みの成果を数字で確かめるためだ。
- **優先度**: Must
- **依存**: US1.1
- **要件**: FR1.1・FR1.2・FR1.3・FR1.5・FR1.9

受入の条件:
- **AC1.4.1** Given S1 の済みの条件を満たした後の 30 日に統合された PR、When 判定する、Then 時間の中央値が今の値の 50% 以下で、手戻りの率も 50% 以下なら「達成」と出る。
- **AC1.4.2** Given 時間の中央値は 50% 以下だが、手戻りの率が 50% を超えている、When 判定する、Then 「未達成」と出て、どちらが足りないかが示される。
- **AC1.4.3** Given 30 日がまだ終わっていない、When 判定する、Then 「判定の前」と出て、達成とも未達成とも出ない。
- **AC1.4.4** Given 意図の記録を指す PR、When 判定する、Then 意図の記録の開始から統合までの時間は別に並ぶが、判定には使われない。

### US1.5 門の FAIL を分類して PR に書く

- **主語**: P3 監査の席
- **物語**: 監査の席として、門が FAIL を出した PR ごとに「門の不備」か「PR の不備」かを決まった形で書きたい。それは、誤って止めた回数を、Owner の手を使わずに数えられるようにするためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR5.1・FR5.2・FR5.4

受入の条件:
- **AC1.5.1** Given 監査の席に分類の役を足す Owner の決定が #49 に記録されている、When 門が FAIL を出した PR に監査の席が分類を書く、Then 機械で読める形の記録が PR に残る。
- **AC1.5.2** Given 分類の役の Owner の決定が #49 にまだ無い、When 分類を始めようとする、Then 始めない（決定の記録が前提）。
- **AC1.5.3** Given 決まった形でない分類の文、When 計測が読む、Then 分類としては数えず、「未分類」のまま残る。

### US1.6 誤って止めた回数と未分類を見る

- **主語**: P1 Owner
- **物語**: Owner として、正しい作業を誤って止めた回数と、まだ分類されていない FAIL の数を見たい。それは、「0」が本当に 0 なのか、まだ数えていないだけなのかを見分けるためだ。
- **優先度**: Must
- **依存**: US1.5
- **要件**: FR1.7・FR5.2・FR5.3

受入の条件:
- **AC1.6.1** Given 「門の不備」と分類された FAIL が 1 件、When 計測を動かす、Then 誤って止めた回数は 1 と出る。
- **AC1.6.2** Given 分類の無い FAIL が 1 件、When 計測を動かす、Then 「未分類 1 件」と出て、誤って止めた回数 0 とは出ない。

### US1.7 切り替えを伺ってよい repo を知る

- **主語**: P5 設計の席
- **物語**: 設計の席として、門を止める形に切り替えてよい repo を計測から知りたい。それは、材料を自分で集めずに Owner に伺うためだ。
- **優先度**: Must
- **依存**: US1.6
- **要件**: FR7.2

受入の条件:
- **AC1.7.1** Given 記録だけの期間に、その repo で実際の PR が 10 件以上門を通り、門の不備が 0、When 計測を動かす、Then その repo に「切り替えを伺える」と出る。
- **AC1.7.2** Given 門の不備が 1 件ある、When 計測を動かす、Then 「切り替えを伺える」とは出ない。
- **AC1.7.3** Given PR が 9 件で、門の不備が 0、When 計測を動かす、Then 「切り替えを伺える」とは出ず、あと 1 件と出る。

## まとまり 2: 門

### US2.1 PR に block と label だけを書いて門を通す

- **主語**: P2 作者の席
- **物語**: 作者の席として、PR に機械向けの block の数行と risk の label 1 つだけを書いて門を通したい。それは、道筋や作業指示を直しに行かずに実装に集中するためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR2.1・FR9.1、NFR10・NFR13

受入の条件:
- **AC2.1.1** Given AI-DLC の記録（intent と段）を指す block と、risk の label 1 つを持つ PR、When 門が動く、Then 作者がほかに何も書かなくても、全部の判定が終わり、結果が出る。
- **AC2.1.2** Given 実際に統合された PR、When diff と作者の席の記録を見る、Then 作者が書いたのは block と label だけで、道筋や作業指示の変更は無い。
- **AC2.1.3** Given 同じ head で門が 2 回動く、When 両方が終わる、Then 結果は同じで、書かれるのは commit status 1 つだけである。

### US2.2 前の段の承認が無い時に、何が足りないかを知る

- **主語**: P2 作者の席
- **物語**: 作者の席として、前の段の承認の記録が無い時に、何が足りないかを門から知りたい。それは、工程を飛ばしたまま進めず、足りない物だけを用意するためだ。
- **優先度**: Must
- **依存**: US2.1
- **要件**: FR2.1・FR2.2、NFR1

受入の条件:
- **AC2.2.1** Given 前の段の承認の記録がある PR、When 門が動く、Then この判定は PASS。
- **AC2.2.2** Given 前の段の承認の記録が無い PR、When 門が動く、Then FAIL で、足りない記録の名前が出る。
- **AC2.2.3** Given 承認の記録が壊れていて読めない PR、When 門が動く、Then FAIL で、PASS にはならない。
- **AC2.2.4** Given S1 の間に作られた `本人確認: なし` の印の承認の記録、When 門が動く、Then 承認として受け入れる。
- **AC2.2.5** Given Shirube が公開する承認の記録とは別の形の「承認」（コメントの文など）、When 門が動く、Then 承認としては読まない。

### US2.3 Inception を採択していない製品で、道筋を置けない

- **主語**: P5 設計の席
- **物語**: 設計の席として、今の段の済みの条件を Owner が採択していない製品では、道筋が受け付けられないようにしたい。それは、Inception を飛ばして作業が始まらないようにするためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR2.3

受入の条件:
- **AC2.3.1** Given 採択の参照の無い道筋、When 計画の受付にかける、Then 受け付けられず、負例の記録が残る。
- **AC2.3.2** Given 採択の参照のある道筋、When 計画の受付にかける、Then 受け付けられる。

### US2.4 監査なしの PR を統合できない

- **主語**: P4 統合の席
- **物語**: 統合の席として、監査の受領の無い R2 以上の PR を、門が止めるようにしたい。それは、自分の目だけを頼りに統合しないためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR3.1・FR3.2、NFR3

受入の条件:
- **AC2.4.1** Given 監査の依頼も返却も無い R2 の PR、When 門が動く、Then FAIL。
- **AC2.4.2** Given 監査が古い head に対するもので、その後に push があった PR、When 門が動く、Then FAIL。
- **AC2.4.3** Given 止める形（Owner が決めた ruleset と必須検査）の repo で、門が FAIL の PR、When 統合しようとする、Then 統合できず、その記録が残る。
- **AC2.4.4** Given 監査の返却を読む GitHub の問い合わせが応答しない、When 門が動く、Then 時間の上限で打ち切られ、「観測できず」になり、PASS にはならない。

### US2.5 道筋に無い作業と、範囲の外の変更で止まる

- **主語**: P2 作者の席
- **物語**: 作者の席として、道筋の Unit を指さない PR や、触ってよい範囲の外を変えた PR が止まり、理由が出てほしい。それは、道筋に無い作業を統合して手戻りを生まないためだ。
- **優先度**: Must
- **依存**: なし
- **要件**: FR4.1

受入の条件:
- **AC2.5.1** Given 道筋の Unit を指さない PR、When 門が動く、Then 判定 4 は FAIL。
- **AC2.5.2** Given 触ってよい範囲の外の path を変えた PR、When 門が動く、Then 判定 4 は FAIL で、外れた path が出る。
- **AC2.5.3** Given 範囲の中だけを変えた PR、When 門が動く、Then 判定 4 は PASS。

### US2.6 設計の置き場の外を変えた時に止まる

- **主語**: P2 作者の席
- **物語**: 作者の席として、承認済みの設計に書いた置き場の外を変えた時に、門が形で止めてほしい。それは、設計と実装のずれを統合の前に見つけるためだ。
- **優先度**: Must
- **依存**: US2.2
- **要件**: FR6.1・FR6.2

受入の条件:
- **AC2.6.1** Given 承認済みの設計を指し、設計に書いた置き場の中だけを変えた PR、When 門が動く、Then この判定は PASS。
- **AC2.6.2** Given 設計に書いていない置き場を変えた PR、When 門が動く、Then FAIL で、外れた path が出る。
- **AC2.6.3** Given 承認されていない設計を指す PR、When 門が動く、Then FAIL。
- **AC2.6.4** Given 設計どおりの振る舞いかという意味のずれ、When 門が動く、Then 門は判定せず、独立監査の項目（実装監査 I7 設計適合）で見る。止める判定に LLM を使わない。

### US2.7 門の切り替えを、repo ごとに自分で決める

- **主語**: P1 Owner
- **物語**: Owner として、門を記録だけから止める形に切り替えることを、repo ごとに自分で決めたい。門には、自分から何かを始めてほしくない。それは、保護面の変更を自分の手に残すためだ。
- **優先度**: Must
- **依存**: US1.7
- **要件**: FR2.4・FR7.1・FR7.3

受入の条件:
- **AC2.7.1** Given 新しく門を入れた repo、When 門が動く、Then 各判定は記録だけで、FAIL でも統合は止まらない。
- **AC2.7.2** Given Owner の決定が無い、When 誰かが pin の mode や必須検査を変える PR を出す、Then 保護面の PR として R4 になり、Owner の exact-head が無いと統合できない。
- **AC2.7.3** Given 承認の記録がそろっている、When 門が動く、Then 門は判定を返すだけで、段や作業を自分から始めない。

### US2.8 Shirube 自身の PR も門を通る

- **主語**: P4 統合の席
- **物語**: 統合の席として、shirube の PR も sds-gate の status を確かめてから統合したい。それは、門を作る repo 自身が門を通らない抜け道を作らないためだ。
- **優先度**: Must
- **依存**: US2.1
- **要件**: FR10.1、NFR4

受入の条件:
- **AC2.8.1** Given shirube の PR、When 統合する、Then その head に sds-gate の status がある。
- **AC2.8.2** Given 門の script そのものを変える shirube の PR、When 門が動く、Then 門は PR の head のコードではなく、固定した shirube の commit から動く。

## まとまり 3: 配布

### US3.1 3 repo に Shirube の版を入れる

- **主語**: P2 作者の席（shirube・aun の実装の席と、Onza の席）
- **物語**: 作者の席として、配布キットで shirube・aun・onza に Shirube の版を入れたい。それは、3 repo で同じ門が効くようにするためだ。
- **優先度**: Must
- **依存**: US2.1
- **要件**: FR8.1

受入の条件:
- **AC3.1.1** Given 配布キットの apply、When 導入の PR を作る、Then 部品と pin が入り、配布先の一覧（`docs/sds/consumers.json`）に repo が 1 行足される。
- **AC3.1.2** Given 最初の導入の PR、When 統合しようとする、Then Owner の exact-head が無いと統合できない。
- **AC3.1.3** Given Onza、When 導入の PR を作る、Then 作るのは Onza の席である。

### US3.2 版上げの PR を決まりどおり統合する

- **主語**: P4 統合の席
- **物語**: 統合の席として、キットの版上げの PR を、監査 PASS の後に毎回 Owner に聞かずに統合したい。それは、版を揃える手間で Owner の手を使わないためだ。
- **優先度**: Must
- **依存**: US3.1
- **要件**: FR8.2

受入の条件:
- **AC3.2.1** Given 差分がキットの file だけで、kit check が OK、上げる先が監査済みの shirube main である版上げの PR、When 監査が PASS、Then 統合の席が作者と別の席として統合する。
- **AC3.2.2** Given 配った file を手で書き換えた repo、When kit check を動かす、Then 一致しないと出る。
- **AC3.2.3** Given 差分に mode・必須検査・profile のどれかの変更を含む版上げの PR、When 統合しようとする、Then Owner の exact-head が無いと統合できない。

## 物語で受け持たない要件

次の要件は、コードの書き方の上限と試験の進め方で、物語の受入の条件にはしない。後の nfr-requirements の段で扱う（`traceability.json` に Deferred と書く）。

- NFR5 実行時の npm 依存を足さない
- NFR6 own-code を 2,300 行以内に収める
- NFR7 PR と関数の大きさの上限
- NFR8 試験が先、行の網羅率 80% を床にし統合の前に CI で確かめる（iyasaka-arc#49 6336689921）
