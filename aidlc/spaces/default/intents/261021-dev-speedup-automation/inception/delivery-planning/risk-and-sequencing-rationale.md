# 順番の理由と危うさ（Risk and Sequencing Rationale）

出典: この段の答え（`delivery-planning-questions.md` の Q1〜Q12）、Unit の依存（`inception/units-generation/unit-of-work-dependency.md`）、要件（`inception/requirements-analysis/requirements.md`）、受け渡しの形（`inception/contract-design/contract-summary.md`）、実現性の評価（`ideation/feasibility/feasibility-assessment.md`）。

Bolt は、作る 1 回分の単位です（1 つの Bolt = 1 つの Unit）。

## 物差し

点数の型（WSJF など。価値・急ぎ・危うさの減り方を足し、大きさで割って並べる型）は使いません（Q2）。7 つの Unit は依存でほぼ順が決まり、点数で並べ替えられる所が少ないためです。順番は、次の 3 つで決めました。
1. 依存の順（`unit-of-work-dependency.md`）。
2. 実現性の条件 C3「門で止め始める前に、今の値を測る」。
3. 完了の条件 S1-SH-01〜07 への効き方。

型の考え方としては、最初に細い版で全体のつながりを確かめる考え（Cockburn の walking skeleton）と、危うさの大きい物を先に置く考え（Cohn の risk-first）を合わせています。

## 順番の理由

| 順 | Bolt | 理由 |
|----|------|------|
| 1 | B1 細い版 | どの Unit も待たない。workflow → commit status → log → 計測のつながりを、機能を足す前に実際の GitHub で確かめる（Q7・Q8）。shirube の保護面（AI-DLC の自己適用・大きさの数えの除外・`.gitignore` の audit の除外・U1 の保護面）と own-code の予算の改めを 1 本の PR にまとめ、exact-head をここで 1 回に済ませる。順番は P1 保護面の 1 本 → R 記録の PR → I1 作り手 → A 承認の記録の PR → I2 kit の自己用の書く先と `budget.mjs` → I3 記録の橋と門の判定 → K kit の版上げ → I4 計測。承認の記録を作る CLI が I1 で初めてできるので、A を I1 の後に置いた（Q10）。門は base の pin の commit から動くので、門の判定（I3）の後に K で pin を上げ、I4 を新しい門で判定される確かめの PR にした（Q11）。実装の PR 3 本・1 本 400 行の中で成り立つ分け方が無かったので（監査の指摘 BF-04）、上限を変えずに実装の PR を 4 本にした（Q12、Units Generation の Q8。Q9 と #49 6354019047 の 4 の順を改めた） |
| 2 | B2 計測 | 門で止め始める前に今の値をそろえる（C3）。主な指標の「半分」の判定と、Owner の手・誤って止めた回数の見張りに要る |
| 3 | B3 承認の記録 | B4 の判定 5 が「設計の記録が承認済みか」を記録の橋に確かめるため、B4 より前に要る |
| 4 | B4 門の判定 | B1・B3 の上に置き場の検査と段階を足す。配る版をそろえる |
| 随時 | B5 Inception が先 | 依存が無く、S1-SH-03 だけに効く。shirube の席の待ち時間に入れる |
| 5 | B6・B7 配布 | B4 でそろった版を配る。S1-SH-01・04 は AUN で確かめるので、B6 が完了の条件に直に効く |

依存の順からの外れはありません。B5 は依存が無いので、どこに入れても依存の順を崩しません。

## 一番の心配と手当て（Q6）

| 心配 | 起きやすさ | 影響 | 手当て |
|------|------------|------|--------|
| 門が正しい PR を止める（誤って止める回数 0 が守れない） | 中 | 高（S1-SH-04） | 全部の判定を記録だけで始める。門の FAIL ごとに監査の席が分類し、門の不備が 0 で実際の PR が 10 件通るまで止める形にしない（FR7.2）。受け渡しの形の未決 C7（置き場の宣言が無い PR）を B4 の設計で決める |
| Owner の手が上限（6 回）を超える | 中 | 中（S1-SH-07） | 保護面の変更を repo ごとに 1 本にまとめ、切り替えも 1 回にまとめ（Q4）、予算の改めも shirube の保護面の 1 本に入れて、予定を 4 回にした（Q10）。計測の専用の資格情報の決定が加わっても 5 回で、6 回に収まる。計測が 1 件ごとの URL つきで数える |
| own-code の予算（残り約 362 行）を超える | 高（U1 だけで約 550〜750 行の見込み） | 中（NFR6） | P1 を出す時に S1 全体の own-code の見積もりを添え、P1 の `hygiene-profile.md` の中で 1 回だけ予算を改める（Q10）。P1 自身の増分は今の予算に収まるので、閾値を同じ PR で緩めない決まりに当たらない |

ほかの心配:
- AI-DLC の版の変化で、記録の橋や承認の記録が壊れる: 版を固定しているので、1 周の間は起きにくい。版を上げる時に audit の形を確かめる（外からの待ち D）。
- 今の値を測る前に止め始める: B2 を B4 より前に置き、切り替えは Bolt の後に行うので防げる。

## 細い版で確かめること

- 細い版（B1）は、PR の block の記録の欄から計測の出力までを、実際の shirube の PR 1 本で通します。
  - 確かめる順: 記録の橋 → 承認の記録 → 門の status と log
  - 試験の入力だけでは、workflow の log・commit status・計測の読取りのつながりを確かめられません（Q7）。
- そのつながりには shirube の門の呼出し（保護面）が要るので、B1 に入れました（Q8）。保護面の exact-head は 1 回のままで、合計の回数は変わりません。
