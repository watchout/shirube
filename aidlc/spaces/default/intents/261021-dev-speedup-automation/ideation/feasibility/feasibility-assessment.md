# 実現性の評価（Feasibility Assessment）: 開発の高効率化・自動化による高速開発化

出典の書き方: `[IC-Qn]` は `ideation/intent-capture/intent-capture-questions.md` の答え、`[FE-Qn]` は `ideation/feasibility/feasibility-questions.md` の答え。推測は「仮説」と明記する。

## 参照した入力

- `ideation/intent-capture/intent-statement.md`（意図の記録: 対象、前提、成功の指標、範囲の目安）
- `ideation/feasibility/feasibility-questions.md`（この段階の答え 10 件と要約の確認）
- 市場調査（Market Research）は、内部向けで外部ツールの選択も決定済みのため実施していない。

## 結論

**条件付きで実現できる。** 次の 4 つの条件を満たす範囲で、最初の版を進められる。

| # | 条件 | 理由 | 出典 |
|---|------|------|------|
| C1 | 最初の版は、いま動いている Suite の製品で始め、OmotenasuAI は再開してから加える | OmotenasuAI の通常の開発は止まっており、速さを測れない | [FE-Q10][FE-Q8] |
| C2 | 最初の版は AUN に頼らない | AUN は常時動いておらず、作り直しの途中である | [FE-Q9][FE-Q4][FE-Q8] |
| C3 | 改善の前に、GitHub の PR の記録から「今の値」を測る | 目標が「今の値の半分」で、今の値がまだ測られていない | [IC-Q10][FE-Q3] |
| C4 | 必須検査・branch 保護・ruleset などに関わる切り替えは、そのつど Owner が決める | 保護面の変更は Owner の決定が要る。最初の版では保護面の自動化はしない | [FE-Q8][IC-Q6] |

## 技術的な実現性

| 対象 | 実現性 | 見立て | 出典 |
|------|--------|--------|------|
| 主な指標: 依頼から統合までの時間 | 高い | GitHub の PR の記録で、PR を開いた時点から統合までは測れる。「依頼（意図の記録）」の時点は、AI-DLC の記録がある repo でしか取れない（仮説: 記録がない repo では PR を開いた時点で代用することになる） | [IC-Q4][FE-Q2][FE-Q3] |
| 主な指標: 差し戻し・手戻りの回数 | 中程度 | 差し戻し（Request changes）と再 push の回数は PR の記録から数えられる。監査の BLOCK はコメントの文面に書かれるため、数えるには書き方がそろっている必要がある（仮説） | [IC-Q4][FE-Q3] |
| 見張り: 1 周あたりの Owner の手の回数（6 回まで） | 中程度 | GitHub 上の Owner の承認や判断の記録は数えられる。chat でのやり取りは GitHub に残らないため、そのままでは数えにくい（仮説） | [IC-Q4][IC-Q9][FE-Q2] |
| 見張り: 正しい作業を誤って止めた回数（0） | 低い〜中程度 | 「正しい作業だった」と後で判定された記録がないと数えられない。止められた作業を人が「誤り」と判定して記録する手順が別に要る（仮説） | [IC-Q4] |
| 最初に解く: 設計と実装のずれ・工程の飛ばしによる手戻り | 中程度 | 前提どおり Shirube の門・配布・測定で扱う。配布キットはすでに report-only で入っているが、止める形にするには Owner の決定が要る | [IC-Q11][IC-Q13][FE-Q4][FE-Q8] |
| 席の LLM の違い（Claude・Codex） | 不確か | 同じ規格を同じように守らせる方法は、まだ確かめられていない。最初の版で確かめる対象になる | [FE-Q4][FE-Q1] |

## リスクの分析

見立ては保守的にしている。詳しくは `raid-log.md` に記録する。

| リスク | 起きやすさ | 影響 | 主な理由 | 出典 |
|--------|------------|------|----------|------|
| 今の値を測る前に改善を始め、「半分になったか」を判定できなくなる | 中 | 高 | 目標が今の値を基準にしている | [IC-Q10][FE-Q3] |
| 門を厳しくして、正しい作業まで止めてしまう | 中 | 高 | 見張りの目標が「誤って止めた回数 0」で、余裕がない | [IC-Q4][FE-Q4] |
| 門の切り替えが Owner の決定待ちになり、Owner の手が 1 周 6 回を超える | 中 | 中 | 保護面の変更は Owner の決定が要る | [IC-Q4][FE-Q8] |
| AUN に頼らないため、席どうしの受け渡しの遅れ（Owner 待ち・中継）は最初の版では減らない | 高 | 中 | 遅れの原因 4 つのうち、最初の版で先に解くのは手戻りだけ | [IC-Q2][IC-Q11][FE-Q9] |
| AI の利用料が想定より増える | 中 | 低〜中 | 増加は許容されているが、上限がまだない | [FE-Q6] |
| 個人情報を含む製品のデータに、検査や記録が触れてしまう | 低 | 高 | 規制上、個人情報を含むデータには触れない | [FE-Q5] |

## Assumptions & Open Questions

- [assumption] AI-DLC の記録がない repo では、「依頼の時点」を PR を開いた時点で代用する。
- [assumption] 監査の BLOCK を数えられるよう、監査の結果の書き方がそろえられる。
- [assumption] 「正しい作業を誤って止めた」ことを判定して記録する手順を、別に用意できる。
- AI の利用料の上限は、まだ決まっていない（後で決める）。 [FE-Q6]
