# P1 — 利用者の体験からゴールを定める手順

対象: 新規製品・改善案件の企画。出力は、判断理由を追える PR/FAQ と P2 に渡すゴール。
PR はここでは **Press Release（発表文）**。GitHub の Pull Request とは別物。
本書は原典を読むための実施手順であり、導入キットではない。

採用主張: **P1 / SRC-M-01（Working Backwards）**。
根拠は [baseline ADR v7][baseline] の「出典の規律」「完成の客観化 1」「P1」、
[既存の出典カード][card] と [その独立確認][review]。
本書の追加した手順への独立確認・製品での実施結果は、それらの過去の確認とは別に記録する。

## 2. 開始時に揃えるもの〔適用案〕

- owner の依頼原文と対象案件。既に決まった制約は出典とともに保持する。
- 利用者の困り事を示す事実、現在の対処方法、未確認事項。既存 repo の仕様・障害記録は参考資料として出典を付ける。
- 文書を書く担当、利用者・運用・実現性を確認する関係者、既存の権限に基づく判断者。
- 案件の Issue または既存文書を一つの作業先として選ぶ。PR/FAQ の所在と版を相互参照し、写しを増やさない。

不明な入力は仮説・未確認と書く。AI が利用者の発言、測定値、判断者の同意を補作しない。

## 3. 実施手順

| 手順 | 担当と行うこと | 残すもの / 原典の節 |
|---|---|---|
| 1 | 作者が対象利用者と重要な困り事を絞り、利用後の体験を描く。〔原典〕 | 誰の何が変わるか。A・B |
| 2 | 作者が発表文を書く。見出し・対象者と便益・提供時期を含む概要・問題・解決と既存手段との差・発言例・使い始め方を揃える。〔原典〕 | PR 初稿。B |
| 3 | 作者が利用者から想定される疑問に、利用者の言葉で答える。〔原典〕 | 外部 FAQ。C |
| 4 | 作者が選択肢、実現上の難所、依存、資源、費用、リスク、成功の前提を検討する。〔原典〕 | 内部 FAQ。C・F |
| 5 | 作者が不明点を調査し、関係者の意見を受けて改稿する。小さな検討から、部門をまたぐ関係者・判断者の検討へ進む。〔原典〕 | 改稿した PR/FAQ。D |
| 6 | 関係者が同じ版を読み、下の問いで議論する。作者が指摘を記録し、PR/FAQ を修正する。〔原典〕 | 問いへの回答と修正版。E |
| 7 | 判断者が進行可否を決める。進める案は資源・概略日程・運用を明らかにする。見送る案は理由に応じて再検討・延期する。〔原典〕 | 判断と次の行動。F |

手順 2 の発言例は「仮想」と明記する。提供時期は計画上の見込みと採択した予定を区別する。〔適用案〕
手順 3・4 は原典 C の具体例を読み、案件に必要な質問を選ぶ。未解決の答えを削って体裁を整えない。〔SDS〕

手順 6 の検討の問い（原典 E の要約）:

1. 利用者は明確か。
2. 問題は明確か。
3. 提案はその問題を解くか。
4. 利用者が利用・購入へ行動を変える理由はあるか。
5. 現在の代替手段より、どの点が改善するか。
6. 対象市場と投資回収は十分か。
7. 事業・資源・技術・法務などの制約は何か。

レビューは提案を改善するために行う。反対意見を消して承認を取り付ける作業にしない。〔原典 E〕
修正が必要なら該当手順に戻る。作者は変更点と未解決事項を同じ文書で追う。〔適用案〕

## 4. SDS の条件と、社内製品への適用

〔SDS: baseline「完成の客観化 1」・P1〕

- 利用者の困り事、期待する変化、成功と負担の指標、範囲、重要 FAQ、未解決事項を残す。
- 1 ページは社内の目安。FAQ や未解決事項を削る理由にしない。
- 指標の値と社内基盤への適用は社内判断。原典が指定した数値として記載しない。

〔適用案: この手順書での具体化〕

- 指標には現状・目標・対象・観測方法・期間を書く。未測定なら未測定とし、確認担当と確認方法を添える。
- 社内基盤では、問い 6 の商用市場評価と、利用者数・削減できる作業や待ち・必要投資の評価を区別する。
  後者を使う場合は社内への読み替えと明記する。市場規模を理由に既存の保護要件を廃止しない（既存カードの適用限界）。
- 原典 D・E の人数・会議時間は原典の進め方として読む。本書では固定人数や定例会を追加せず、
  同じ版を読むこと、問いへの回答、指摘と改稿を追えることを実施形として提案する。
- 人の判断待ちは一度伝えて停止する。沈黙を同意にせず、待機中に改稿や催促を繰り返さない。
  これは既存の待機規則に従う運用であり、Working Backwards 原典由来の規則ではない。

## 5. 終了確認と P2 への受け渡し〔適用案〕

提出前に作者が次を確認し、判断者がその同じ版を検討する。

- [ ] 利用者・問題・期待する体験、PR と両方の FAQ が読み取れる。
- [ ] 成功・負担の指標、対象範囲と範囲外、事実・仮説・未解決事項が区別されている。
- [ ] 上の 7 問の回答があり、未解決なら判断への影響と確認方法が残っている。
- [ ] 採否を判断するための資源・概略日程・制約が記載されている。
- [ ] 判断者の結論・理由・対象版・次の担当と行動を参照できる。

採択された P1 は、[要求シート](../../templates/requirement-sheet.md)の Feature Goal / Target User /
Business・Operational Reason から参照する。指標・範囲外・未解決事項も P2 に引き継ぐ。
P2 で受入条件と証拠を具体化する。P1 の採択を実装・提供・効果発現の完了とは数えない。〔SDS: 完成の客観化 2〜4〕

判断が未回答なら P1 は判断待ち。採択記録が必要な案件は既存の control_source に
URL と本文 SHA-256 で結び、ローカル文書の `accepted` 表記だけを認可にしない（既存の権限規則）。

## 6. 手順の読み合わせ用の正負例〔適用案〕

| 例 | 確認すること |
|---|---|
| 正例: 対象利用者と現在の手作業を示し、目指す体験・両 FAQ・指標の観測方法・制約・判断記録がある | P2 に渡す根拠を辿れる。実測前の指標は未測定のまま保持する |
| 負例: 「コードを短くした」「CI が緑」だけを製品ゴールにする | 利用者の変化と負担が不明。手順 1 に戻る |
| 負例: 1 ページに収めるために FAQ の難所を削る / 架空の発言を実績にする | 手順 2〜4 で未解決・仮想の区別を復元する |
| 負例: 文書を作っただけ、判断への返事がないだけで着手可とする | 手順 7 の判断が未了。待機を報告し停止する |

本書の読み合わせ・原典照合と、実案件でこの手順を使えた証拠は別に記録する。
