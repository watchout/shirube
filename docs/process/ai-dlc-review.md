# 原典差し替え・手順書の読み合わせと監査

対象: [根拠](../sds/lifecycle-basis.md)・[実施手順](ai-dlc.md)・[原典lock](../sds/source-lock.json)と同じPRの入口/雛形、対応するarc差分。
作者: codex-adf。独立監査は作者以外の既存監査席へ依頼する。下表は監査の入力であり判定ではない。

## 独立監査の確認項目

| ID | 読み合わせること | 拒否すべき反例 |
|---|---|---|
| LC-01 | 原典ID/版/bytes/digest/確認節→主張→手順が追える。原典と適用差分を区別 | 未取得/別版を同じhashとして扱う。章の引用だけで原典全体を採用済みにする |
| LC-02 | AI-DLC主軸、G1〜G5の比較と補完、重複工程なし | AI-DLCにCI/反復確認が無いと偽る。OpenUP/XPを第二ライフサイクルにする。CIの頻度達成のため監査を省く |
| LC-03 | 目的→境界/所有→単位/依存→契約→実装→統合/受入がつながる | 小さいPRを積んだだけで全体を完成とする。schema/名前だけで連携PASS |
| LC-04 | 追加/破壊変更/不具合/軽微修正の入口と再確認が具体的 | 毎回全設計を作り直す。旧利用元や影響する親を確認対象から外す |
| LC-05 | 既存64ID・F01〜F10・保護認可・独立性・実環境/復旧・証拠の真正性を保持 | 原典実装のguard offや作者レビューで保護操作を許可。未実施をPASS |
| LC-06 | 意味の確定が対話で行われ、原文/仮説/採択を区別 | AIが利用者、指標、予定、同意を作り、沈黙を承認にする |
| LC-07 | 入口と雛形が同じ版を参照し、別repoのIssueからも到達 | 相対リンク転記で参照が切れる。旧PR#18の入口が新方式を上書きする |

## 作者による手順の読み合わせ例（製品での実行証拠ではない）

| 例 | この手順で選ぶ経路と出口 |
|---|---|
| 新規製品を小さく始める | §1→2で利用者と目的を対話。§3〜5で主要接続を決め、§6/7で最初の実動作を示す。§8の実環境/効果未確認は未完 |
| 既存検索APIに任意の絞込を追加 | §1で対象版/利用元を確認、§2で追加要求、§5で未指定時の既存動作と新条件を合意。§6/7で新旧利用側・既存検索を検証 |
| 既存APIの必須field名を変更 | 破壊変更として§5へ。全利用元/版、移行・旧版同居・廃止・復旧の確認前に旧fieldを消さない |
| 既存契約内の計算不具合 | §1で契約と再現を確認→§6で回帰試験と修正→§7で統合。目的不変ならPR/FAQの再作成は不要 |
| 文書の誤字 | §1で非挙動・非保護を確認→同PRの理由/範囲/既存参照と適切な確認。新設計・新ADR・一律のLLM監査を足さない |
| 各単位は緑だが利用側が失敗 | §7では未達。§9で契約/実装の原因を確かめ、新版で提供/利用側を再検証。子PASSで親を閉じない |
| branchは緑、共有mainの更新版は赤/未実行 | §7では統合未完。更新mainの検証・修正/認可済み復帰を優先。待ちによる日次未達も達成と表示しない |
| 実装で重複/結合の問題を発見 | §9→3/5/6で設計とコードを小さく改善。自動回帰と統合がない状態を進化的設計の成立としない |
| 外部DB用adapterを追加、mockだけ緑 | §5の同一契約・権限/失敗条件を確認し、§7で試験データを持つ実DBとの統合、§8で必要な実環境受入まで未完を残す |
| 原典の80%/件数だけ満たす | LC-05で拒否。採択要件・重要不変条件・必要な検証種別を満たす根拠へ戻す |
| 同意が未回答、実環境が未用意 | 前者は一度通知して停止。後者は未実施と担当/解消条件を残す。どちらも完了へ換算しない |

これらは作者による適用確認。独立監査は原典と差分を読み、必要なら別の反例を加える。
返却: 対象head、LC項目別の根拠、重大な不一致/未確認、判定、次担当。既存監査規格の共通判定を使う。
監査PASSは採択・merge・配布・Shirube製品の完成を意味しない。手順の実地適用は独立監査と採択後の別証拠で確かめる。
