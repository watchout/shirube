# AI-DLCを基盤に、小さく作ってつなぐ実施手順

状態: 独立監査・採択前の候補。[原典と適用差分](../sds/lifecycle-basis.md)がこの手順の根拠。
目的: 全体の利用者価値を保ち、小さな実動作を確認しながら追加・連携・変更できる製品を作る。
以下の番号と記録形式はSDSの適用案。原典の章番号や、全変更への一律な工程義務ではない。

## 1. 入力・担当・今回通る範囲を確認する

担当: 既存の案件リード/作者。利用者・設計担当・実装担当・独立監査・受入担当・merge担当を実名/席IDで示す。同一人の兼務は既存の独立性条件を超えない。
入力: owner依頼原文、control_source_ref、対象repo/HEAD、採択要件/設計/契約、現在の動作、既存の試験・運用、リスク/保護対象。
既存製品では実コードとモデルの一致・解析した範囲/版を確認する（AI-05）。一致と鮮度を示せるものは再利用し、不明点をAIが補作しない。
新規/追加/修正を分類し、§9で開始箇所を選ぶ。通る節、再利用する証拠、適用外の理由、確認する人を同じIssueに書く。
出力: この変更の目的・範囲・既存版・実施順・担当・確認方法。保護認可が不足する操作は実行対象へ含めない。

## 2. 目的と要求を対話で固める（P1/P2）

担当: 利用者/判断者と作者。入力: §1の依頼と観測した困り事。原典: AI-00,12。
1. 既に合意した内容を根拠つきで示し、不足する意味を一項目ずつ確認する。最初の利用者、困り事、利用後の体験をAIだけで確定しない。
2. 期待する成果、成功/負担指標、scope/non-goals、制約、代替案、実現上の難所、重要FAQ/未解決を整理する。数字が無ければ未測定とし、担当・測り方・期間を決める。
3. 合意した体験を機能/非機能要件と具体例へ落とす。採択済みIDを保ち、新要件だけIDを追加する。既存のEARS/Given-When-Then記法を使える。
4. 作者が同じ版で要約し、利用者/判断者が確認する。未決が後工程の判断に影響するなら解消までそこを止める。独立に進められる範囲を明示する。
出力: 合意内容と版/根拠、受入条件、対象/範囲外、仮説・未決の担当。PR/FAQを使う場合も同じ合意を参照し、二重採択にしない。
終了: 利用者/判断者が目的と要求を確認し、必要な判断の出所が辿れる。初稿・返答待ち・仮の予定を採択として扱わない。

## 3. 全体の責任とデータの境界を定める（P3）

担当: 設計担当と判断者。入力: §2の要求、既存構造。原典: AI-01 + XP-01/HA-01。
各部品が担う業務、所有するデータ、呼ぶ相手/呼ばれる相手、外部依存を図と一覧で示す。
分ける理由を責任・変更頻度・データ所有から説明する。データの更新責任は一意にする。異なるモデル間の変換責任も指定する。
業務上の部品と、配布単位・開発作業・PRを区別する。別サービス化を前提にせず、一つのアプリ内のモジュール構成も選べる。
初期の大まかな構造と変更しにくい判断を先に検討し、実装から学んだら§9で更新する。UI/DB/外部サービスが内部処理の試験・変更を妨げる境界にはPorts & Adaptersを使い、内部の契約と外部技術への変換を分ける。根拠のない汎用層は作らない。
出力: 既存設計の境界/依存の差分、要求への対応、必要な新ADR。既存判断を変更するなら先に理由と後継を記録する。
終了: 必要な要求に担当部品があり、責任の重複・未所有・説明できない依存を解消している。

## 4. 開発単位と小さな反復を決める（P2/P3/P4）

担当: リード・設計/実装担当と価値を判断する人。入力: §2/3。原典: AI-02,04。
Unitは範囲と責任がまとまった開発単位、Boltはその実装・検証を進める短い反復。PRは提出物の容器であり、これらと同一ではない。
単位ごとに要求ID、実装範囲、依存、接続箇所、担当、受入、配布形態を示す。単位をまたぐ要求は全担当へ結び、親自身の受入も残す。
依存で可能な順序を確かめ、その中で利用者価値とリスクから順番を決める。循環する開発依存は契約先行等で解き、無理な分割は戻す。
最初の反復は、主要な接続を通る小さな実動作を確認する範囲を選ぶ。設計書だけ・単独の層だけを動作成立と呼ばない。
出力: 反復ごとの範囲・完了条件・実行できる確認・期待する実演・依存・次の担当。将来の全機能の詳細実装を先に埋めない。
終了: 次の反復が既存版に接続でき、動作をどう観測するかが決まっている。観測手段が無ければその構築を同じ反復に含める。

## 5. 接続契約を先に合わせる（P3/T2/T3）

担当: 接続の提供側・利用側の設計担当。入力: §3/4の全接続境界。原典: AI-03。保護・tenant・冪等の具体条件は既存SDS。
既存契約は再利用し、新設/変更する境界だけ次を同じ正本へ記録する。

| 項目 | 記録して確認する内容 |
|---|---|
| 責任 | 提供側、利用側、契約の所有者、データの更新責任 |
| 入出力 | 型・必須/任意・意味・単位・既定値。API、関数、イベント等の接続方法 |
| 振る舞い | 正常/空/不正入力/権限拒否、状態遷移、timeout、再試行、重複・順序・部分失敗の扱い |
| 信頼境界 | 認証/認可、tenant、秘密/個人データ、外部送信先、操作の副作用 |
| 変更 | 契約版、対応する提供/利用版、追加と破壊変更の基準、同居・移行・旧版廃止・復旧条件 |
| 検証 | 提供側の適合と利用側の期待を確認する試験、両者をつなぐシナリオ、担当と証拠 |

出力: 版付き契約と提供/利用側の確認。HTTPならOpenAPI等、メッセージなら対応schema、内部呼出しなら型/振る舞いの契約を使う。
終了: 各接続の合意・検証方法が揃う。schemaがあるだけ、provider単体が緑だけでは連携の受入にしない。
未解決の契約に依存する実装は止める。mockで進めた範囲は明示し、実接続の証拠へ置換するまで受入未完とする。
Ports & Adaptersを使う境界は、試験用/実用adapterが同じ契約を満たすことを確認する（HA-01）。内部の自動試験に加え、実用adapterと実DB/外部系の結合試験を§7/8へ割り当てる。mockの成功をその代用にしない。

## 6. 今回の範囲を設計し実装する（P3/P4/P6）

担当: 設計/実装担当、必要な独立監査担当。入力: 合意した要求・Unit/反復・契約。原典: AI-06,07 + XP-01。
状態遷移、データ整合性、異常/並行時動作、影響する既存機能、必要な非機能・脅威・復旧を差分設計にする。
試験の期待値を要求から定め、対象ID、コマンド、環境、担当、証拠を実装計画と同時に決める。TDD/BDD等は製品で選んだ順序に従う。
[監査方法](../sds/audit-method.md)と既存policyのリスク別事前確認後、実装と試験を小さなまとまりで進める。設計が変わるなら先に設計/契約を直す（§9）。
実装・試験で設計の問題を見つけたら、根拠を示して設計を更新し、振る舞いを保持する小さなリファクタリングと自動回帰確認を行う。機能変更は別に識別する。試験・統合の裏付けが不足していれば先に補う。将来推測だけの汎用層は足さない。
出力: 要求/設計を参照するPR、実装、必要な試験、実結果。ページ・行数予算のために必要な動作や試験を切り捨てない。
終了: 今回のDoDを満たし、必要な独立監査を受ける。作者自身が監査PASS・認可・mergeを発行しない。

## 7. 小変更を統合し、全体の動作と反復の成果を確認する（P5/P6/P7/P9）

担当: 実装/試験担当、別のmerge担当、利用者/受入担当。入力: §6の変更・基準版・契約・受入条件。原典: AI-04,08,11 + G1/CI-01 + G2/OU-03。
1. 最新の検証済み基準版に今回の変更を合わせる。競合だけでなく、契約・データ・設定・他単位への意味上の影響を確認する。
2. 統合状態でbuild、単体/契約、影響する既存機能の回帰、接続を通るsmokeを実行する。既存CIが同じ対象版を確認済みなら有効な結果を再利用する。
3. 正常だけでなく重要不変条件の境界/失敗を確かめる。権限拒否なら外部効果0、再送なら二重効果なし等、契約の期待値と照合する。
4. 単位をまたぐ要求と非機能も確認し、採択IDの全件に必要な実証を結ぶ。実環境が要る検査は§8の担当/場所を明示し、未実施をPASSにしない。
5. 必須失敗/UNKNOWNなら原因箇所へ戻す（§9）。適用外は根拠を残す。試験対象や期待値を減らして成功にしない。
6. 既存の独立監査・認可・required checksを満たした小変更を別担当が共有mainへmergeし、更新されたmainのSHAでbuild/試験を確認して次の基準にする。各branchの緑やmainの取り込みだけでは統合完了にしない。失敗時は修正または認可済み復帰を優先し、緑に戻すまで健全な基準と呼ばない。
7. 反復終了時、合意した完了条件に対する成果を利用者へ示す。完成分の動作を確認してもらい、未完・発見・追加要望は同じIssue群へ返す。未完の実験は未完と明記し完成実演に数えない。
出力: 統合版/実結果/監査、反復の達成・未達・利用者の確認・次の変更。実装完了と実環境受入/運用移管/効果発現は別判定。
頻度: 稼働中の変更は少なくとも日次、できれば数時間ごとに共有mainへ統合できる大きさにする。認可/監査を飛ばして頻度を満たさない。待ちで日次未達なら理由・次担当を一度記録して止め、CIの原典条件を達成したとは言わない。人待ちの空実行や新たな定例会は作らない。

## 8. 実環境受入・運用・効果を確かめる（P7/P8）

担当: 配布担当、運用引受側、利用者/判断者、必要な独立監査。入力: 統合済み成果物、認可、runbook、実環境の受入条件。原典: AI-09,10 + 既存PRR/SDS。
採択した認可範囲で同じ成果物を配布し、実環境の正常/失敗・監視・必要な復旧/移行を実証する。scopeにない本番操作を手順から認可しない。
技術的な実用確認と利用者/引受側の受入を分け、成果指標と負担指標を対象・期間・方法に従って測る。CIや文書の完成を成果の代用にしない。
出力: 配布版・利用元読戻し・受入/復旧/引継ぎ・観測証拠。運用で得た欠陥/追加要望を§9へ戻す。
終了: 実装・受入・運用移管・効果のどこまで確認したかを明示。未測定の段階は未完のまま残す。

## 9. 追加開発・不具合・設計変更の戻り先

担当: 作者/リードと変更を判断する人。入力: 変更理由・対象成果物/版・優先度・影響する利用者/契約/データ/試験（AI-00 V,05,09 + G3/OU-04）。
次表はSDSの適用判断。複数に該当すれば、影響する上流まで戻る。変更がない節は有効な参照を再利用する。

| 変更 | 戻る場所 / 更新するもの | 再確認するもの |
|---|---|---|
| 利用者・問題・成果・scopeが変わる | §2で対話し要求を改訂。その影響を§3〜へ伝える | 変更した目的と全体受入・成果指標 |
| 合意した目的内の機能追加 | §1で既存モデル確認→§2の追加要求→必要な§3〜6 | 新旧契約・既存機能・親全体の受入 |
| 責任・データ所有・依存が変わる | §3/4で境界・単位・決定を改訂→§5/6 | 影響する提供/利用側と統合版 |
| 実装から設計改善が必要と分かる | §3/5/6の該当設計を先に更新。振る舞いを変えない整理と機能変更を区別 | 改善理由、既存動作の自動回帰、共有mainでの統合。契約が変わるなら下行へ |
| 接続契約を壊す | §5で対象利用元/版、互換期間・移行・廃止・復旧を合意。scope変更なら§2 | 新旧版の組合せ、切替/復旧、全利用元の移行確認 |
| 既存契約内の不具合修正 | §1で要件/設計と不具合を照合→§6。設計が誤りなら該当節を先に更新 | 再現する回帰試験と影響範囲の統合検証 |
| 振る舞い不変の軽微修正 | §1の理由・scope・既存参照を同じPRに記録→§6/7の必要範囲 | 既存動作の保持。新規要件書/ADRを一律要求しない |
| 結合/受入で失敗、証拠が無効化 | 原因を確認し、要求§2・構造§3・契約§5・実装§6・環境§8の該当箇所 | 新しい対象版で影響した試験/監査。古いPASSを流用しない |

既存の成果物を版管理で更新し、旧決定は後継を示す。要件IDを再利用・黙って削除しない。
変更に影響される親の受入・結果も再確認する。局所PASSの足し算で全体PASSにしない。
人の判断が必要なら論点・根拠・既定案・影響を一度示して停止する。無回答を既定案の採択にしない。
