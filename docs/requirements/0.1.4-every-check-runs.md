## Feature Goal

One hygiene run tells the consumer the outcome of every check, whatever failed first.

## Target User

- the operator of a consumer repository that calls `hygiene.yml` with `mode: report_only` (first: agent-comms-mcp);
- the seats that read a run to decide what to fix next (suite-lead, devauditor, the repo's implementer).

## Business / Operational Reason

The first consumer's run stopped at the first failing check and reported nothing for the eight later checks
[検証済: agent-comms-mcp#980 run 36524256657 — lines-baseline FAIL with 103 files; large-files, jscpd, knip,
depcruise, structural, guard, secrets, PR size SKIPPED; aun agent-comms-mcp#977 5884009062]. A report-only consumer
therefore learns one finding per run and must fix-and-rerun to see the next; the switch plan's evidence "all steps
recorded" (2-S2) cannot be produced.

## Main Flow

1. A PR or a push triggers the consumer's hygiene job (pinned to a Shirube version).
2. Setup runs (checkout, tools identity, install from lockfile, refs). If setup fails, the job fails there.
3. Every check runs, each with its own outcome, even when an earlier check failed.
4. The last step prints one `check=outcome` line per check into the step summary.
5. The job result is failure when any check failed or when a check has no outcome; success otherwise.
6. The reader fixes or baselines from the full list, not from the first failure.

## Acceptance Criteria (EARS; Given / When / Then in the design page's examples A1–A5)

| ID | criterion | pattern |
|---|---|---|
| R17 | When a check fails, the workflow shall still run every later check and shall fail the job. | event |
| R17a | The workflow shall not use `continue-on-error` on any step. | ubiquitous |
| R17b | While setup has not succeeded, the checks shall be skipped and the job shall fail at the setup step. | state |
| R17c | The last step shall list every check's outcome and shall fail if any of the nine unconditional checks is not `success`, if neither PR-size step is `success`, or if Python is neither `success` nor `skipped`. | ubiquitous |
| R17d | If a check step is cancelled, then the last step shall fail. | unwanted |
| R1 (re-worded) | The workflow shall run every check listed in the profile against the PR head and shall fail the job if any check fails. | ubiquitous |

R1's 0.1.0 phrase "on the first failing check" is superseded by R17: a failing check no longer stops the later
checks, and the job still fails. The requirement is not weakened; only the "first" is dropped. The spec seat's Issue
carries this wording; the implementer applies it to `docs/spec-w1.md` R1 in the takeover commit.

Success measure: checks with an outcome per run = 12 (Python counted as `skipped` when off), whatever the number of
failures — measured on the first consumer run after its pin moves to 0.1.4 [推測: not yet observed]. Burden measure:
reruns needed to see every result, from one per check to 1.
