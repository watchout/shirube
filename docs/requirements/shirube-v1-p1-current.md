## 2. 人と共有する初版の完成条件

最初の利用者はAIへ開発を依頼・管理する人。新規/作り直しの初期から、1repoの案件で使う。Mac miniのCodex CLI/Claude CodeとGitHubを利用する。
窓口との対話で目的・要求を固め、結果を変える判断だけ人へ返す。認可済みの通常作業は設計・実装・試験・独立監査・統合・実環境受入へ引き継ぎ、次担当の実開始まで確認する。
初版の受入は、次の利用体験と既存AC/AH/WPの条件を同時に満たすこと。第一の小さな実証や、画面/文書/CIだけを初版全体の完成にしない。

| 観点 | 利用できると判定する内容 |
|---|---|
| 完走 | 一つの実機能を要求から実環境の利用まで通し、人が運用開始を受け入れる。別機能で再現し、追加/修正でも同じ流れと既存機能の保持を確認する |
| 判断と自動進行 | 未承認/対象違い/必須不合格を通さない。範囲内は不要な開始号令を求めず進み、判断待ちでは停止する |
| 履歴 | 何を提示し誰がどう回答し、どの作業に適用したかと変更/失効を辿れる。現在有効な承認と過去の記録を混同しない |
| 見通し | 同じ工程表から順序・担当・現在地・詰まり/待ち先・次の行動・残る完了/利用条件が読める。予定/実績/確認済みを区別する |
| 単独/連携 | 単独で工程・承認・監査を使い、aun接続時の自動引継ぎ、kusabi接続時の再説明不要の再開も初版で実証する。各製品の責任を重複実装しない |

初回の人向け接続はCLI。Onza/Discord等の追加時に同じ要求/回答/履歴の適合と実接続を確認する。各窓口の試験条件を残すが、後続窓口の実導入を第一段階の必須へ暗黙追加しない。
第一段階は承認履歴と基本工程表/実績の保存・照会まで。詳細なOnza可視化と、改善案の検証/共有を回すPDCA機能は次段階。既存の独立監査や欠陥の是正を次段階へ延期する意味ではない。
複数repoを横断する上部管理、Codex Macアプリ、破綻済み開発の修復は初版対象外のまま。製品説明中の「進まなかった」を既存案件の救済機能へ読み替えない。

## 4. 工程1の出口と次の工程

今回の追加分は意味・範囲・責任・検証可能性を[固定8観点](shirube-v1-p1-addendum-audit-items.json)で独立監査する。項目集合自体の不足や表にない必須欠落も返却対象。作者の自己確認・CI・機械前検査だけでPASSにしない。
必要な是正と独立返却の機械受領が揃えば、追加分の工程1監査を完了とし、設計へ渡す。意味/範囲を変える指摘は人の判断へ、合意内容の転記誤りはその根拠で修正する。
次の設計/受入計画で具体化するもの: APIと認証/権限・本人回答経路、CLIの開始拒否を保証する方式、型/DB/保存/公開/復旧の整合、保持/削除、案件別粒度と計測、実証の対象版/別機能/担当/期間/費用。原文と各要求の未決をこの表だけで完了扱いにしない。
最初の実証は既採択の「要求・承認と作業開始の照合」を保持する（[設計案](../design/shirube-v1-design-questions.md)S1）。設計案にある候補を要求監査のPASSから自動採択しない。未決に依存する実装は開始しない。
