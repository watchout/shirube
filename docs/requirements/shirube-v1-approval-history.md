## 1. 保存を始める範囲と責任

初版の承認処理から履歴を保存する。可視化画面の実装は後の段階でも、当時の判断を追うために必要なデータを最初から残す。承認に関する全経緯が対象であり、全会話・全通信・LLMの内部推論を収集する要求ではない。
GitHubは承認権限の正本。Shirubeは判断要求と履歴の保存・照会・工程への適用を所有し、Onzaは将来の表示を担う。履歴の保存済み、GitHubでの有効な承認、実際の作業開始を区別する。
[Onza共通仕様の固定版](https://github.com/watchout/onza/blob/5abd5d93952434228a6e2387b2714d19ec133a9a/docs/common/README.md)に従い、共有PostgreSQLでは履歴をShirube固有スキーマに置き、人・席・実行主体等は提供側が定める共通参照へ結ぶ。物理テーブル名・型は本書で決定しない。

## 2. 残す情報の意味

以下は論理的な保存項目。正式なカラム・ID形式・API・保存技術の一括採択ではない。対象に該当しない情報と、未取得/未確認の情報を区別する。

| 情報 | 後から追える内容 |
|---|---|
| 要求と対象 | 一つの判断要求とその版、repo/案件/工程/作業、要求・設計・成果物の参照と版/digest、許可範囲・範囲外・有効性条件 |
| 実際の提示内容 | 人に示した質問・選択肢・理由/影響の説明・対象版の内容、表示した窓口と提示の試行/結果。回答をその提示版へ結ぶ |
| 回答 | 本人の原文または実際の選択値、回答元message/interaction等の参照、対応する要求/提示版。自由文を要約だけに置き換えない |
| 誰が関与したか | 依頼者、判断した人、取得/記録した主体、工程担当の席・実行主体の参照。人の回答とエージェントによるGitHub代理投稿を区別する |
| 時点と順序 | 発生時刻（取得可能な出所つき）、受信/保存時刻、要求内の確定順序と原因となる記録への参照。到着順を人の判断順と決めつけない |
| 照合と判断 | 本人/権限/対象版の照合結果と根拠・検査版、承認/修正/保留/取消、未確定・拒否理由。判断理由は本人が述べた内容を保持し、無回答なら理由を補作しない |
| 公開と有効性 | GitHub公開/読戻しの試行・結果、control_source_refのURL/digestと確認時点、失効/撤回/差替えの理由と先行/後継の対応 |
| 失敗や重複 | 取得/保存/公開の失敗、応答不明、旧版/無権限/曖昧な回答、重複配送・競合を同じ要求へ対応づけた結果。承認や適用の件数へ二重計上しない |
| 作業への適用 | どの承認版で、どの作業の開始を許可/拒否したか。指示・実開始・結果の証拠参照を区別し、実行記録から承認へも逆に辿れる |
| 記録の解釈 | 記録形式の版、訂正前/後の関係と理由、欠損・照合不能の区別。後の型/表示変更でも当時の意味を保持する |

本文・提示内容は後から元サービスのmessageが編集/削除されても当時の判断を再現できる形で保持する。URLやhashだけで内容保存を代用しない。元証跡の参照も残し、保存した写しを現在有効な権限に昇格させない。
秘密の資格情報や無関係な会話は含めない。承認に必要な本文の閲覧・出力には同じアクセス制御を適用する。訂正や秘匿化が必要な場合も、実施者・理由・対象と欠損の有無を追跡できる契約を定める。

## 3. 履歴の整合と可視化への接続条件

- 現在の状態だけに上書きせず、以前の質問/回答/承認と変更・訂正・失効の関係を辿れること。履歴保存の技術方式は未決であり、汎用イベント基盤の新設を要求しない。
- 要求待ち、回答取得、照合、公開確認、有効性、作業への適用は別の事実として照会できること。表示上の「承認済み」一項目へ未公開や失効を混ぜない。提示失敗も、人が見た証拠にしない。
- UI/会話形式の切替、再送、遅延・順序逆転、同時回答、再起動後も同じ要求/回答/適用を識別する。二重処理の検出は履歴に残すが、人の新たな判断や二重の開始にしない。
- GitHub本文の変更/削除、不一致、確認不能は、その観測と過去の確認を区別する。履歴照会は過去を表示できても、現在の開始許可は正本と有効性を再照合する。
- 必要な承認/適用記録の保存を確認できない場合、保存済み・開始可能と扱わない。故障した保存先へエラーを書けたと仮定せず、復旧後に外部証跡と照合する。回復不能な欠損は明示し、記録を推測で補完しない。保存と公開/開始の部分成功を回復する契約は実装前に定める。
- 案件・repo・要求・対象版・人/席・期間・結果/有効性・適用作業から、履歴と現在状態を機械可読で照会/出力できること。Onzaは同じデータから時系列と作業との対応を表示し、承認状態を独自に再判定しない。
- 表示用の集計を作る場合も元記録へ戻れること。検索・ページ分割・出力の途中で欠落や重複を起こさず、権限のない対象の内容・件数を漏らさない。具体的なAPIと権限境界は未決。
- 人待ち中の定期的なhold記録や同じ質問の再生成は行わない。実際に起きた提示・回答・変更・失敗等を記録する。

| ID | 要求と試す場面 | 満たしたと判定する観測 |

| AH-03 | 対象変更・撤回・訂正・GitHub本文の編集/削除 | 過去の内容と後継/失効理由が残り、履歴表示から古い許可を復活させず、新しい作業開始に流用しない |

| AH-06 | Onza UIを停止し、複数案件の履歴を再起動後に照会/出力する | §3の検索条件と参照を使って全件を重複なく取得し、同じ保存データから時系列・承認と作業の対応を再現できる。画面の完成はこの受入の前提にしない |
| AH-07 | 閲覧権限の違う主体、記録形式の更新、バックアップからの復元 | 閲覧/出力の境界を守り、旧記録の意味と参照関係を維持する。採択する保持/復旧条件に対する欠損・不一致を確認できる |
