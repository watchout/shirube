## 1. 段階と利用体験

| 段階 | 実現すること | この段階の完了に含めないもの |
|---|---|---|
| 第一段階 | 計画時から工程表を用意。人とAIが同じ順序・依存・担当・現在地・次の行動・完了/利用開始条件を参照する。着手/終了/確認済み完了と待機・手戻り・問題/成功の実績を承認へ結んで保存する | 詳細ダッシュボード、傾向分析、改善案の検証・共有を自動で回す機能 |
| 次段階 | Onzaで計画/実績/承認/滞留/手戻りを辿る。成功と失敗から改善案を比較・検証し、採択した手順/スキル等を次の案件へ適用して効果を確認する | 未検証の教訓の全席への自動適用、目標や機能範囲をAIだけで変更すること |

第一段階ではCLI会話と同じ記録から生成する工程表で成立させる。人が手作業でGitHubや別の表を更新しなくても、人とAIの参照内容が一致すること。Onza UIの稼働を必須にしない。
着手・完了・差戻し・重要な詰まり等の変化で更新し、窓口から現在地を取得できる。人の開始号令を通常工程に追加せず、人待ちの再通知や空の履歴生成を繰り返さない。
予定は計画の根拠と版を持ち、実績とは別に表示する。見込みが未測定なら「不明」とする。未確定の依存や日付を埋めて、確約した工程表に見せない。

## 2. 工程表の粒度と計画

粒度の初期案は「機能/開発単位 → その中の工程 → 必要な実行作業」。一行は成果・担当・完了の証拠を対応づけられる単位とし、担当/受入/依存が異なる時に分ける。全案件を同じ工程数や時間幅へ固定せず、tool呼出し一回ごとを工程にしない。
案件計画で具体的な粒度・依存・順序を示して確認する。手戻りは元の工程に紐づく別試行として残し、最初の完了や失敗を消さない。工程の追加/分割/統合/中止にも先行計画との対応と変更理由を残す。
各工程は、目的/親要求、成果物、前提・依存、担当席と役割、完了条件と観測方法、必要な承認/監査、次へ渡す条件を持つ。全体では「実環境で何ができれば利用開始か」まで結ぶ。
近い作業から具体化し、先の未決事項を区別する。順序の変更が価値・範囲・実装方式等を変える場合は人が決める。工程表を作ること自体で未選択の設計を採択しない。

## 3. 第一段階から残す情報

論理的な保存項目であり、物理テーブル/API/型は未決。承認履歴と同じ案件・対象・工程・試行への参照を使い、別の承認台帳を作らない。

| 情報 | 保存・表示の条件 |
|---|---|
| 計画と変更 | 計画の版、目的/対象/親子関係、順序・依存、完了/利用条件、承認参照、変更理由と前後の対応。元の計画を見込みで上書きしない |
| 担当 | 予定担当と実際の担当、役割、共通の席・実行主体の参照、交代履歴。LLM/モデル/セッションと継続する席を区別し、取得不能なIDは推測しない |
| 時刻 | 予定、現在の見込みと根拠、指示/配送、実着手、停止/待機/再開、作業終了、完了条件の確認、利用受入の各時点。発生時刻と受信/保存時刻を区別する |
| 状態と次の行動 | 未着手・実行中・確認中・完了・待機/停止・差戻し・中止等の意味、根拠と最終確認時点、詰まりの理由/影響・待ち先・解除条件・次の行動。正式な列挙型は詳細設計で定める |
| 作業と証拠 | 対象版、入力、適用した設計/手順/スキル/試験の参照と版、実行結果、成果物・監査・承認・実開始の証拠。取得できた事実と未確認を区別する |
| 問題と手戻り | 発生した工程、発見した工程、観測内容と影響、修正先/元の試行、対応とその結果。原因が不明な時に発生箇所を断定しない |
| うまくいったこと | 行った方法、状況/前提、観測した結果、出所。成功の事実と「この方法が原因」という仮説を分け、未観測なら補作しない |

実着手/完了は実行元の証拠と工程条件から記録する。aunの配送受領やLLMの「完了しました」だけを開始/完了時刻にしない。人の判断者と代理記録者も区別する。
経過時間、実行区間、承認待ち/外部待ち/確認待ち、手戻りの時間は区別できるよう保存する。並列作業の時間を単純加算して案件の経過時間にせず、CLI稼働時間を人の工数とみなさない。欠けた区間を0として埋めない。
画面/回答では計画版と最終確認時点を示す。「実装終了」「試験/監査確認」「統合」「実環境受入」を区別し、何が残れば使えないかを表示する。予測不能や記録欠損も表示する。
進捗率を出す場合は対象母集団・計算方法を先に定める。未定なら成果物/受入条件の達成状況を示し、LLMが百分率を推定しない。scopeや計画の変更で分母を黙って縮めない。

## 4. 次段階の振り返りと改善

計画の成果/観測条件 → 実績 → 成功と失敗の検証 → 次に変えること/続けること → 次の作業での効果確認、を同じ工程記録へ結ぶ。毎工程に別帳票や会議を増やす前提にはしない。
振り返りの開始点は工程/反復の終了、失敗や手戻り等を候補とし、頻度・対象・費用上限は次段階の設計で決める。改善のために未完の開発を無期限に止めない。

| 処理 | 担うものと証拠 |
|---|---|
| 実績の収集/集計 | 実行系とコードが記録・版/重複/時刻/対象を照合する。事実の取得と集計をLLMの作文だけに委ねない |
| 要因と改善案 | LLMが事実から複数の原因仮説、再現できる成功条件、対立する説明、改善候補と比較方法を提示する。仮説を確認済みの因果にしない |
| 効果の確認 | 元の手順と変更案を、事前に固定した対象/条件/試験で比較する。品質・再発・手戻り・時間と負担を合わせて確認し、品質低下による速さを改善にしない |
| 調整の選択 | 目的、計画、方法の変更か、継続かを明示し、担当・次の行動・完了証拠を結ぶ。結果が変わる選択は人へ返し、その判断を承認履歴へ接続する |
| 再利用 | 採択した手順/スキル/試験/引継ぎ方法を適用範囲・版・根拠・切戻し条件つきで利用する。次の実案件でも効果を確認し、合わなければ修正/失効と後継を残す |

改善は「仮説→限定検証→必要な独立監査/人の判断→採択→実適用と再検証」を追えること。既存認可内の通常作業は自動で続けるが、手順の自己書換え・未検証の学習内容の全席配布を許可しない。
「エージェントの開発スキル向上」は、版管理した作業方法を次の案件に使い、その成果を測れる要件へ落とす。LLM本体の再学習方式は選定していない。席やモデルが交代しても、採択版・適用条件・過去の作者/監査履歴を引き継ぐ。
指標の候補は、受入までの経過時間、待ちの内訳、手戻り/欠陥の再発、実環境受入、状態確認のための人の操作負担。PR数・文書量・反省文数を技能や改善の代用にしない。比較期間・分母・目標値は未採択で、改善効果は未測定。
