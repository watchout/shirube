## 工程1：単独利用・連携範囲の合意と、要求の全体確認版

記録者: codex-adf。今回の合意を公開し、既存の対話を同じ版で確認できるようまとめる。今回の合意は下記§1。§2以降は個別の合意を統合した確認版で、全体確認・要求監査・実装受入の完了を意味しない。

### 1. 今回のOwner回答と採択範囲

直前に作者が確認した内容:
> Shirube単独では工程・承認・監査の管理を使え、担当間の自動引継ぎにはaun、経緯を説明し直さない再開にはkusabiを接続する、という提供範囲でよいでしょうか？

Owner原文:
> はい

この回答により、単独利用と連携利用の提供範囲を以下とする。

| 構成 | 提供する範囲 |
|---|---|
| Shirube単独（合意済みの開発環境・GitHubは利用） | 開発工程・承認・監査の管理 |
| Shirube + aun | 上記に加え、窓口と各役割の通信を通じた担当間の自動引継ぎ |
| Shirube + kusabi | 記憶・文脈を復元し、GitHubや実作業状態との照合を経て、経緯の再説明なしに再開 |
| Shirube + aun + kusabi | 上記を組み合わせ、再開後の担当間の引継ぎも含めて確認 |

自動引継ぎと再説明不要の再開は初版の要求として残る。単独構成が提供する機能と、連携を含む初版全体の完成条件を分ける。単独構成だけの成功を初版全体の完成に読み替えない。aun・kusabiの同等機能をShirube内に再実装する採択ではない。

前コメントで未決としていた「単独時に成立する利用範囲」は本節で具体化する。接続方式・未接続/障害時の詳細動作は設計で扱う。

### 2. 工程1の目的と、これまでの要求のまとめ

最初の利用者は、AIエージェントへ開発を依頼・管理する人。Ownerの目的は「開発の高効率化自動化による高速開発化」。第一段階は「完成できることでいい」。

Ownerから報告された困り事は、AUNの冗長化、Shirubeの形式的で実用できない成果、OmotenasuAI群の多数のバグ・修正・作り直しによって、望む完成に辿り着かないこと。これは利用者の経験であり、個別製品の技術原因を認定したものではない。

| 項目 | 合意した要求 | 根拠 |
|---|---|---|
| 完成 | 合意した機能を実利用でき、利用を妨げる不具合が解消され、人が運用開始できると判断する | S1, S2 |
| 対象 | 新規・作り直しの初期から導入。初版は1repoの開発案件 | S1, S4 |
| 全工程 | 要求の対話→設計・契約→開発単位と計画→実装→試験→独立監査・是正→統合→実環境受入。監査は対象に応じて必要な段階にも入る | S2, S9 |
| 追加・修正 | 目的・要求の確認から実環境受入まで再度つなぐ。有効な既存成果・承認を再利用し、影響する既存機能も検証する | S2 |
| 人の判断 | 実装方法・機能・影響範囲・拡張性・汎用性など、結果を変える判断は人が行う。LLMは選択肢・根拠・影響を示す | S1, S2 |
| 通常進行 | 承認された作業と工程移行は自動でつなぎ、次担当の実際の開始まで確認。人の開始号令や伝言を通常フローにしない | S2, S6 |
| 窓口 | 各repoにつき1窓口。人はエージェントとの会話で判断・承認し、エージェントがGitHubへ記録する | S5, S6 |
| 独立性 | 窓口を一つにしても、作者・独立監査・mergeの責任と権限は分ける | S2, S6, S9 |
| 中断後 | kusabiから文脈を復元し、GitHubと実作業状態を照合して再開。有効な承認を再利用し、欠落や新判断は推測で埋めない | S7, 本文§1 |
| 役割と製品分担 | 役割は継続する席に置き、LLM/セッション交代と区別する。Shirubeは開発工程、aunは通信、kusabiは記憶・復元 | S7, S8, 本文§1 |
| 対応環境 | ローカルMac mini、Codex CLIとClaude Code、GitHub管理 | S3 |
| 共通情報 | PostgreSQL共有時は1DBのcommon/製品別スキーマ。共通仕様・型等の正本はOnza。Onza UIの常時起動を必須にしない | S8 |
| 基盤となる規格 | 採択済みのAI-DLCを基盤とするShirubeの原典・手順・監査方法を利用する。固定項目、機械照合、独立した内容判断を組み合わせる | S9 |

GitHubのcontrol sourceへ公開した判断の対象・版・有効範囲を辿れるようにする。kusabiの記憶やaunの通信結果を、それだけで承認や作業完了の証明にしない。

初版の対象外は、複数repoを横断する上部管理層とその窓口、Codex Macアプリ対応、破綻した既存開発を調査・修復する機能。将来の上部管理層にも1窓口を置く構想を保持する。

### 3. 受入で観測する内容の整理（試験結果ではない）

既存AC-01〜10のID・母集団・完了条件は維持する。以下は対話で合意した要求と、既存AC/確認方法案をまとめた検証観点。

| 観点 | 観測すること |
|---|---|
| 実用上の完走 | 実機能を要求から実環境の利用まで通し、利用者が合意した完成条件で受け入れる。既存AC-10どおり別機能でも再現する |
| 自動引継ぎ | aunを接続し、前工程の終了条件充足から後工程の実際の開始までを記録。通常の開始号令・人の中継が不要であることを確認する |
| 人の判断と検査の実効性 | 未承認の選択、欠落/古い証拠、必須検査の不合格を通さない正負の確認。独立監査の指摘を是正して再確認する |
| 中断と再開 | kusabiを接続し、中断後に経緯を再入力せず再開。承認失効・成果物変更・完了済み作業がある場合も整合と二重実行の有無を確認する |
| 追加・修正 | 変更した要求から実環境受入までつなぎ、影響する既存機能・契約の保持も確認する |
| 単独と連携の分離 | aun/kusabiを未導入でも単独範囲が使えることと、接続後に連携範囲が成立することを分けて実行確認する |

合意済みの完成条件を、文書数・PR数・CI greenだけの指標に置き換えない。初版に速度短縮率や自動化率の未合意の数値目標は追加しない。

### 4. 残る具体化と、この確認版の扱い

- 受入計画で具体化する事項: 実証する機能と別機能、対象版・利用場面、観測担当・期間。通常の引継ぎに必要だった人の操作と、人の判断・承認のための待ちを区別して記録する方法も明示する。未測定の速度・負担を改善済みと主張しない。
- 設計で案を出し、人が選ぶ事項: 接続API、席の割当と権限、判断の取得元/対象版との対応と検証、状態遷移・保存方式、起動/再開の実行主体、通信・記憶の障害/再送/重複時の動作。
- 次の全体確認では、§2の要求と§3の受入観点がOwnerの意図と一致しているかを確認する。上記の具体化が未決であることも残す。全体確認を技術方式の一括承認にしない。
- 独立監査には、要求の意味・出典の忠実性、抜け/矛盾、単独/連携範囲、検証可能性、責任境界を確認できる対象として渡す。監査未実施をPASSにしない。

## 既存の親受入条件（削除・縮小しない）

取得元: https://github.com/watchout/shirube/issues/6 / Issue本文SHA-256 `05eae8f69250e68d43f80780ecc9fe9282166b620c68433260f2b8d573132d17`。
上記の確認済み本文が保持するとしているAC-01〜10を、監査対象の同じ版から引用できるよう固定する。Issue本文自体を新しいowner decisionとして扱わない。

### AC-01 正本が一つ
- 現行Shirubeの正本repo・版・commit/tag・入口が一意。
- 旧ADF/旧policyとの優先関係が明示される。

### AC-02 Goalとscopeを実装前に固定
- 何を作るか / 作らないか / Done / 証拠が実装前に固定される。
- Goal→atomic acceptance→test/evidenceまで追跡できる。

### AC-03 工程の入口・出口が一意
- 企画→設計→実装→試験→監査→merge→受入→実案件投入の各工程に開始条件・終了条件・証拠がある。

### AC-04 冗長化・肥大化を止める
- 重複実装、不要抽象化、同一機能の再実装、無制限な行数増加を検査できる。
- 例外は理由・期限・責任者付きで明示する。

### AC-05 各repoが同じ規格を利用できる
- 共通規格の複製なし。
- 各repoはprofile等の製品固有値だけを保持。
- 導入手順が固定版だけで再現できる。

### AC-06 検査が実効する
- 正例と負例の両方を実行。
- FAIL/UNKNOWN/NOT_RUNをPASSへ読み替えない。
- 必要な対象ではrequired/blockingとして実際に拒否できる。

### AC-07 既存成果と境界を壊さない
- 導入前後で既存の主要試験・契約・公開境界・互換性を比較。
- 規格導入を理由に製品機能を削らない。

### AC-08 担当が待たずに次へ進める
- BLOCKED時に `原因 / 次担当 / 次成果物 / 解除条件 / 証拠` が一意。
- CEOの細かなHOW指示待ちを通常フローにしない。

### AC-09 統合・受入・実案件まで同じ流れで閉じる
- CI greenや単体テストだけで完成扱いしない。
- API/DB/権限/UI/実機/現場/実案件のうち適用対象を明示し、必要証拠まで閉じる。

### AC-10 実運用再現性
- 1つの実機能を企画から実案件投入までこの規格で通す。
- 別機能でも同じ手順で再現できる。
