## 1. 原典から定める範囲

いまの完了条件は、単独と連携の境界、開始/結果の相互作用、失敗時の観測方法と選択肢を判断可能にすること。正式なUnit分割、型/API、実行権限契約の確定ではない。

| 構成 | 必要なもの / 提供範囲 |
|---|---|
| 単独 | Shirube、採用PostgreSQLの共通/製品領域、GitHub、対応CLIとその認証。工程・承認・監査・履歴/現在地を管理。AUN/Kusabi/Onza UIの起動や接続情報は不要 |
| AUN接続 | 同じ工程条件へAUNの作業/実行参照を結び、担当間の通信と自動引継ぎを追加。単独時の接続を並行して同じ作業に使わない |
| Kusabi接続 | 文脈の復元後に現在の要求/判断/実作業へ照合。未接続でもGitHubと保存記録の照会はできるが、再説明不要の再開を達成したとはしない |

単独時も独立監査者の配置は必要で、一人の作者による自己監査へ変更しない。共通DBの導入/型はOnza正本を再利用する。
AUN接続済みの実行が不明になっても、単独方式へ自動で切り替えて再実行しない。停止中の旧実行を照合し、構成変更の判断と試行の対応を残す。
単独利用の成功は、AUN/Kusabi連携と別機能の全工程を含む初版全体の完成条件を代替しない。

## 2. 接続の責任と情報

案件/判断/履歴の所有は既存境界案のまま。実行元の変換は接続部が担当し、工程判定をCLI別・AUN別に複製しない。
利用者はどちらの構成でも同じ窓口エージェントへ依頼・回答し、同じ工程表と履歴を確認する。AUNの有無だけを理由に、別コマンドでの開始や工程ごとの開始号令を求めない。
Shirubeが開始条件を照合した後、単独ならローカル実行側へ、連携ならAUNを通じて担当へ依頼する。返却の表現を接続部で変換し、同じ工程条件へ照合する。
依頼/受領/実開始/結果/工程合格の区別、認可の範囲、失敗/不明時の停止は共通。別担当への自動配送はAUN接続で追加される機能であり、単独でも同じ配送機能があるとはしない。

| 境界を通る情報 | 必要な意味 / 所有者 |
|---|---|
| 開始要求 | 案件/工程試行、要求・設計・対象repo/版、作業範囲/操作/環境、席と接続世代、判断/証拠参照。同じ試行を識別する再送キー。工程側が条件を所有 |
| 照合結果 | 対象と照合版、許可/拒否/不明の理由、必要な人の判断・解除条件。表示やLLMの返答で許可へ変換しない |
| 実行元参照 | 実行元の種類と版、元の実行識別子、席/接続世代。単独ならローカル実行、連携ならAUNの参照を使い、AUN IDを単独の必須項目にしない |
| 開始/終了の観測 | 接続部が観測した起動試行、プロセス/セッションとの対応、実操作の証拠、終了/切断、発生時刻と受領時刻。LLMの申告は別の入力 |
| 成果の照合 | 成果物の固定版、試験/独立監査/受入条件への証拠。工程側が実行報告を照合し、次工程/差戻し/待機を決める |

これは論理項目の一覧。通信型、制約、永続化の確定点、認証方法と契約版は境界/Unit確認後にSDS§5/6で固定する。
単独接続部は管理対象のCLI作業を開始/観測する最小限の処理とする。親依頼の配送網、複数席のタスクキュー、provider選択・費用回復を新設しない。

## 3. 共通の進行と接続先の違い（案）

1. 窓口で人が目的と必要な判断を伝える。対話の開始と、承認対象の変更作業の開始を区別する。
2. 窓口からの開始要求をShirubeが受け、保存記録とGitHubの公開本文/digest、現在の対象/席、必須監査・CIを照合する。
3. 条件を満たした同じ作業だけ実行側へ渡す。単独時はローカル接続、AUN接続時は担当への依頼を使い、両方で同じ開始条件を実行側の効果へ結ぶ。許可済み範囲での通常進行に人の開始号令を追加しない。
4. 実行の直前に対象変更/撤回/重複を再照合する。開始受付の保存と実開始を別々に観測し、CLIの起動・turn開始だけで変更作業が着手済みとはしない。
5. 単独時のCLI出力、またはAUNの実行報告を接続部で受け、終了結果と対象の差分/試験結果を同じ試行へ結ぶ。exit 0や「完成しました」だけで工程を完了しない。
6. 工程条件を満たせば現在地と次の作業を更新する。同じ管理対象で実行可能な許可済み作業を続け、必要な人の判断では一度通知して停止する。別担当への自動配送はAUNの範囲。

開始前にCLIへ対象の書込み権限や保護操作の資格情報を渡さない接続を検討する。対話用CLIが同じ対象へ別経路で書ける配置は、この拒否を保証できない。
実行プロセスが起動後に持つ権限、対象外の操作、MCP/ネットワーク経由の効果も契約へ含める。単なるwrapperや作業ディレクトリ指定を隔離と呼ばない。
管理対象の変更作業は、AUNの有無にかかわらずShirubeの開始照合を通す。これは機械的な実行経路の条件であり、人に新しい起動操作を毎回求める条件ではない。PC全体の任意CLI/シェルを管理できる保証とは分ける。

## 4. 失敗・停止・復旧で守る条件

| 場面 | 必要な動作 / 観測 |
|---|---|
| 未承認・対象違い・必須監査FAIL/UNKNOWN | 変更作業の実行へ渡さず、理由と解除条件を返す。人待ちは一度通知して停止 |
| GitHub/必須DB/照合処理が利用不能 | 新しい許可を出さない。記録できない完了を保存済みにしない。任意Onza UIの停止と区別 |
| 許可後の対象変更/撤回 | 許可を流用しない。開始直前の確定点と撤回の順序を契約化し、開始済み操作の中断可能性/残る効果を区別する |
| 同じ開始の並列要求・応答喪失 | 同じ試行に結び、実行有無が不明なら新規起動しない。保存済み受付だけで未実行とも開始済みとも断定しない |
| 実行中の切断・再起動 | 元の実行と実対象を照会して照合。不明のまま自動再実行しない。時刻欠損を推定値で補わない |
| hook無効・異常・対象外tool、CLIの直接起動 | 管理対象の効果が別経路から発生するかを実測。防げなければその配置の開始拒否は不合格とする |
| 終了報告と証拠の不一致・古い結果 | 未完/差戻しとして根拠を残す。別試行/別版への転用やAUN処理完了による工程合格を拒否 |

認証した本人回答の取得・転記、撤回の確定点、停止上限/timeout、保存と起動の部分成功、実行権限の隔離方式は未決。実装前に具体契約と試験を揃える。
人待ちでなくても連続非進捗の上限3回を保持し、状態変化がない同じ取得失敗を空回りさせない。

## 6. CLIの確認事実と残る技術設計

2026-10-04の読取り確認: ローカル`codex-cli 0.144.2`の`exec --help`に`--json`/`--sandbox`、`Claude Code 2.1.281`の`--help`に`--print`/`--output-format stream-json`がある。モデル処理は実行していない。
[Codex非対話実行](https://learn.chatgpt.com/docs/non-interactive-mode)と[Claude Codeの非対話実行](https://code.claude.com/docs/en/headless)は構造化出力を説明する。取り込みの候補であり、本人承認や開始拒否をそれだけで保証しない。
[Codex hooks](https://learn.chatgpt.com/docs/hooks)のMCP tool hooksはエラー/接続先不在を操作拒否にしないと説明する。hookを唯一の拒否境界にしない根拠で、当該版の実機試験結果ではない。CLI資料は接続可否の入力で、SDSの原典追加ではない。

先のS-A/S-Bを「単体だけの使い方の選択」として提示した質問と推奨は作者が撤回する。AUNの有無と、CLIのどこへ開始照合を接続するかを混同していた。
開始処理側へ照合を接続する方式、既存セッションの操作前へ接続する方式などは、共通の利用体験を満たす技術候補として比較する。AUN接続時も実行側の拒否が必要で、AUN導入だけで解決したとはしない。
どちらも操作の迂回・hook障害・権限分離を実証する必要がある。型/API、既存セッションの継続方法、導入設定、実行権限の分離は未選定。利用方法に実際の制約が出る場合に、その根拠と代替案を具体化して人へ示す。

内部責任は後続のOwner回答によりAを採択済み（[採択参照](shirube-v1-responsibility-and-data.md)）。AUN有無の質問やこの採択を、CLIの技術方式の選択へ拡張しない。
内部境界の確認→Unit/短い反復→必要な正式契約/詳細設計→独立監査→実装・試験へ接続する。新たなDB/CLI設定・常駐実行器をこの文書で導入しない。

目的は既存要求AC-08とPC-01〜04/14の具体化。共通契約の返却待ちを、この方式比較まで停止する理由にしない。

今回の完了の観測は、LLMの正常終了/異常終了・Shirube停止・Macのログアウト/再起動ごとに、次に動く主体、元実行の照会、利用者の追加操作と未保証部分を比較できること。単なる開始宣言を進捗にしない。

### 7.1 確認した接続入口と、確認していないこと

2026-10-05にmacOS `26.6.2`、`codex-cli 0.144.2`、`Claude Code 2.1.281`を読取り確認した。CLIは版とhelpだけを実行し、モデル処理・設定変更・新規席・サービス起動は行っていない。

| 一次資料とローカル観測 | 設計へ使える範囲 |
|---|---|
| [Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode)、ローカル`exec --help`と`exec resume --help` | JSONL出力と、指定セッションの再開入口がある。thread/turnの開始・完了/失敗とtool項目を接続入力にできる。プロセス/turn開始だけで要求された変更作業の実開始・工程合格とはしない |
| [Claude programmatic mode](https://code.claude.com/docs/en/headless)、ローカル`--help` | 非対話実行、stream-json、明示sessionの再開入口がある。resultは実行結果として扱い、監査/受入の合格にはしない。許可拒否・失敗・途中切断を接続試験に含める |
| [Claude SessionEnd](https://code.claude.com/docs/en/hooks#sessionend)、[Codex hooks](https://learn.chatgpt.com/docs/hooks) | 終了等の通知を取り込む候補。通知の欠落・hook異常と、host自体が停止した後の復旧は別に扱う。hookへ「続けろ」と返すだけでは全経路の継続を保証しない |
| [Apple launchd](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)、当該Macの`launchd.plist` manual | macOSは利用者ログイン中のagentと、system側のdaemonを区別し、必要時起動/継続稼働を管理できる。ログアウトや終了の扱いが異なる。Apple文書はarchiveで、今回の設定/版での動作は実機確認が必要 |

CLIの機械向け出力とsession再開は、席ID・本人性・権限隔離の保証ではない。providerのsession IDを共通seat IDへ置換せず、当該試行と実行の参照として保存する。並行作業があるため「最後のsession」の自動選択を用いない。可変の公式文書と、このMacのhelp観測、未実施の製品試験を区別する。

### 7.2 推奨する構成と比較

**提案: 進行判定と次行動の処理を、LLMのturnから独立して動くShirube本体の処理に置く。** 同じ製品の実行部であり、別の汎用配送製品・共通常駐MCP・AI-DLCの専用engineを追加する案ではない。AUNなしは最小のローカル実行接続、AUNありは既存の実行管理契約へ渡す。

| 候補 | 次行動と停止後の扱い | 判断材料 |
|---|---|---|
| **Shirubeの制御処理がイベントを受け続ける（推奨案）** | CLI出力/終了・検証済み回答・外部結果を受け、現在条件を再照合し保存済みNextActionを進める。自身の再起動でも未確認実行と次行動欠落を照会 | CLI終了後も受信・確認処理が残る。継続稼働するプロセスとOSの起動/停止管理が必要。永続化・権限分離・二重起動排除を省略できない |
| OSが必要時に短いShirube処理を起動する | 同じ核を呼ぶ。各通知/再起動から実行し、長いCLI実行の観測を別の実行元へ保持する | 常時稼働を減らせるが、通知の耐久化・欠落再取得と長時間実行の監督を別に接続する必要がある。単独初版では接続箇所が増える見込み。性能/実装日数は未測定 |
| CLIのhook/LLM継続だけに任せる | 通常終了時に次を促せても、CLI自身の停止や通知欠落後の起動主体が残らない場合がある | この方式単独の採用は推奨しない。外部の耐久な起動・照合を補えば上記いずれかとの組合せになる |

この推奨は方式比較であり採択ではない。AUNが既に実行管理を担う構成で、Shirubeが同じCLIを二重に起動/監督しない。継続判定はShirube、配送/実実行の管理は接続先という監査済み境界を保つ。

### 7.3 実行に落とす時の動き

1. 窓口との会話、必要な本人判断、許可済みの変更作業を分ける。同じ窓口体験を保ち、メッセージごとに別CLIを起動し直す仕様にはしない。指定した試行/席/既存sessionへの接続又は認可された新実行を選ぶ。
2. 進行側は対象版・現在の判断/共通参照・必須監査を照合し、同一試行の開始要求を耐久保存。実行側が現在権限を再検査してから対象CLI/処理を開始する。具体的な隔離境界がない状態では開始拒否を保証しない。
3. CLI接続部は管理した実行から構造化イベントを受け、元試行・実行・世代に結ぶ。stdoutのLLM文・JSONの自己申告を特権ある観測へ昇格させない。既存sessionへ接続する場合も正当な発行元と制御範囲を検査する。
4. CLIの正常終了/失敗/切断をそのまま工程完了にしない。進行側が成果/必要試験/独立監査の固定版を確認し、終了条件が揃えば次行動を保存して進める。人の再号令は不要。未充足なら是正先/照会先へ結ぶ。
5. 人の判断待ちになった該当作業は一度通知して止める。再質問、LLMの空実行、hold生成を繰り返さない。受信口が待ち受けることと、待機中の作業を再試行することを区別し、独立した実施可能作業は進める。
6. 制御処理が落ちた時はOS側が選定した条件で復帰させ、永続記録と既存実行を照会する。新しい制御処理が動いたことだけで旧CLI/gatewayを停止済みとせず、元実行の解決前に二重起動しない。回復の予算を超えた作業は止め、プロセス再起動で予算/停止状態をリセットしない。

ローカル実行結果・本人回答・GitHubの外部監査返却にはそれぞれ受信契約が必要。GitHub側の変更を取り込む経路、失われた通知の照会、問い合わせ予算は未確定であり、hookの存在で代用しない。LLMを定期起動して返却を探させる案にはしない。
制御処理が稼働していても、hostの電源断/スリープ中に実行が進むとは保証しない。再開時には当時の許可を再照合する。

### 7.4 Ownerに必要な稼働条件の選択（未回答）

初版のMac miniで、次のどちらを必要とするかを決める。工程ごとの開始許可やCF-AUTH-01 Aを再確認する質問ではない。初版の動作範囲と導入/運用負担が変わるため、作者が黙って決めない。

| 選択 | 利用者の動きと進む範囲 | 導入・復旧への影響 |
|---|---|---|
| **A: ログイン中に自動進行（初版の推奨）** | Macにログインし起動条件を満たす間は、CLIの返答終了後もShirubeが許可済み作業を進める。ログアウト中は進めず、次のログイン時に照合して再開 | OSの利用者セッションを起動範囲にする案。ログアウト後も進む保証を初版へ加えない。CLI/制御処理の異常終了からの復旧と権限分離は省略しない |
| B: ログアウト後も自動進行 | ログイン状態に依存せず、Mac稼働中は許可済み作業を進める。本人の判断が必要な作業だけ回答を待つ | システム側の起動管理、専用実行主体、ログインなしのCLI認証供給/更新、確認画面への到達と復旧を初版で実証する。追加の設定/運用が必要 |

どちらでも、本人確認・秘密/保存先をAI実行から隔離する要件は同じ。稼働時間の選択をOS権限方式の採択へ拡張しない。導入時の一度の登録/起動条件の整備と、毎工程の開始号令を区別する。
回答後は選定した範囲で起動元/CLI入力出力/照会・停止/設定の具体差分と試験手順を固定し、結果を変える配置上の未決を示して必要監査へ渡す。ログアウト条件を決めても、共通F01・本人確認の配備/登録・外部効果の確定点まで解消済みにはしない。
