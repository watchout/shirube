## 1. 原典から定める範囲

[採択済みSDS手順](../process/ai-dlc.md)§3は責任/所有/依存、§4は実動作の観測、§5は提供/利用双方の契約、§6〜8は実装・結合・実環境の確認を要求する。
原典AI-01/03の固定版・digestは[設計質問](shirube-v1-design-questions.md)を参照。本案はその適用であり、AI-DLCがShirubeのCLI方式を指定しているわけではない。
いまの完了条件は、単独と連携の境界、開始/結果の相互作用、失敗時の観測方法と選択肢を判断可能にすること。正式なUnit分割、型/API、実行権限契約の確定ではない。

| 構成 | 必要なもの / 提供範囲 |
|---|---|
| 単独 | Shirube、採用PostgreSQLの共通/製品領域、GitHub、対応CLIとその認証。工程・承認・監査・履歴/現在地を管理。AUN/Kusabi/Onza UIの起動や接続情報は不要 |
| AUN接続 | 同じ工程条件へAUNの作業/実行参照を結び、担当間の通信と自動引継ぎを追加。単独時の接続を並行して同じ作業に使わない |
| Kusabi接続 | 文脈の復元後に現在の要求/判断/実作業へ照合。未接続でもGitHubと保存記録の照会はできるが、再説明不要の再開を達成したとはしない |

単独時も独立監査者の配置は必要で、一人の作者による自己監査へ変更しない。共通DBの導入/型はOnza正本を再利用する。
AUN接続済みの実行が不明になっても、単独方式へ自動で切り替えて再実行しない。停止中の旧実行を照合し、構成変更の判断と試行の対応を残す。
単独利用の成功は、AUN/Kusabi連携と別機能の全工程を含む初版全体の完成条件を代替しない。

## 2. 接続の責任と情報

案件/判断/履歴の所有は既存境界案のまま。実行元の変換は接続部が担当し、工程判定をCLI別・AUN別に複製しない。
利用者はどちらの構成でも同じ窓口エージェントへ依頼・回答し、同じ工程表と履歴を確認する。AUNの有無だけを理由に、別コマンドでの開始や工程ごとの開始号令を求めない。
Shirubeが開始条件を照合した後、単独ならローカル実行側へ、連携ならAUNを通じて担当へ依頼する。返却の表現を接続部で変換し、同じ工程条件へ照合する。
依頼/受領/実開始/結果/工程合格の区別、認可の範囲、失敗/不明時の停止は共通。別担当への自動配送はAUN接続で追加される機能であり、単独でも同じ配送機能があるとはしない。

| 境界を通る情報 | 必要な意味 / 所有者 |
|---|---|
| 開始要求 | 案件/工程試行、要求・設計・対象repo/版、作業範囲/操作/環境、席と接続世代、判断/証拠参照。同じ試行を識別する再送キー。工程側が条件を所有 |
| 照合結果 | 対象と照合版、許可/拒否/不明の理由、必要な人の判断・解除条件。表示やLLMの返答で許可へ変換しない |
| 実行元参照 | 実行元の種類と版、元の実行識別子、席/接続世代。単独ならローカル実行、連携ならAUNの参照を使い、AUN IDを単独の必須項目にしない |
| 開始/終了の観測 | 接続部が観測した起動試行、プロセス/セッションとの対応、実操作の証拠、終了/切断、発生時刻と受領時刻。LLMの申告は別の入力 |
| 成果の照合 | 成果物の固定版、試験/独立監査/受入条件への証拠。工程側が実行報告を照合し、次工程/差戻し/待機を決める |

これは論理項目の一覧。通信型、制約、永続化の確定点、認証方法と契約版は境界/Unit確認後にSDS§5/6で固定する。
単独接続部は管理対象のCLI作業を開始/観測する最小限の処理とする。親依頼の配送網、複数席のタスクキュー、provider選択・費用回復を新設しない。

## 3. 共通の進行と接続先の違い（案）

1. 窓口で人が目的と必要な判断を伝える。対話の開始と、承認対象の変更作業の開始を区別する。
2. 窓口からの開始要求をShirubeが受け、保存記録とGitHubの公開本文/digest、現在の対象/席、必須監査・CIを照合する。
3. 条件を満たした同じ作業だけ実行側へ渡す。単独時はローカル接続、AUN接続時は担当への依頼を使い、両方で同じ開始条件を実行側の効果へ結ぶ。許可済み範囲での通常進行に人の開始号令を追加しない。
4. 実行の直前に対象変更/撤回/重複を再照合する。開始受付の保存と実開始を別々に観測し、CLIの起動・turn開始だけで変更作業が着手済みとはしない。
5. 単独時のCLI出力、またはAUNの実行報告を接続部で受け、終了結果と対象の差分/試験結果を同じ試行へ結ぶ。exit 0や「完成しました」だけで工程を完了しない。
6. 工程条件を満たせば現在地と次の作業を更新する。同じ管理対象で実行可能な許可済み作業を続け、必要な人の判断では一度通知して停止する。別担当への自動配送はAUNの範囲。

開始前にCLIへ対象の書込み権限や保護操作の資格情報を渡さない接続を検討する。対話用CLIが同じ対象へ別経路で書ける配置は、この拒否を保証できない。
実行プロセスが起動後に持つ権限、対象外の操作、MCP/ネットワーク経由の効果も契約へ含める。単なるwrapperや作業ディレクトリ指定を隔離と呼ばない。
管理対象の変更作業は、AUNの有無にかかわらずShirubeの開始照合を通す。これは機械的な実行経路の条件であり、人に新しい起動操作を毎回求める条件ではない。PC全体の任意CLI/シェルを管理できる保証とは分ける。

## 4. 失敗・停止・復旧で守る条件

| 場面 | 必要な動作 / 観測 |
|---|---|
| 未承認・対象違い・必須監査FAIL/UNKNOWN | 変更作業の実行へ渡さず、理由と解除条件を返す。人待ちは一度通知して停止 |
| GitHub/必須DB/照合処理が利用不能 | 新しい許可を出さない。記録できない完了を保存済みにしない。任意Onza UIの停止と区別 |
| 許可後の対象変更/撤回 | 許可を流用しない。開始直前の確定点と撤回の順序を契約化し、開始済み操作の中断可能性/残る効果を区別する |
| 同じ開始の並列要求・応答喪失 | 同じ試行に結び、実行有無が不明なら新規起動しない。保存済み受付だけで未実行とも開始済みとも断定しない |
| 実行中の切断・再起動 | 元の実行と実対象を照会して照合。不明のまま自動再実行しない。時刻欠損を推定値で補わない |
| hook無効・異常・対象外tool、CLIの直接起動 | 管理対象の効果が別経路から発生するかを実測。防げなければその配置の開始拒否は不合格とする |
| 終了報告と証拠の不一致・古い結果 | 未完/差戻しとして根拠を残す。別試行/別版への転用やAUN処理完了による工程合格を拒否 |

認証した本人回答の取得・転記、撤回の確定点、停止上限/timeout、保存と起動の部分成功、実行権限の隔離方式は未決。実装前に具体契約と試験を揃える。
人待ちでなくても連続非進捗の上限3回を保持し、状態変化がない同じ取得失敗を空回りさせない。

## 5. 実証と監査への接続

以下は試験計画で**全件NOT_RUN**。既存ST-01〜08へ追加の構成/観測を指定し、同じ要求の別台帳を作らない。

| 確認 | 実施と期待値 / 要求への対応 |
|---|---|
| 単独の正例 ST-01 | AUN/Kusabi/Onza UIを未接続にし、実GitHub・実DB・Codex CLIとClaude Codeを各々用いて許可範囲の変更開始→結果→工程確認を観測。起動時のAUN必須設定/通信がなく、必要な履歴を照会可能。AC-02/03、AH-01/06、WP-01/02 |
| 拒否 ST-02/03/04/08 | 未承認、範囲/主体違い、改変本文、必須不合格を注入。判定出力に加えて独立した開始観測と対象差分で、拒否対象の効果がないことを確認。正常時は同じ経路で開始可能。AC-06/07、AH-02 |
| 競合・再開 ST-05/07 | 撤回/対象変更と開始を競合させ、開始後に応答を失わせる。契約の順序・実行一意性・過去の承認/試行保持を照合。AH-03/04/05、WP-03/05 |
| 障害 ST-06 | GitHub/DB/照合処理/出力接続の障害を注入し、未許可開始・二重起動・保存済みの誤表示がない。復旧後に同じ対象で再照合。AH-05/07、WP-05 |
| 迂回・報告偽装 ST-04/08 | hook不在/異常・別tool経路・偽のLLM完了報告を試す。管理対象へ効果が出れば拒否保証は不合格、証拠不一致では工程未完。AC-06、WP-02 |
| AUNへ接続した構成 | 同じ工程の期待値をAUN参照で確認。通信断でローカル実行へ自動切替しない。実際の別担当開始まで観測して初めてAC-08の連携範囲を確認。全体AC-09/10も残す |
| 共通する操作・判定 | 同じ要求/判断/試験証拠を両構成へ与え、同じ開始可否・工程合否・必要な人の判断・履歴の意味になることを確認。利用者に接続先ごとの開始号令を要求しない。提供機能/待ち時間/実行元参照の差は区別する。AC-03/06/08、AH-01、WP-02/03 |

作者が実装/試験証拠を作り、別の監査席が[SDS監査方法](../sds/audit-method.md)の設計D1〜D6・実装/試験・実環境の該当項目を固定して確認し、人が実利用を受け入れる。
実行前に版、隔離対象、席、費用/回数、停止・復旧方法と実操作の観測手段を確定する。mock・help・文書の確認は実接続の成功に数えない。

## 6. CLIの確認事実と残る技術設計

2026-10-04の読取り確認: ローカル`codex-cli 0.144.2`の`exec --help`に`--json`/`--sandbox`、`Claude Code 2.1.281`の`--help`に`--print`/`--output-format stream-json`がある。モデル処理は実行していない。
[Codex非対話実行](https://learn.chatgpt.com/docs/non-interactive-mode)と[Claude Codeの非対話実行](https://code.claude.com/docs/en/headless)は構造化出力を説明する。取り込みの候補であり、本人承認や開始拒否をそれだけで保証しない。
[Codex hooks](https://learn.chatgpt.com/docs/hooks)のMCP tool hooksはエラー/接続先不在を操作拒否にしないと説明する。hookを唯一の拒否境界にしない根拠で、当該版の実機試験結果ではない。CLI資料は接続可否の入力で、SDSの原典追加ではない。

先のS-A/S-Bを「単体だけの使い方の選択」として提示した質問と推奨は作者が撤回する。AUNの有無と、CLIのどこへ開始照合を接続するかを混同していた。
開始処理側へ照合を接続する方式、既存セッションの操作前へ接続する方式などは、共通の利用体験を満たす技術候補として比較する。AUN接続時も実行側の拒否が必要で、AUN導入だけで解決したとはしない。
どちらも操作の迂回・hook障害・権限分離を実証する必要がある。型/API、既存セッションの継続方法、導入設定、実行権限の分離は未選定。利用方法に実際の制約が出る場合に、その根拠と代替案を具体化して人へ示す。

内部責任は後続のOwner回答によりAを採択済み（[採択参照](shirube-v1-responsibility-and-data.md)）。AUN有無の質問やこの採択を、CLIの技術方式の選択へ拡張しない。
内部境界の確認→Unit/短い反復→必要な正式契約/詳細設計→独立監査→実装・試験へ接続する。新たなDB/CLI設定・常駐実行器をこの文書で導入しない。
