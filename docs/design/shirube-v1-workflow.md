## 2. 席、窓口、機械制御

- 人の窓口はrepoごとに一つ。窓口は状況を説明し、選択肢・根拠・影響を示し、回答を対応する判断へ結ぶ。
- 工程担当は成果物を作る。工程を進める許可や独立監査の判定を、自分の「完了」報告から発行しない。
- Shirubeの工程制御は、採択済み工程条件と現在の証拠から次に実行可能な作業を返す。人への質問が不要なら通常の引継ぎを続ける。
- aunは配送・処理報告、kusabiは文脈復元を担う。Shirubeが同機能や他製品の状態を別の書き手として再実装しない。
- 共通の席/主体/接続はOnza正本を参照する。役割の配置と今回の工程条件はShirubeの情報。cwdやmodel名を認証に使わない。
- 同じ席のLLM交代後も作者履歴を保持する。役割ラベルを変えるだけで独立監査者にしない。

今回の作者はcodex-adf、判断者はOwner。既存監査席devauditor、merge引渡し先suite-leadは既存経路を維持するが、本設計の監査受領/実着手は未確認。
将来の製品導入先の実席割当は未確定。設計質問への回答前に席を起動・設定変更しない。席不足を理由に作者が独立判定を代行しない。

## 4. 最初の実証の順序と状態

対象は採択済みの「要求・承認と作業開始の照合」。LLM起動そのものと、承認対象の変更作業の開始を区別する。未承認の間も目的を説明・対話できる必要がある。

1. 窓口が要求/設計、repo/対象版、工程、担当席、操作範囲、実行環境、必要証拠を一つの開始要求へ結ぶ。
2. 工程制御が公開判断の出所/有効範囲、対象版、席と実接続、必須証拠を照合する。未回答は人待ち、取得不能は不明として区別する。
3. 確認済みの場合だけ、同じ対象へ結びつく開始指示を発行する。指示の発行だけでは実開始にしない。
4. 実行側が操作の直前に、対象/条件の変更・失効・同じ試行の既存実行を照合する。判定と実行の競合を契約の確定点で扱う。
5. 実開始の観測を対象作業へ結ぶ。応答喪失なら照会して確かめ、未確認のまま新しい試行を開始しない。
6. 作業の返却後、成果物と終了条件を照合する。成立なら次へ、不成立なら根拠と修正先へ戻す。全体完成への昇格は各工程と親受入の条件を満たす時だけ。

| 状況 | 次の動き | 自動で行わないこと |
|---|---|---|
| 必要な判断がない | 一度だけ質問を提示して待つ | 無回答の採択、同じ質問/hold記録の反復 |
| 対象違い・必須FAIL | 理由と是正先を返す | 一般承認で免除、期待値や対象の縮小 |
| 証拠/開始結果が不明 | 必要な取得・照会の条件を返す | UNKNOWNをFAILや成功へ変換、別IDでの再実行 |
| 有効な条件が揃った | 同じ範囲の作業を開始し、実開始を確認 | 新たな開始号令を要求、範囲外の操作追加 |
| 必須の終了条件が揃った | 次担当/次作業へ引き継ぐ | LLMの最終返答だけで工程/全案件完了 |
| 対象/設計が変更された | 影響条件と証拠を無効化し、該当工程へ戻す | 古い承認・監査を別の対象へ流用 |

人待ちでは即停止。自動処理の連続非進捗上限は既存規則の3回を継承し、同じ失敗を無意味に再実行しない。タイムアウト・通信/操作別の予算・期限は実行契約で固定し、未指定で無制限に回さない。

## 5. CLI接続の調査結果と、確認する利用体験 DQ-02

2026-10-03にローカルのread-only確認で `codex-cli 0.144.2` / `Claude Code 2.1.281` を観測した。ヘルプ/版の読取りだけで、設定変更・新しいLLM実行・実機試験は行っていない。
公式文書は可変の現行版であり、インストール版の実挙動を証明しない。採用前に同じCLI/設定で正常・拒否・故障を実測する。

| 確認した事実 | 設計への意味 |
|---|---|
| [Codex Hooks](https://learn.chatgpt.com/docs/hooks)のPreToolUseは明示的なdenyを返せる。非管理hookは信頼確認が必要。未対応の返却形等では処理が続く場合がある | hookを置くだけで検査不能時の拒否が保証されたとしない。起動/有効設定・対応tool・故障時まで実測する |
| [Claude Hooks](https://code.claude.com/docs/en/hooks)もdenyを返せるが、hook起動失敗・不正応答等が非blockingになる条件を持つ | hookだけを唯一の認可境界にしない。失敗しても変更できない実行側の権限制御が必要 |
| [Codex App Server](https://learn.chatgpt.com/docs/app-server#mcp-server-elicitation-requests)と[Claude MCP](https://code.claude.com/docs/en/mcp#respond-to-mcp-elicitation-requests)は、MCPからhostへ構造化した質問を提示し回答を返す仕組みを説明している | 人の回答をLLMの転記と分けて受け取る候補。APIの存在だけで実CLI対応・本人性を成立させない |
| Claudeの公式資料にはelicitationへ自動応答するhookもある。Codex App Serverは接続clientから回答を受ける | acceptという値だけでは本人回答の証明にならない。許可した人向けclient、設定、回答経路、対象/質問の版を確認する必要がある |

**DQ-02 提案: 普段は窓口との会話を続け、結果を変える判断・承認の時だけCLI内の確認欄で本人が確定する。**
画面を別に開いてGitHubを操作する方式にはしない。表示内容はShirubeが対象から生成し、LLMが独自の承認文へ差し替えない。

表示例（説明用。実際の承認要求ではない）:
```text
対象: watchout/shirube / 最初の実証の設計 / 対象版
今回決めること: 提示した方式Aを採用する
許可する範囲: この設計版に記載した作業
含まれないこと: 別方式・別対象への変更
選択: 承認する / 修正を求める / 今は決めない
```

回答は質問ID・対象版・人向け接続へ結び、GitHubへ公開して本文を読戻す。無回答・取消・送信失敗は承認にしない。有効な既存判断の範囲内の通常作業で再びこの欄を出さない。
利点は確認対象と回答の結合、LLM転記の排除、同じ窓口の維持。導入負担はMCP/hostの接続設定と、本人回答経路・自動回答設定の検証。
比較案は自然文の「はい」をhost入力の出所つきで採る方式。自然な会話を保てるが、人の入力とaun等から来た入力の識別、どの質問への回答か、対象変更後の回答の扱いを別途実証する必要がある。promptやsession IDだけでは代用しない。
Ownerの回答: **未回答**。方式の同意は現在の稼働席の設定変更認可とは分け、導入内容と切戻しを具体化して扱う。

実行側では、モデルが判定を経ず対象を書き換えたり、制御設定/承認記録を変えたりできない権限境界が必要。
既存のsandbox・管理設定・実行入口の利用を先に比較し、汎用のshell/通信実行器をShirubeに再実装する決定にはしない。native tool/MCP/通信先を含む迂回経路と故障時の挙動を確認できるまでは、開始拒否の実効性はNOT_RUN。

## 6. 開発単位・観測・監査への引継ぎ

最初の反復は「実GitHubの固定要求/判断 → 対象との照合 → 実CLIの対象操作の許可/拒否 → 開始証拠」を一続きにする案。判定器だけの完成をBolt完了にしない。
その後の自動引継ぎ、kusabi再開、別機能での全工程再現は初版の受入として残る。後続の順序と第二の機能は未採択。

- 開始照合のST-01〜08は[既存の試験案](shirube-v1-design-questions.md)§5を同じ意味で継承する。正常は実操作を観測し、拒否は対象への効果0を観測する。
- 追加の接続確認: hook無効/起動失敗/不正応答/時間切れでも未許可操作が実行されないこと、人の回答を偽装したtool引数・aun本文・自動回答を承認にしないこと。全件NOT_RUN。
- 正例と負例を同じCLI/対象repo/設定版で実行する。作者が操作とGitHub/実行側の記録を収集し、独立担当が照合し、Ownerが実利用を確認する案。将来の担当割当完了とはしない。
- 観測期間は一回の実証の開始から終了/停止までとする案。通常の作業待ち、人の判断待ち、修正、再実行を区別する。速度短縮率は未測定のまま保持する。
- 原典AI-03/04/06/07は2026-10-03再取得し、既存source-lockのbytes/hashと一致。具体API、権限方式、共通型、競合の確定点、保存/復旧、費用/予算は未決であり実装可能な契約が完成したとはしない。

本案の親受入への対応: AC-01/AC-05=固定正本と共通参照、AC-02=要求/判断/対象固定、AC-03/AC-08=全工程表と引継ぎ、AC-04=既存検査と責任の重複回避、AC-06=正負/故障時拒否、AC-07=変更時の無効化/回帰、AC-09=統合と実環境受入、AC-10=別機能での再現。
技術方式を選定し、情報所有・機械可読の契約・状態/競合・検証計画が揃った版を、既存の固定項目＋機械照合＋独立判断で監査する。現時点で独立設計監査の依頼や実装許可は発行していない。
