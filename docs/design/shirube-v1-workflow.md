## 2. 席、窓口、機械制御

- 人の窓口はrepoごとに一つ。窓口は状況を説明し、選択肢・根拠・影響を示し、回答を対応する判断へ結ぶ。
- 工程担当は成果物を作る。工程を進める許可や独立監査の判定を、自分の「完了」報告から発行しない。
- Shirubeの工程制御は、採択済み工程条件と現在の証拠から次に実行可能な作業を返す。人への質問が不要なら通常の引継ぎを続ける。
- aunは配送・処理報告、kusabiは文脈復元を担う。Shirubeが同機能や他製品の状態を別の書き手として再実装しない。
- 共通の席/主体/接続はOnza正本を参照する。役割の配置と今回の工程条件はShirubeの情報。cwdやmodel名を認証に使わない。
- 同じ席のLLM交代後も作者履歴を保持する。役割ラベルを変えるだけで独立監査者にしない。

## 4. 最初の実証の順序と状態

対象は採択済みの「要求・承認と作業開始の照合」。LLM起動そのものと、承認対象の変更作業の開始を区別する。未承認の間も目的を説明・対話できる必要がある。

1. 窓口が要求/設計、repo/対象版、工程、担当席、操作範囲、実行環境、必要証拠を一つの開始要求へ結ぶ。
2. 工程制御が公開判断の出所/有効範囲、対象版、席と実接続、必須証拠を照合する。未回答は人待ち、取得不能は不明として区別する。
3. 確認済みの場合だけ、同じ対象へ結びつく開始指示を発行する。指示の発行だけでは実開始にしない。
4. 実行側が操作の直前に、対象/条件の変更・失効・同じ試行の既存実行を照合する。判定と実行の競合を契約の確定点で扱う。
5. 実開始の観測を対象作業へ結ぶ。応答喪失なら照会して確かめ、未確認のまま新しい試行を開始しない。
6. 作業の返却後、成果物と終了条件を照合する。成立なら次へ、不成立なら根拠と修正先へ戻す。全体完成への昇格は各工程と親受入の条件を満たす時だけ。

| 状況 | 次の動き | 自動で行わないこと |
|---|---|---|
| 必要な判断がない | 一度だけ質問を提示して待つ | 無回答の採択、同じ質問/hold記録の反復 |
| 対象違い・必須FAIL | 理由と是正先を返す | 一般承認で免除、期待値や対象の縮小 |
| 証拠/開始結果が不明 | 必要な取得・照会の条件を返す | UNKNOWNをFAILや成功へ変換、別IDでの再実行 |
| 有効な条件が揃った | 同じ範囲の作業を開始し、実開始を確認 | 新たな開始号令を要求、範囲外の操作追加 |
| 必須の終了条件が揃った | 次担当/次作業へ引き継ぐ | LLMの最終返答だけで工程/全案件完了 |
| 対象/設計が変更された | 影響条件と証拠を無効化し、該当工程へ戻す | 古い承認・監査を別の対象へ流用 |

人待ちでは即停止。自動処理の連続非進捗上限は既存規則の3回を継承し、同じ失敗を無意味に再実行しない。タイムアウト・通信/操作別の予算・期限は実行契約で固定し、未指定で無制限に回さない。

## 5. 窓口に依存しない確認方式 DQ-02

2026-10-03にローカルのread-only確認で `codex-cli 0.144.2` / `Claude Code 2.1.281` を観測した。ヘルプ/版の読取りだけで、設定変更・新しいLLM実行・実機試験は行っていない。
公式文書は可変の現行版であり、インストール版の実挙動を証明しない。採用前に同じCLI/設定で正常・拒否・故障を実測する。

| 確認した事実 | 設計への意味 |
|---|---|
| [Codex Hooks](https://learn.chatgpt.com/docs/hooks)のPreToolUseは明示的なdenyを返せる。非管理hookは信頼確認が必要。未対応の返却形等では処理が続く場合がある | hookを置くだけで検査不能時の拒否が保証されたとしない。起動/有効設定・対応tool・故障時まで実測する |
| [Claude Hooks](https://code.claude.com/docs/en/hooks)もdenyを返せるが、hook起動失敗・不正応答等が非blockingになる条件を持つ | hookだけを唯一の認可境界にしない。失敗しても変更できない実行側の権限制御が必要 |
| [Codex App Server](https://learn.chatgpt.com/docs/app-server#mcp-server-elicitation-requests)と[Claude MCP](https://code.claude.com/docs/en/mcp#respond-to-mcp-elicitation-requests)は、MCPからhostへ構造化した質問を提示し回答を返す仕組みを説明している | 人の回答をLLMの転記と分けて受け取る候補。APIの存在だけで実CLI対応・本人性を成立させない |
| Claudeの公式資料にはelicitationへ自動応答するhookもある。Codex App Serverは接続clientから回答を受ける | acceptという値だけでは本人回答の証明にならない。許可した人向けclient、設定、回答経路、対象/質問の版を確認する必要がある |

**DQ-02: 確認欄方式を基本とし、非対応の外部窓口では会話で確認する。同じ判断要求へ回答できることが条件で、連動の実証は未完。**
普段は窓口との会話を続け、結果を変える判断・承認の時に本人が確定する。最初はCLI、外部窓口では表示能力に応じてボタン/選択欄または会話で同じ情報を提示する。
画面を別に開いてGitHubを操作する方式にはしない。表示内容はShirubeが対象から生成し、LLMが独自の承認文へ差し替えない。CLIの画面やMCPの応答待ちを判断の正本にしない。

今回の同意は外部連動を成立条件とする。方式への同意、条件充足の実証、稼働席/外部サービスの設定変更は区別し、導入内容と切戻しを具体化して扱う。

### 5.1 共通の判断要求と、窓口の表示

| 利用する窓口 | 利用者が見るもの | Shirubeへ戻す意味 |
|---|---|---|
| Codex / Claude Code | 会話中の確認欄 | 同じ要求・対象版に対する本人の選択 |
| Onza | 対象を示す確認画面 | 同上。判断条件をUI側で再定義しない |
| Discord等 | 対象と範囲の説明＋承認/修正/保留ボタンや選択欄 | 同上。認証したサービス利用者を案件の判断者へ照合 |
| 確認欄/ボタンに非対応の外部窓口 | 同じ対象と範囲・選択肢を会話で提示し、返信で確認 | 同上。本人と返信先の要求を確認し、曖昧な返答は確定しない |

共通契約の案は「判断要求の参照と版、対象/範囲のdigest、許された選択肢、回答者の権限、有効性条件」と「確認した回答者/出所、要求の版、選択、配送重複を識別する参照」を結ぶ。
Shirubeが判断の意味・一度だけの確定・公開後の工程への適用を所有し、各接続部が表示と出所の確認を担う。サービス利用者と人の対応を表示名から推定しない。共通の本人対応を新しいDB型としてここで独自に追加しない。
配送/回答の経路はaun、Onza等の提供側と契約を確認する。現在のaun通信契約はtext中心の案で、構造化した確認への対応は未確定。Shirubeの中にDiscord botや汎用通信機能を重複実装する判断ではない。

Discordでは[ボタンのcustom_id](https://docs.discord.com/developers/components/reference#button)と[操作した利用者・元message等を含むInteraction](https://docs.discord.com/developers/interactions/receiving-and-responding)を使う接続が可能。送信専用Webhookへ文章を投稿するだけでは回答経路にならない。
HTTP受信を選ぶ場合は[Discordの署名検証](https://docs.discord.com/developers/interactions/overview#validating-security-request-headers)を行い、案件の回答権限も別に照合する。custom_idや署名が正しいだけでは承認者とは認定しない。Gateway/HTTPの方式選定・資格情報配置は未決。
Discordはクリック等のイベントへの初期応答に3秒、応答tokenに15分の制約がある。受信への応答とGitHub公開を分け、これを人の判断期限にしない。CLI/MCPの切断や通信期限も、無回答の承認や判断の消滅へ変換しない。

### 5.2 外部で回答した後の進行

1. Shirubeが同じ判断要求を保持し、有効な版を指定先の窓口へ表示する。公開可能な対象情報だけを送り、秘密や無関係な会話を転送しない。
2. 接続部が回答者と出所を確認し、同じ要求への回答として返す。LLMにボタンの意味を再解釈させたり、CLIのキー操作を代行させたりしない。
3. Shirubeが現在の対象/回答権限/要求版を再照合し、未確定であることを条件に一つの回答を確定する。重複は同じ結果を返す。競合・古い回答は上書きせず確定済み/対象変更を示す。
4. GitHubへ公開・読戻しし、有効な判断を工程へ渡す。公開失敗/応答喪失は未完として照会・回復し、重複投稿や作業開始へ飛ばさない。
5. ほかの窓口へ確定結果を反映し、古い選択を無効にする。外部回答後にCLIで再承認を求めない。表示更新が遅れても、サーバー側は二回目の確定を拒否する。
6. 次作業へ進める条件が揃えば再開し、実開始を確認する。CLIの確認ダイアログが開いたままの時の取消/終了・中断後の再照合も接続試験へ含める。ダイアログを閉じられず人の再操作が必要な状態は、連動成功にしない。

**共通で行う受入（全件NOT_RUN）**: CLIと外部窓口で同じ結果になる、外部回答でCLIの二重承認なしに再開する、両窓口の同時/重複回答が二重実行を起こさない、古い版/期限切れ/無権限を拒否する、GitHub障害中は開始しない、切断/再起動後も同じ要求と結果へ復帰する。
公式APIの確認は実現可能性の材料で、製品での連動完了ではない。まず共通契約をCLIから使い、Onza/チャット追加時も同じ適合試験と実機受入を通す。今回Discord導入を初版へ一括追加したり、既存サービスへ接続・送信したりしない。

### 5.3 非対応窓口での会話確認

- 確認欄/ボタンに非対応なら、同じ要求の対象版・判断内容・許可範囲・選択肢を文章で提示する。確認待ち中の切替でも要求を新規発行しない。
- 返信先messageや明示した要求参照と、検証した送信者を使い、有効な一つの質問へ回答を結ぶ。引用・転送・bot/LLMの出力を本人回答にしない。具体的な回答語彙・入力形式は接続契約で定める。
- 例: 「確認Q-17: この対象版と範囲を承認しますか。承認/修正/保留を返信してください」→同じ確認への本人の「承認」。Q-17は説明用で、ID仕様の決定ではない。
- 返答先が一意で契約上の明示回答なら、短い回答で確定できる。曖昧な「はい」、複数質問への回答、条件付き同意・範囲変更は、確認する対象と意味を整理して本人へ返す。LLMの推測や条件の省略で承認へ昇格させない。
- 本人/返信先を検証できないサービスでは、確認可能な窓口への案内を一度出して待つ。認証/権限の失敗を会話への切替で回避しない。無回答は承認にしない。
- 確定前の対象照合、GitHub公開/読戻し、重複/古い回答の処理、外部回答後のCLI再承認なしの進行は§5.2を使う。会話形式だけの別承認規則は作らない。

**会話確認の受入（全件NOT_RUN）**: 正常な返信で一度だけ進行、曖昧/条件付き回答では未確定、複数要求の取り違え・引用/偽装・旧版回答は開始効果0、表示方式の切替前後の重複回答も一度だけ確定する。応答本文と送信者・返信先・対象版・公開結果を照合し、LLMの「承認済み」報告を証拠に代えない。

Bolt完了はその反復で約束した範囲と実演の成立。未実施の要求や後続Unitを製品完成へ繰り上げない。共通工程の実績も重複加算しない。

### 7.5 検証への対応と次の設計

以下は実装時に実行する観測条件。現時点は全件NOT_RUNで、文書やCIの成功を実動作の成功にしない。

| 入力・操作 | 期待する観測 | 要求 |
|---|---|---|
| 一つのUnitを二反復で進め、初回だけ完了 | 初回の成果とUnitの未実施要求を両方表示し、案件完成にならない | WP-01/06、AC-09/10 |
| 複数Unitが同じ設計/横断試験を参照 | 同じ作業/証拠を辿れ、二重実行・二重計上せず、各Unitの残条件を保持 | WP-01/05/06 |
| 実装終了報告はあるが監査未達、または親受入未実施 | 終了・確認・利用可能を区別し、未達条件と次担当を表示 | WP-02/06、AC-06/09 |
| 計画改訂で分割・交代・差戻しが発生 | 元計画/試行/作者と変更理由・判断、新対象と再確認範囲を往復して辿れる | WP-01/03/04、AH-03/04 |
| ACKだけ、開始時刻欠損、遅着/重複、再起動が発生 | 証拠がない実開始/完了を補作せず、同じ試行を照合。区間不明と鮮度を表示 | WP-02/05、AH-04/05 |
| 独立した並列作業、実行/人待ち/手戻りがある | 案件経過と各区間を区別し、加算による時間の過大計上や人待ちの空実行がない | WP-03/05 |
| Onza停止中にCLIで現在地を照会、条件が揃った通常作業を再開 | 保存/照会が成立し、次と残条件が分かり、新たな開始号令は不要。権限不明の操作は始めない | WP-03/05/06、AH-06、AC-03/08 |

設計の次の入力は§3の情報所有と§4/5の開始照合。確定すべき契約は、実開始/終了の観測元と真正性、保存/公開/実行の確定点、重複/遅着/競合/復旧、本人/閲覧権限、保持/削除、共通型/具体API。
個別Unitの境界と依存はこれらの責任/契約から具体化し、価値/範囲/方式が変わる選択は人へ返す。未決を隠して「工程表の粒度を選んだから実装できる」としない。
独立設計監査へ渡す時は、この節と最初の実証・外部契約を同じ対象版で示す。要求監査の8項目PASSは本設計のPASSではない。
