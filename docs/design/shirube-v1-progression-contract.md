## 1. 所有する入力と出力

以下は技術非依存の論理型。共通参照の文字列形式や物理schemaを規定しない。必須情報の欠落はUNKNOWNとし、空文字・既定値で埋めない。actor/seat/scope/bindingはOnzaの契約へ結ぶ不透明な参照で、Shirubeが発行・自己申告検証しない。

| 論理記録 / 更新責任 | 必須の内容・参照・一意性 |
|---|---|
| Work / 案件の進行 | 案件・作業の安定参照、計画版、repo/対象版、範囲/操作/環境、担当席/必要な独立性、前提/終了/親受入の条件。条件の出典・版・確認方法/担当と、未決の影響範囲を§2.1で結ぶ。範囲変更は新計画版。1作業に複数の試行を許す |
| Attempt / 案件の進行 | 作業参照・試行参照、開始時の入力版、当時の判断/証拠、予定担当と実担当、実行元参照、各実績時刻、条件ごとの照合と集約した確認結果（§2.1）。手戻りは元試行を参照する別試行。未解決の同一実行を新試行へ偽装しない |
| Decision / 人の判断と履歴 | 判断要求/提示版、本人回答原文/選択、本人と記録者、対象/範囲/条件、公開本文とURL/digest、照合時点、訂正/失効/後継。工程の状態を直接更新しない |
| Observation / 元発行者→案件の進行 | 出所・対象版・試行/実行参照、検査/契約版、発生時刻と受信時刻、結果と証拠。一つの元報告の重複は再適用しない。時刻不明は不明のまま |
| NextAction / 案件の進行 | 原因の確認記録、対象作業/試行/計画版、動作種別、次担当、入力/成果/解除条件、実行先、適用する期限/再試行上限、処理状況。工程試行に結ぶ次行動で、AUNの独立したタスク台帳を複製しない |

NextActionの種別は`start / stop / verify / reconcile / ask_human / repair / accept`。同じ原因・対象・動作に対する継続処理は一件として扱い、再受領で新規起動しない。`stop`は既存実行の後続効果を抑止する論理操作で、共通管理の失効操作やOSのkill方式そのものではない。物理キー/排他方式は未決。
LLMは成果物・候補・説明を返す。入力の真正性、開始許可、条件の合否、次行動の登録/実行状態を文章だけで更新できない。参照のhash一致だけを内容の合格にしない。

## 2. 開始の判定と判断履歴

開始条件は、①現在の計画/対象/範囲一致、②必要な判断の本人性・公開・有効性、③現在の席/権限/独立性、④必要な前提/検査のPASS、⑤必要な保存と既存実行の照合、の全成立。①〜⑤の照合元/時点を開始要求へ結ぶ。真偽はモデルの自己申告から取得しない。
判定の出力は次の区分と具体的な原因一覧。複数の未充足があればすべて保持し、REJECTED→UNRESOLVED→HUMAN_REQUIREDの順で代表区分を表示する。まだ人へ提示/回答していないこと自体は取得障害ではなくHUMAN_REQUIRED。ELIGIBLEは未充足0の場合だけ。許可候補を実行権限そのものにせず、実行直前に§4の接続が再照合する。

| 判定 | 条件 / 次行動 |
|---|---|
| ELIGIBLE | 全条件成立。既存の判断範囲内なら新たな開始質問を作らず、同じ対象の開始処理へ渡す |
| HUMAN_REQUIRED | 計画/契約上必要な本人の判断が未確定。質問と提示版を一度作り、その判断待ちの処理を停止 |
| REJECTED | 対象違い・明示失効・無権限・必須FAIL。根拠と是正先を返す。一般承認で免除しない |
| UNRESOLVED | 取得不能・未公開・欠損・現在性不明・既存実行不明。既知の事実を保持し、原因に対応する照会/復旧へ結ぶ |

本人回答の取得、GitHub公開、現在の適用可否は別の事実。回答取得後も公開/読戻し未確認なら開始不可。条件付き回答は条件を評価できた範囲だけへ適用し、自由文の曖昧さをLLMが承認へ正規化しない。
CF-AUTH-01 Aの回答は、Shirubeの保護された画面で提示版/選択/範囲と本人確認証拠へ結ぶ。代理保存serviceと回答humanを別に保持する。共通の`resolve_actor`/`read_principal`のsnapshotだけでは本人の回答にしない。本人確認後も公開/読戻しと現在条件の照合を必要とする。
回答訂正・撤回・対象変更は先行記録を消さず、現在の適用可否を更新する。並行する回答の意味や順序を確定できなければ競合として停止し、最後に受信した回答を自動採用しない。
拒否/保留の記録も当時の提示→回答→公開/照合→適用先から逆引きできる。公開先本文の編集/削除や読取不能では、過去の写しを表示できても現在の許可にしない。

### 2.1 既存の工程条件を、今回の成果・証拠へ照合する

[採択済みSDS手順](../process/ai-dlc.md)§1〜8には出力と完了確認の条件がある。適用する節と順序は同手順§1/9に従う。Shirubeはそれらと採択要件をWorkの条件へ結び、Attemptの確認記録を根拠に状態を更新する。規格の写し、独立した完了台帳、工程ごとの一律な追加承認は作らない。

| 照合の入力/記録 | 必須の対応 |
|---|---|
| 確認する条件の集合 | 計画版・作業/対象範囲、出典の版/節/条件参照、必要な出力と終了条件、確認方法と確認担当。当該作業の開始条件として固定する。規格の出力/終了条件と採択要件への対応を残す |
| 条件ごとの成果と証拠 | 今回の成果物/観測の参照と固定版、対象作業/試行、元発行者、確認に使った検査/監査/判断の版・結果・根拠・確認者・確認時点。ファイル存在やURL/hash一致だけで条件の意味を満たしたとしない |
| 条件ごとの判定 | PASS/FAIL/UNKNOWN/NOT_RUNを区別。照合していない条件はNOT_RUN、照合に必要な証拠を取得/検証できない条件はUNKNOWN。作者の「済み」や自由な真偽値でPASSへ更新しない |
| 未決と後続作業 | 未決の内容/担当/解除条件、影響する対象・判断・作業、独立して進める範囲とその根拠。影響を判定できない候補作業は独立扱いしない。計画や判断を変える選択は人へ返す |

機械は、固定した条件集合に対して全件の照合記録が揃うこと、対象/版/出所/必要な確認担当と結果の対応を確認する。検査を実行した証拠、必要な独立内容監査、人の判断は各々の正当な発行元へ結ぶ。文書の意味・十分性をhashや文字列検索で判定できるとはしない。内容の確認は計画と既存リスク規則で指定された確認者が行い、必要な独立性を作者の完了報告で代用しない。全工程へ新しい独立監査義務を一律追加する規定ではない。

進行側は保存した条件別照合を集約し、当該範囲の必須条件がすべてPASSの場合だけ確認済みとする。空の条件集合、照合記録の欠落/重複、対象外証拠や別版のPASSの混入で全件一致にはしない。重複する元報告の再受信は一度の適用に収束させる。条件の省略/適用外はSDS§1/9の理由・範囲・確認者へ結び、必要な判断の公開根拠を検査する。完了時にLLMが条件集合を減らす、未決を適用外へ移す、分母を縮めて合格させる更新は受理しない。正当な条件変更は計画を改版し、影響する照合をやり直す。

本人との対話の保存と、目的/要求を本人が確認したことは別条件である。SDS§2で数値が未測定の場合も、未測定の表示・担当・測り方・期間という必要事項を照合する。測定計画が揃っても実測値や§8の効果確認をPASSにしない。後工程へ影響する未決が残る場合、独立範囲の確認記録だけで上流全体をVERIFIEDへ昇格させない。現在計画に明示された独立作業は、その作業自身の開始条件が揃えば進められる。

完了の直接設定や前工程の確認を迂回する操作を、LLMの通常入力として受理しない。§3のVERIFIEDと§5の次行動は、この同じ条件別照合を参照する。開始直前にも対象/計画/判断と参照した確認結果の現在性を再照合し、保存/読取り不能・変更・失効を以前のPASSで埋めない。照合記録の保存と状態/次行動が食い違う中間状態を許可として返さない。具体的な保存/排他は既存の同一TX契約へ接続する。

工程検討のために起動済みのCLIも、別工程や範囲外の変更作業にその許可を流用できない。[単独実行接続](shirube-v1-standalone-execution.md)§3の操作境界で拒否を実証する。既に不正な先行実装が発生していた場合は実開始/差分の事実を消さず、条件未成立と逸脱を記録し、後続効果の抑止と既存の停止/照合へ結ぶ。先行した実装や監査を上流条件の代替にせず、無断rollbackや追認も行わない。

## 3. 試行の状態と、事実を消さない遷移

工程状態と「次の効果を起こせるか」を分ける。停止理由は状態を上書きする単一のBLOCKEDではなく、該当する作業/試行へ結ぶ。既に観測した実開始を、後の認可失効で未着手へ戻さない。

| 状態 | 入るための事実 | 次へ進む条件 |
|---|---|---|
| PLANNED | 現在の計画に作業がある | 開始判定と保存が成立するとSTART_REQUESTED。まだ動いた証拠ではない |
| START_REQUESTED | 対象/試行へ結ぶ開始要求と次行動を永続記録した | 実行側への送付/ACKだけでは留まる。有効な実開始観測でRUNNING |
| RUNNING | 検証済み実行元が同じ試行/対象の開始を示した | 結果返却を対応づけてRESULT_RECEIVED。終了コード0だけで合格にしない |
| RESULT_RECEIVED | 成果/実行結果が対象と結びつく | 終了条件の照合へVERIFYING。開始証拠が遅着した場合も順序を補作せず、欠損を残す |
| VERIFYING | 必要な試験/監査/受入条件と元証拠を確認中 | §2.1の全必須条件PASSならVERIFIED。必須FAILならRETURNED、NOT_RUNは検査待ち、UNKNOWNは照会待ち |
| VERIFIED | 対象範囲の終了条件を満たす確認記録がある | 次の対象作業を評価する。全案件の受入は別条件で判定 |
| RETURNED | 不合格の根拠と修正先が特定された | 合意範囲内の修正は後継試行へ。新しい方式/範囲選択が必要なら人へ |
| CANCELLED | 中止が有効に決まり、実行の停止/未開始が確認できた | 履歴は保持。取消要求だけでは入らず、未確認の実行を照合する |

順序逆転・重複報告は元発行者の識別と対象/版で整合を確認し、状態を逆戻りさせない。終了が先に届いても開始時刻を終了時刻から作らない。矛盾する報告は保留し、後着を無条件に正としない。
計画改訂は旧計画/試行を保持し、変更で無効になった現在条件と証拠を識別する。旧版でのVERIFIEDは歴史的な事実として残し、新版が完了したという表示へ流用しない。

## 4. 境界ごとの論理操作と整合

| 提供側→利用側 / 操作 | 入力→出力と、失敗時の意味 |
|---|---|
| 判断と履歴→案件の進行 / 適用照合 | 固定した判断要求・Work対象→公開本文/版/出所と適用可否。照合不能はUNRESOLVED。人の回答そのものを書き換えない |
| 案件の進行→実行アダプタ / 開始 | 同一試行の要求、対象/許可範囲、実行元の照合用参照→受付/拒否/不明。その後の実開始・終了観測は別に返す |
| 案件の進行→実行アダプタ / 停止 | `stop`の一意な要求参照、案件/scope・元試行/実行・世代、撤回/停止の根拠、現在の要求主体と停止権限、対象効果範囲→受付/拒否/停止不能/応答不明。受付と実効停止の証拠を区別し、詳細は§4.1 |
| 実行アダプタ→案件の進行 / 照会・観測 | 元の開始/停止要求と実行参照→要求の受付状態と、未開始/実行中/停止確認/終了/不明を別々に返す。発行元と対象効果範囲の証拠を照合。「見つからない」が未開始/未受付の証明になる条件は提供側契約で固定 |
| 検査/監査/人の受入→案件の進行 / 確認 | 対象版・要求条件・発行元・結果→当該条件への照合。未完の受入をCLI終了・CI成功で置換しない |
| 案件の進行→同じ情報の照会 / 現在地 | 権限付き案件/版→各状態、最終確認時点、残条件、次行動/担当。閲覧権限外の本文/件数を返さない |

全操作は論理契約版・対象・原因となる入力参照を持つ。物理API/JSON Schema/共通型は§8で確定し、意味を変える追加・列挙値は利用側への影響を確認する。契約不一致や不明な状態値を成功へ既定化しない。
次を実装上の必須整合条件とする設計案。具体的なtransaction/記録方式はまだ採択していない。

- 実効果の前に開始要求と判断適用を耐久保存する。前工程の確認後に停止しても、未実行の次行動を回復できること。確認済みと次行動が食い違う中間状態を成功として外へ返さない。
- 同じ試行の同時開始は一件へ収束させる。Shirubeの記録排他だけで外部の効果一意性を保証せず、実行側の同一要求照会/重複抑止と組み合わせる。
- 判定後の対象変更・撤回・席交代を実開始前に再照合する。開始と失効の競合順序は提供側を含む確定点で定義する。確定点を証明できない接続は実開始の受入未完。
- 既に開始した後の撤回は、後続の効果を止める要求と実行状態の照合へ結ぶ。取消要求を「停止済み」と表示せず、実行済みの変更が自動で戻ったことにしない。
- GitHub公開後/実開始後の応答喪失では同じ参照を照会する。新IDでの再投稿・再起動、AUN不明時のローカル代替起動を行わない。
- DB保存不能時は新しい効果を開始しない。既存実行の結果を失った場合は未確定を明示し、復旧後に実行元と照合する。故障中に保存できたと仮定しない。

### 4.1 実開始後の撤回を停止要求へつなぐ

1. 有効な撤回/取消/失効を観測したら、その根拠と元の試行へ、未送付を含む対象の開始要求と実行参照を対応付ける。同じ対象の新規開始・後続効果の許可は停止し、既に観測したRUNNINGを消さない。実行有無が不明でも新しい開始で確認しない。
2. 対象ごとに`stop`の要求参照と根拠/範囲を耐久保存する。開始要求とは別の識別を持ち、同じ停止要求の再送/再起動では同一参照を保持する。同一参照に別対象/別内容を与えた場合は競合として拒否。席の現在の新実行へ送り直さず、元実行・世代を宛先にする。
3. 要求主体の現在の認証/対象scope/停止管理権限と、根拠の真正性/適用範囲を、送付側と実行側で検証する。開始許可の失効を停止管理権限の喪失と同一視しない一方、停止要求の本文だけで管理権限を与えない。必要権限なしは効果0で拒否し、権限を持つ実行管理担当と解除条件へ結ぶ。
4. 実行側は対象の後続効果抑止と送信済み/不明効果の照合を扱う。AUN接続ではAUNの実行管理へ、単独では同じ意味のローカル実行契約へ変換する。共通`begin_revoke`/`finish_revoke`をShirubeが無断実行したり、DB失効だけを外部停止と扱ったりしない。

| 返却/照会結果 | Shirube側の扱い・次行動 |
|---|---|
| 受付済み | `stop`を送付/受付済みとして保持し、同じ要求/実行へのreconcileへ。停止済みやCANCELLEDにはしない |
| 実効停止確認 / 未開始確定 | 対象とする全実行/効果範囲、元世代、発行元、抑止した新効果と既送信分の照合を証拠で確認。単なるACK・プロセス終了・stopped=trueでは足りない。作業自体の中止が有効に決まり未解決効果がなければCANCELLED。承認撤回だけなら、実行停止の事実と再判断待ちを保持し作業まで中止にしない |
| 既に終了 | 実行結果と実効果を取得してRESULT_RECEIVED/VERIFYINGへ結ぶ。停止成功・変更の巻戻し・工程合格には読み替えない |
| 拒否 | 対象違い/停止権限不足/競合を保持し、その是正先へ。対象・権限を勝手に広げて再送せず、元実行の観測は継続して区別 |
| 停止不能 / 未対応 | どの効果を抑止できないかと最後に確認した実行状態を残す。CANCELLEDや実効停止の受入にはせず、権限を持つ実行管理担当へ既存契約の隔離/手動処置の要否を一度返す。別方式の強制停止・補償操作を無断で実行しない |
| 応答不明 / 照会不能 / 実行中 | 元の停止要求と実行をreconcileで照会。新しい停止ID/開始IDや新しい世代へ置換しない。再送は提供側が同じ要求の冪等性と安全な再送条件を保証し、既存認可/予算内の時だけ。解決できなければ次担当/期限/解除条件つきの未確認を保持 |

保存不能で停止要求を確定できない場合も停止したとは表示せず、元実行と未抑止の可能性を実行管理担当へ返す。保存/外部の部分成功・再起動/restoreは元の停止参照から照合し、旧許可や失効前の世代を復活させない。履歴には要求主体、根拠、送付/受付/確認を別に残す。
停止要求後に本人判断が変わっても、停止の取消や旧試行の自動再開を推測しない。既存効果の照合後に現在の判断と計画から次作業を評価する。停止不能を一般承認でPASSにすること、実行済み効果を停止で巻き戻したとすることは禁止する。

## 5. 「進みます」で止めない継続処理

LLMが次のtoolを呼ぶ意欲や、最終返答をするかどうかに通常進行を依存させない。Shirube側の継続処理は、検証した終了/監査返却/回答/依存解消/起動時再照合を契機として、以下を実行する設計案。信頼した起動経路は§8で選ぶ。

1. 受け取った事実を対象版と元報告へ照合し保存する。前工程のVERIFIEDは§2.1の条件別照合へ結び、LLMの完了申告を代入しない。「案件全体が完了」とも分ける。
2. 現在計画の依存が満たされた作業を評価する。順序/優先順位が既決でない選択をLLMが埋めず、必要な人の判断へ結ぶ。独立した作業まで別作業の人待ちで止めない。
3. 条件成立ならNextActionを一意に記録する。前工程終了からこの記録までの停止を回復可能にする。既存判断の範囲で新しい「開始してよいか」を聞かない。
4. 記録した行動を実行側へ渡し、送付・受領・実開始を区別して更新する。AUN時のタスク配送/再試行の実装はAUN、単独時は選んだローカル接続へ委ねる。
5. 実開始の証拠を同じ試行へ照合する。期限内に未確認なら次行動をreconcileへ進め、実行側を照会する。起動していないことが契約上確定した場合だけ、既存認可/予算内で同じ要求の回復を試す。
6. 人の判断が必要なら一度提示して停止。通信/実行不明は外部確認待ち、実行系の不調は担当と解除条件を示す。期限/予算が未定なら無制限に動かさず契約不足を示す。

開始期限と操作別の回復予算は接続契約へ固定し、作者が任意の秒数を埋めない。連続非進捗のバックストップは既存規則の3回で停止し、同じ失敗を繰り返す理由にはしない。人待ちではこの3回を待たず直ちに停止する。
停止中に定期hold記録・同じ通知・新しい待機成果物を生成しない。回答や外部状態の変更を受領することは、待機作業を繰り返すこととは区別する。
状態変化または再起動時に、保存された未実行/未確認の次行動に加え、確認済み作業に対応する次行動の欠落も照合する。欠落なら現在の条件から同じ継続処理を再評価し、開始済みなら新たに起動しない。継続処理そのものが停止した場合に検知/再開できる実行主体・起動経路も、接続受入で必須確認する。記録だけあって動かす主体がない構成は不合格。
継続処理の実装例として、既存実行hostの終了/起動イベントを利用する案と、独立常駐の実行器を置く案を比較対象にする。前者は常駐部品を減らせるが終了後にイベントが届く証明、後者は起動/監視/停止の運用が必要。どちらも未選定で、LLMの追加指示だけで強制済みとはしない。

## 6. 現在地と利用者への返答

「Aは条件確認済み、Bは開始要求記録済み・実開始未確認。次担当X、照会対象Y、次回照合条件Z」のように、同じ記録から返す。未開始を進行中と表示しない。過去に確認した時点と現在の取得不能を分ける。
人待ちの原因/質問/回答者、依存待ちの提供物/担当/解除条件、差戻しの根拠/元試行/修正先を取得できること。自己申告の待機理由だけで止まらず、実際の未充足条件に結びつける。
