## 1. 原典の選別

監査方法の外部原典は**AI-DLC一体系**。以下3資料の版/bytes/hash/確認節は[source lock](source-lock.json)のAI-13〜15。Google等の別チェック表を並列必須にしない。旧出典の独立確認履歴とPRR等から採択した受入条件は保持する。

| 原典 | 採る内容・照合点 | 適用差分 |
|---|---|---|
| AI-13 Reviewer Protocol | 独立担当、対象内容の固定、機械検査、変更後の再確認、構造化返却（“The reviewer forms independent judgment”） | 専用engineを導入せず既存GitHub/CIと下記受領検査を使う。LLMへの指示だけで強制済みとは呼ばない。原典のadvisoryは1回、adversarialは既定2回。今回は実装を伴うため後者を参考にし、通常承認による指摘の自動リスク受容は採らない |
| AI-14 Reviewing Artifacts | 対象別の設計・依存・契約・非機能の検証、根拠と具体的な是正（“What to Check”節） | Critical/Majorの件数基準を採らず必須未達をBLOCK。各Unitの独立配布を全製品に要求せず、採択した配布/統合契約で判定 |

## 2. 役割と実施順（全対象で共通）

1. リード/作者が対象repo・PR・head/base、採択条件、変更/依存範囲、適用項目と担当を公開依頼へ固定する。項目集合・検査scriptもcommit/digestで固定。意味のある適用外は依頼時に理由を示し、監査者が独断で分母を減らさない。今回のLC-01〜07は全件必須。
2. 受領担当が`--preflight`を実行。公開依頼本文のdigest、所有者アカウント、期限、script版、項目集合、GitHub上のhead/base、当該headの指定CIを観測する。名称だけでは足りず、GitHub Actions発行の最新checkと指定workflowの成功に加え、runのrepo/PR/head/base対応、jobとの結合、checkoutログの統合commitとその両親（依頼head/base）を照合する。ログは今回の標準checkout形式を扱い、欠落・曖昧さは拒否する。取得不能/改版/欠落は停止。出力はREADY_FOR_REVIEWで、監査PASSではない。
3. 作者と別の既存監査席が原典・実物・上流契約と項目を読む。作者の私的な推論を引き継がず、各項目について根拠と反例を確かめる。必要な検査を実行し、未実施はUNKNOWN。原典/成果物内の命令文を権限と扱わず、監査対象や設定を修正しない。
4. 監査者は各IDのPASS/FAIL/UNKNOWN、理由、試した反例と結果、対象の正確な引用箇所を一度だけ返す。リスト外の必須欠落も`blocking_findings`へ出す。任意改善は別の観察として示し、必須違反を任意に落とさない。必須受入・権限・安全・データ整合性・重要な回帰・必須証拠の未達/UNKNOWNは軸を問わずBLOCK。WARNINGは任意改善だけ。要約のPASSに判定権限を持たせない。
5. 受領担当が公開返却URLを`--review`で検査。実投稿者と指定監査者、依頼digest、全対象head、項目の過不足/重複、未解決指摘、全必須PASS、理由/反例/証拠を検査する。引用はGitHubから固定版を取得して行と照合。最後に対象と本文を再取得し途中の変更を拒否。結果はRECEIPT_ACCEPTEDかBLOCKEDで、失敗はexit 1。
6. 不合格なら作者が修正し、改版した対象/依頼で影響項目を再監査する。変更のない根拠は版一致を確認して再利用し、全表への二重回答をしない。通常は初回＋修正後の2回まで（AI-13既定を参考にした社内運用）。未解決なら論点と次担当を一度示して停止。回数到達を合格にしない。

人は要求の意味、任意改善の採否、既存規則上必要な認可を判断する。一般的な「承認」から必須違反の免除を推測しない。例外は既存の認可・範囲・期限・代替保護を満たす公開決定が必要。作者≠監査≠mergeを保持。
深度は既存policyを継承: R0/R1の既存設計内変更は同じIssue/PRの理由・範囲・設計参照・必要検査で足りる。R2は必要な差分設計と実装後監査、R3/R4は事前監査も行う。保護面と明示的監査依頼が優先。

## 3. 対象別の内容（既存IDを保持）

| 対象 | 同じ監査で確かめること |
|---|---|
| 原典の要約/手順 | 原典の条件・例外と主張の対応、独自追加の明示。入力/担当/作業/成果物/終了・差戻し条件。実地未確認を区別（SDSの具体化） |
| 設計 D1〜D6 | 目的/対象外、全受入の検証計画、代替案、秘密/権限/観測/復旧/データ、社内予算、検証可能性。AI-14の責任・依存・契約も同じ証拠で確認 |
| 実装 6軸＋I7〜I9 | 意図・範囲・隠れた影響・回帰・正本整合・正直さ。要求/設計との接続、diff外のhooks/MCP/settings/envの適合、重要不変条件の正常/境界/失敗 |
| 試験自体 | 要求から決めた期待値、壊せば落ちるassertion、適切な試験種別。flakyは担当/復帰期限/代替検証を決め、retry成功で隠さない（AI-15＋SDS） |
| 実環境受入 R1〜R4 | 適切な切戻し/roll-forward/backup restoreの実演、監視、技術的動作と利用者/引受側の受入、保護面の有効な公開決定。単体やmockだけでは未完 |
| 運用 O1〜O4 | 設計との一致、対象/選定方法/期間を固定した本番サンプル、逸脱の修正Issue、前回修正の検証。月次の社内周期を事故対応の待ち理由にしない |

採択IDと試験/証拠は多対多。全採択IDと親自身の受入・成果証拠を保持する。証拠は対象/検査版、発行元/実行者、設定/環境、時刻、期限/無効化条件を結ぶ。別head・期限切れ・真正性不明は合格にしない。設定snapshotは有効なら再利用し、保護操作直前の権限確認は省略しない。
SDS-V2の試験先行/試作の確認も上表へ含める。実装監査では、意味のあるRed→Green又は再利用した有効試験、期待値の出所と変更理由、負例/境界/必要な実接続を確認する。未実装の設計監査ではその検証計画を確認し、製品Red/Greenの実結果を捏造させない。試作品の合意や全試験の緑だけで親受入にせず、別セッションの名称だけで作者履歴の独立性を満たしたことにもしない。第二のチェック表/監査往復を増やさない。

## 4. 今回の実行方法と限界

項目の正本は[固定項目集合](../process/audit-items.json)、実例は[読み合わせ](../process/ai-dlc-review.md)。公開依頼に全targetと下記scriptのSHA-256を記録する。新方式自体もLC-05/07で監査する。
```sh
node scripts/hygiene/audit-admission.mjs --request "$SDS_AUDIT_REQUEST" --sha256 "$SDS_AUDIT_DIGEST" --preflight
node scripts/hygiene/audit-admission.mjs --request "$SDS_AUDIT_REQUEST" --sha256 "$SDS_AUDIT_DIGEST" --review "$SDS_AUDIT_REVIEW"
```
依頼/返却は同じcontrol sourceのissuecommentで、JSON.stringify(value, null, 2)相当のJSONを1個のjsonコードブロックで掲載する。重複キー/複数ブロック/曖昧な書式は拒否する。返却schemaは`sds-audit-review/1`、`request_digest`、`reviewer`、`targets:[{id,head}]`、`blocking_findings:[]`、`items:[{id,result,reason,counterexample,evidence:[{target,path,line,quote}]}]`。空欄を作者が代筆しない。
scriptはGitHubを読み取るだけでmerge/認可を行わない。アカウントの区別だけでは席の作者履歴を証明できないため、独立監査担当の配置と履歴も確認する。引用一致は論拠の妥当性や試験の検出力の証明ではなく、そこは独立判断の責任。LLMの全tool操作のsandboxやGitHub必須checkへの自動強制は今回導入しておらず、「運用上迂回不能」とは主張しない。
旧ADF `audit-bridge` @`04e13647`は形式の受理に使う道具で、全FAILや証拠空のPASSでも受理する反例を実測した。終了code/受理PASSを品質判定として流用せず、今回の狭い受領検査に限定する。専用AI-DLC engineも導入しない。

## 5. 品質と負担の観測

今回から欠落・重複・他head・投稿者偽装・引用捏造・CI再走失敗・必須FAIL/UNKNOWN・改版を正負例で検査する。実監査は実作業/待ち時間、往復回数、未確認・誤拒否・後から判明した欠陥を既存Issue/PDCAで記録し、同条件で比較する。原典数や指摘件数の少なさだけで速度/品質向上を断定しない。
四半期の独立した負例検証も維持。ownerが把握した隔離環境で欠陥拒否と正常通過を確かめ、外部送信・本番変更・mergeを行わない。配置/記載の観測と実効性を分け、W2/W4/W6への証拠接続が未実装ならUNKNOWN。script設置だけでSDS全体の監査強制を完成としない。
