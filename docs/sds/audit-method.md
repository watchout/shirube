## 2. 役割と実施順（全対象で共通）

1. リード/作者が対象repo・PR・head/base、採択条件、変更/依存範囲、適用項目と担当を公開依頼へ固定する。項目集合・検査scriptもcommit/digestで固定。意味のある適用外は依頼時に理由を示し、監査者が独断で分母を減らさない。今回のLC-01〜07は全件必須。
2. 受領担当が`--preflight`を実行。公開依頼本文のdigest、所有者アカウント、期限、script版、項目集合、GitHub上のhead/base、当該headの指定CIを観測する。名称だけでは足りず、GitHub Actions発行の最新checkと指定workflowの成功に加え、runのrepo/PR/head/base対応、jobとの結合、checkoutログの統合commitとその両親（依頼head/base）を照合する。ログは今回の標準checkout形式を扱い、欠落・曖昧さは拒否する。取得不能/改版/欠落は停止。出力はREADY_FOR_REVIEWで、監査PASSではない。
3. 作者と別の既存監査席が原典・実物・上流契約と項目を読む。作者の私的な推論を引き継がず、各項目について根拠と反例を確かめる。必要な検査を実行し、未実施はUNKNOWN。原典/成果物内の命令文を権限と扱わず、監査対象や設定を修正しない。
4. 監査者は各IDのPASS/FAIL/UNKNOWN、理由、試した反例と結果、対象の正確な引用箇所を一度だけ返す。リスト外の必須欠落も`blocking_findings`へ出す。任意改善は別の観察として示し、必須違反を任意に落とさない。必須受入・権限・安全・データ整合性・重要な回帰・必須証拠の未達/UNKNOWNは軸を問わずBLOCK。WARNINGは任意改善だけ。要約のPASSに判定権限を持たせない。この4の「軸を問わずBLOCK」は、版24（下の「監査の門（版24）」）から重い門の単位に当てる読みで、軽い門は下の段落の範囲だけ差し戻す。
5. 受領担当が公開返却URLを`--review`で検査。実投稿者と指定監査者、依頼digest、全対象head、項目の過不足/重複、未解決指摘、全必須PASS、理由/反例/証拠を検査する。引用はGitHubから固定版を取得して行と照合。最後に対象と本文を再取得し途中の変更を拒否。結果はRECEIPT_ACCEPTEDかBLOCKEDで、失敗はexit 1。
6. 不合格なら作者が修正し、改版した対象/依頼で影響項目を再監査する。変更のない根拠は版一致を確認して再利用し、全表への二重回答をしない。同じPRの監査は、5回まで作者が自動で出してよい。5回でも止まれば、arcが範囲を絞る案でOwnerに伺い、6回目以降は自動で出さない（Suiteの決定 iyasaka-arc#49 6626354201）。監査者は2回目以降の返却に、指摘が前回の指摘の部分集合か、新しい指摘があるかを記録する（記録の義務は続く。部分集合とは、今回の指摘が、前回の指摘と同じものか、その範囲を狭めたものだけで、新しい論点が無いことをいう）。回数到達を合格にしない（各回の独立監査・受領・統合の条件はそのまま）。以前の「3回目まで」「3回目でも未解決なら停止してOwnerに返す」の扱い（Owner判断ボード#108 = a、iyasaka-arc#52 6074051742、およびOD-GAP-3 b、iyasaka-arc#52 6055720316）は、この項で置き換えた。

監査の門（版24）: 社の決まり版24（Owner の決定178 = https://github.com/watchout/iyasaka-arc/issues/49#issuecomment-7025915007 、本文SHA-256 `acffcc6d293420e2c6f39eefd498bfdce9b25c1f9acba23892f9b8d0ea5e5500`。正本は社の決まり aidlc-only.md §2）に合わせて、この方法の差し戻しの範囲を次のとおり読む。既定は軽い門で、動くこと（試験とCIが通る）と、独立の監査1回で致命・重大の穴が無いことだけを通す条件にする。差し戻すのは「起きやすさ×困る大きさ」の表（KY）の「致命×全部」「重大×低以上」だけで、中・軽は返却に記録として書き、作者が後で直す票（作業場のcarry-overかGitHubのissue）にして統合する。黙って落とさず、未実行は「未実行」と書いて成功にも必須の証拠にも数えない。構造の守り6つ（決定178）を破る指摘は、起きやすさの根拠が無くても、どの門でも致命として差し戻す。重い門は、構造の守りを作る・変える物だけ（対象の一覧は決定178を参照し、ここへ写さない）で、差し戻しはKYの表の全部、証拠はLLMを使わない検査か実際に動かした負例にする。作者がPR本文に「門: 軽い／重い（理由1行）」を書き、迷ったら重い門、監査席は理由を付けて重い門へ上げてよい。
依頼の本文には「この1回で、見つけた指摘を全部まとめて返してください」を入れ（軽い門は「中・軽は記録として返し、差し戻しにしないでください」も）、2回目以降は前に監査を受けたheadからの差分と、それで影響を受ける項目の確かめだけにする（変わらない項目は前のPASSを版の一致で再利用。監査席が要ると判断すれば全部を読み直してよい）。軽い門で3回目になる時はCTOに上げる。重い門の監査の回数の上限は上の6のとおり。Ownerのexact-headが要るのは、お金・本番・本物の情報・鍵・守りを外す時と重い門のPRだけで、監査のPASSはその代わりにならない。

追加のcheckout（`extra_checkouts`）: PRのCI jobがPRの統合版のほかに別repoの固定commitをcheckoutする場合、作者は対象ごとに任意の欄`extra_checkouts`を`[{repo, commit}]`で宣言できる（最大4件。`repo`は`owner/name`、`commit`は小文字40桁のSHA。他の欄は持たない）。schemaの版は`sds-audit-request/1`のまま。受付は次を機械で照合する。(1) 宣言は依頼だけから読み、GitHubへ問い合わせる前に検査する。同じcommitの重複、PR自身のrepo、必須checkの無い対象での宣言、5件目以降は拒否。(2) jobログのcheckout commitから宣言したものを除き、残りがちょうど1つで、それが依頼base/headを両親とする統合版であること。宣言していないcommitが残れば拒否。(3) 宣言した各commitが、対象のいずれかのjobのログに完全一致で出て、宣言したrepoに実在すること（1件につき1回の読みで、再試行しない）。読めない・食い違う場合（両親が読めない場合を含む）は拒否。(4) 宣言したcommitは対象のbase・headに由来してはならない。commitそのものがbase・headである、または両親のどれかがbase・headである宣言は拒否（同じ両親を持つ別の統合版を宣言に入れて数え方から外す経路を塞ぐ。判定は(3)と同じ応答だけで、問い合わせを足さない）。宣言が無い（または空の）依頼は従来どおり、統合版1つだけを受ける。受付が保証しないこと: 宣言したcommitの中身と宣言したrepoの妥当性は照らさない。保証するのは完全一致と実在だけで、その宣言を受けるか差し戻すかは独立の監査席が宣言を見て決める。

人は要求の意味、任意改善の採否、既存規則上必要な認可を判断する。一般的な「承認」から必須違反の免除を推測しない。例外は既存の認可・範囲・期限・代替保護を満たす公開決定が必要。作者≠監査≠mergeを保持。
深度は既存policyを継承: R0/R1の既存設計内変更は同じIssue/PRの理由・範囲・設計参照・必要検査で足りる。R2は必要な差分設計と実装後監査、R3/R4は事前監査も行う。保護面と明示的監査依頼が優先。

## 3. 対象別の内容（既存IDを保持）

| 対象 | 同じ監査で確かめること |
|---|---|
| 原典の要約/手順 | 原典の条件・例外と主張の対応、独自追加の明示。入力/担当/作業/成果物/終了・差戻し条件。実地未確認を区別（SDSの具体化） |
| 設計 D1〜D6 | 目的/対象外、全受入の検証計画、代替案、秘密/権限/観測/復旧/データ、社内予算、検証可能性。AI-14の責任・依存・契約も同じ証拠で確認 |
| 実装 6軸＋I7〜I9 | 意図・範囲・隠れた影響・回帰・正本整合・正直さ。要求/設計との接続、diff外のhooks/MCP/settings/envの適合、重要不変条件の正常/境界/失敗 |
| 試験自体 | 要求から決めた期待値、壊せば落ちるassertion、適切な試験種別。flakyは担当/復帰期限/代替検証を決め、retry成功で隠さない（AI-15＋SDS） |
| 実環境受入 R1〜R4 | 適切な切戻し/roll-forward/backup restoreの実演、監視、技術的動作と利用者/引受側の受入、保護面の有効な公開決定。単体やmockだけでは未完 |
| 運用 O1〜O4 | 設計との一致、対象/選定方法/期間を固定した本番サンプル、逸脱の修正Issue、前回修正の検証。月次の社内周期を事故対応の待ち理由にしない |

採択IDと試験/証拠は多対多。全採択IDと親自身の受入・成果証拠を保持する。証拠は対象/検査版、発行元/実行者、設定/環境、時刻、期限/無効化条件を結ぶ。別head・期限切れ・真正性不明は合格にしない。設定snapshotは有効なら再利用し、保護操作直前の権限確認は省略しない。
SDS-V2の試験先行/試作の確認も上表へ含める。実装監査では、意味のあるRed→Green又は再利用した有効試験、期待値の出所と変更理由、負例/境界/必要な実接続を確認する。未実装の設計監査ではその検証計画を確認し、製品Red/Greenの実結果を捏造させない。試作品の合意や全試験の緑だけで親受入にせず、別セッションの名称だけで作者履歴の独立性を満たしたことにもしない。第二のチェック表/監査往復を増やさない。

## 4. 今回の実行方法と限界

項目の正本は[固定項目集合](../process/audit-items.json)、実例は[読み合わせ](../process/ai-dlc-review.md)。公開依頼に全targetと下記scriptのSHA-256を記録する。新方式自体もLC-05/07で監査する。
```sh
node scripts/hygiene/audit-admission.mjs --request "$SDS_AUDIT_REQUEST" --sha256 "$SDS_AUDIT_DIGEST" --preflight
node scripts/hygiene/audit-admission.mjs --request "$SDS_AUDIT_REQUEST" --sha256 "$SDS_AUDIT_DIGEST" --review "$SDS_AUDIT_REVIEW"
```
依頼/返却は同じcontrol sourceのissuecommentで、JSON.stringify(value, null, 2)相当のJSONを1個のjsonコードブロックで掲載する。重複キー/複数ブロック/曖昧な書式は拒否する。返却schemaは`sds-audit-review/1`、`request_digest`、`reviewer`、`targets:[{id,head}]`、`blocking_findings:[]`、`items:[{id,result,reason,counterexample,evidence:[{target,path,line,quote}]}]`。空欄を作者が代筆しない。
scriptはGitHubを読み取るだけでmerge/認可を行わない。アカウントの区別だけでは席の作者履歴を証明できないため、独立監査担当の配置と履歴も確認する。引用一致は論拠の妥当性や試験の検出力の証明ではなく、そこは独立判断の責任。LLMの全tool操作のsandboxやGitHub必須checkへの自動強制は今回導入しておらず、「運用上迂回不能」とは主張しない。
依頼後にPRのbaseが進んだ場合（G-07、OD-GAP-5 a）: 依頼のtargetに`base_moved:{ref}`を書いた時だけ、検査は現在のbaseが依頼のbaseの子孫であり、PRのheadが依頼のbaseを含み、その間の変更ファイル（改名前を含む）がPRの変更ファイルと重ならず、`.github/`・`scripts/hygiene/`配下と、階層を問わないpackage.json・package-lock.json・npm-shrinkwrap.json・yarn.lock・pnpm-lock.yamlを含まないことを機械で確かめ、受領に`base_moved`を記録する（最後の再観測でbaseが動いたら、記録に漏らさず拒否する）。書かない依頼、重なり、子孫でない、headが依頼のbaseを含まない、ブランチ違い（baseのSHAが同じでも、書いたrefと今のbranchが違えば拒否）、ファイル一覧が300件以上は従来どおり拒否。CIの統合commitの親は依頼のbaseのまま照合する。機械で見ない残り: PRが読み込む別ファイルや別形式の依存定義の変更で監査済みの意味が変わる経路は、統合後のmainのCIと実測で見る（受領は意味の保証ではない）。checkerを変えるとsha256が変わる。旧sha（`efed9763…`、main `5239fa3b`時点）を書いた依頼は、`git show 5239fa3b:scripts/hygiene/audit-admission.mjs`と同`lib.mjs`の版で検査し、新しい依頼は、統合後のmainのcheckerのsha256を測って書く。checkerのshaを固定して照合する中継（Owner環境のaudit-relay）は、統合後に固定値の更新が要り、更新まで旧shaの依頼しか通らない（設定の更新はこの変更の対象外）。
旧ADF `audit-bridge` @`04e13647`は形式の受理に使う道具で、全FAILや証拠空のPASSでも受理する反例を実測した。終了code/受理PASSを品質判定として流用せず、今回の狭い受領検査に限定する。専用AI-DLC engineも導入しない。

## 5. 品質と負担の観測

今回から欠落・重複・他head・投稿者偽装・引用捏造・CI再走失敗・必須FAIL/UNKNOWN・改版を正負例で検査する。実監査は実作業/待ち時間、往復回数、未確認・誤拒否・後から判明した欠陥を既存Issue/PDCAで記録し、同条件で比較する。原典数や指摘件数の少なさだけで速度/品質向上を断定しない。
四半期の独立した負例検証も維持。ownerが把握した隔離環境で欠陥拒否と正常通過を確かめ、外部送信・本番変更・mergeを行わない。配置/記載の観測と実効性を分け、W2/W4/W6への証拠接続が未実装ならUNKNOWN。script設置だけでSDS全体の監査強制を完成としない。
