## この文書の使い方（先に読む）

- 設計手段の既定から外れる場合は、理由・代替案・守る不変条件の証拠を既存 PR に残す。
  **記録だけで例外は成立しない。** 必須受入・権限・安全・データ整合性・重大回帰・必須証拠の未充足は BLOCK。
  例外が認められる範囲でも、有効な承認・期限・代替保護が必要。S8/S9 と保護認可を免除しない。
- **言語・framework・DB 製品・test runner を指定しない。** どの実装にも当てはまる形だけを置く。
- 機械検査の未導入は規範の免除や合格を意味しない。機械による強制と独立監査の実証を分け、
  必須条件は有効な手動証拠等で確認する。未確認は UNKNOWN とし通過根拠にしない。
- **1 つの規則を 2 つの問題に広げない。** 各節に「これは〜を意味しない」を置いてある。そこを超えて適用しない。

## S1 — 参照されている行は消さない。消す必要があるものは分けて置く

**目的は整合性が壊れないこと。** そのための既定は次の 3 つ。

1. **参照されうる実体は、削除ではなく引退させる。** 何が起きたかを名前にした列で状態を表す
   （`disabled_at` / `revoked_at` / `expires_at` / `archived_at` / `status`）。行が残るので
   外部キーは壊れず、他所に保存された id も切れない。
2. **消さなければならない中身は、参照される identity と別の表に置く。** 安定した id を持つ
   identity 行は残し、消す必要がある中身（個人データなど）を satellite 表に置いて、そちらを
   実際に消す（暗号消去でもよい）。これで「参照は切れない」と「消せる」を同時に満たす。
3. **それでも物理削除するなら、関係ごとに `ON DELETE` を選ぶ。** 既定は `RESTRICT`。参照元を
   すべて列挙してから消す。`CASCADE` は「子は親と一体で単独では意味を持たない」と言える関係に
   だけ使い、**履歴・監査の表へ CASCADE しない**。

履歴は追記専用の別の表に置く。運用側の行を消しても履歴が消えない形にする。

**これは「ソフトデリート禁止」を意味しない。** ゴミ箱のように「復元」が利用者向けの機能である
記録の種類には、宣言して使ってよい。禁じるのは、汎用の削除フラグを**既定の仕組み**として
全表に敷くこと。

**なぜ既定にしないか**: 一律の削除フラグは、整合性の問題を解かずに別の問題へ移す。
全クエリに除外条件が要り（1 箇所漏れれば削除済みが見える）、一意制約が壊れ（同じ値で再登録できない）、
外部キーの意味が曖昧になり（削除済みの親を参照する子は正常か異常か型で表せない）、
消去請求への対応も別に要る。引退列だけでも無条件検索には行が現れ、一意性の再利用は衝突しうる。
引退の意味づけに加え、検索時の状態条件・一意性の対象・参照整合性・消去/復元の方針を設計し試験する。

**実測 2026-09-22 / `agent-comms-mcp`**: `deleted_at` / `is_deleted` は 0 件。
`disabled_at` 7・`revoked_at` 4・`expires_at` 5・`archived_at` 1、`status` を持つ表 15。
satellite 表（`agent_identity_keys` / `agent_provider_identities` / `connector_credentials` /
`oauth_access_tokens` 等）が identity と分かれている。外部キーは関係ごとに
`SET NULL` 20 / `CASCADE` 17 / `RESTRICT` 10。既にこの形。
ただし `agents` を参照する外部キーのうち 11 本が `CASCADE` で、identity 行を物理削除すると
11 表の行が連鎖して消える。だから `agents` は状態で引退させ、削除経路を通常運用に持たない。

**機械検査**: 削除経路を通したあとに宙に浮いた参照が 0 件であること。
参照されうる実体の型が引退状態を持ち、通常運用に削除経路を持たないこと。
運用表から履歴・監査表への `CASCADE` が 0 件であること。
汎用の削除フラグを持つ表は、その記録の種類が復元機能を宣言していること。

## S2 — 必要性を確かめて抽象化する

3例目は判断の目安で、強制する個数ではない。現契約・保護境界・試験分離に必要な抽象は、理由を示せば初回から使える。将来推測だけの一般化を避ける。
意味の核の一元性は S3 を参照し、adapter ごとに別の判断規則を置かない。digest 一致だけでは実際に同じ核を呼ぶことの証明にならない。呼出経路と契約試験で確認する。

## S3 — 知識の重複は禁止、文字列の重複は許容

判断規則・閾値・決定表・理由コードの集合は、**1 箇所にだけ存在する**。他はそこを参照する。
見た目の似たコードは、無理に共通化しない。

**これは「同じ記述を 2 度書かない」の全面適用を意味しない。** 2 つの関数がたまたま似ているのは重複ではない。
同じ判断が 2 か所で下せる状態だけが重複。

**機械検査**: 規則の値（閾値・コード集合・分母）が 2 か所以上に literal で現れたら指摘。

---

## S4 — 時刻・乱数・識別子は明示入力

意味の核は、現在時刻・乱数・UUID を自分で取得しない。**呼出側が渡す。** 周囲から拾わない。

**これは adapter や I/O 層での禁止を意味しない。** 時計を読むのは adapter の仕事。
核が読まない、という意味。LLM の回答本文にバイト一致を要求しない。AI回答品質の反復評価はT5、権限境界の決定論的検査はP12/T6に接続する。

**なぜ**: 決定性が要る。同じ入力で同じ出力にならないものは、fixture で証明できず、再実行で検証できない。
**実測**: AUN の D1（起動ごとの UUID を launcher が渡す）、反映機構 gen2（`now` を必須入力にして
`FIXTURE_NOW` で固定、2 回実行バイト一致）。gen1 は `now` が無く、期限判定を検証できなかった。

**機械検査**: 意味の核のファイルに `Date.now` / `new Date()` 引数なし / `Math.random` / `randomUUID` が現れたら指摘。

---

## S5 — 宣言された値は証拠ではない

観測側の値は、**観測された事実から再計算する**。宣言された値（desired・期待値・設定）を観測側へ写さない。

結果は「一致」「不一致」「観測できず」の 3 値を持つ。**観測できずを成功に読み替えない。**
外部への問い合わせには期限と総予算を宣言し、使い切ったら「観測できず」を返す。

保存証拠は、実物から再計算可能で、発行元・実行者・対象版・検査版・設定・環境・観測時刻・有効期限/無効化条件が検証できる範囲で再利用してよい。
対象の変更・期限切れ・未観測では再取得する。生きた権限や設定、操作直前の認可を古い cache で代用しない。

**なぜ**: 宣言値を写すと、検査は常に一致する。検査していないのと同じになる。
**実測**: 反映機構 gen1 の監査指摘 F02（宣言 digest が観測側へ echo されていた。
監査席が中身を書き換えた反例でも「一致」になった）。AUN の同型指摘。
gen1 は観測の期限も持たず、超過を成功として扱えた。

**機械検査**: 観測側の digest が観測 field だけから計算されていること。負例（中身を変えた入力）が
不一致になること。予算超過の入力が「観測できず」になること。

## S6 — schema 変更は互換期間と実証された復旧を持つ

schema 変更ごとに、rollback / roll-forward / backup restore から必要な整合性と復旧目標を満たす方法を選び、対象環境で実証する。不可逆な消去を down 可能と偽らない。消去要求に反するデータ復元も行わない。
変更の途中で、**旧コードと新コードが同じ schema に対して動く**こと（追加 → 移行 → 削除の順）。

**これは破壊的変更の禁止を意味しない。** 段階に分けることの要求。

**なぜ**: 片方向の変更は、稼働中のコードを壊す。
**実測**: AUN の監査指摘 P1-1。新 migration が 2 つの表への INSERT を全面拒否する一方、
稼働している通常経路はその INSERT に到達していた。追加の前に削除をした形で、典型的な失敗。

**検証**: 選んだ復旧方法で必要なデータ・整合性・旧新の契約が回復し、採択した復旧目標を満たすこと。down の存在や exit 0 だけで合格にしない。
削除・拒否を含む変更は、同居期間の宣言を持つこと。

## S7 — 外部への効果は冪等

外部に効果を出す操作は、**送信前**に冪等キーを作る。同じキーの再送は元の結果を返し、効果は 1 回。
応答が失われた場合は**照会してから読む**。盲目的な再送をしない。新しいキーを作らない。

**これは読み取りへの適用を意味しない。** 副作用の無い読みには不要。

**なぜ**: 応答喪失と失敗は区別できない。区別せずに再送すると二重に効果が出る。
**実測**: Onza の受入定義 C17 / C28 / C30、Totonoe T2 の U2、Common の注文 API。いずれも同じ形。

**機械検査**: 同一キー同一内容の再送で効果が 1 回、同一キー別内容が衝突として拒否されること。

---

## S8 — 失敗を隠さない

必須の工程は、失敗したら全体を失敗させる。`|| true`、必須 step の `--if-present`、
`continue-on-error`、無条件 PASS、表明の無い test を置かない。
timeout・skip・cancel・不明を成功として数えない。

**これは警告や任意 step の禁止を意味しない。** 必須と任意を宣言し、必須だけを止める条件にする。

**実測**: 5 製品 repo に `check:no-failure-hiding` が既にあり、#630 の P5 が同じ内容を要求している。

**機械検査**: 既存の `check:no-failure-hiding` 系。CI の必須 step 一覧と実行結果の突合。

---

## S9 — 資格情報は用途ごとに最小

読み取りしかしない経路には、読み取りだけの資格情報を渡す。
書ける資格情報を、test プロセスや汎用の build step に渡さない。AI の tool 実行・記憶/検索・tenant 境界にも適用し、許可外の操作が外部効果の前に拒否される証拠へ接続する。
どの job が何を受け取るかを宣言する。

**これは資格情報の分割を全経路に要求することを意味しない。** 書ける資格情報の配布先を絞る、という意味。

**実測**: #630 の据付手順 7（metadata 取得 job だけに read-only 資格情報、test プロセスには渡さない）。

**機械検査**: workflow の各 job が受け取る secret の一覧と、その job が行う操作の突合。

---

## 適用の順序

1. 新しく書くものは最初からこの形にする。
2. 既にあるものは、触る時に直す。まとめて直す計画を作らない（それ自体が S2 違反になる）。
3. 機械検査の強制段階は既存の enforcement graduation と採択記録に従う。report-only は自動 gate の状態を表し、必須の安全・認可・受入条件の免除ではない。検査名の登録だけで強制済みとしない。
4. この標準を変えるのは owner 裁定。arc は差分案を出すだけ。

## 一行記憶

**消し方は記録の種類ごとに決める。抽象は必要性で決める。知識は 1 箇所。時刻は渡す。
宣言は証拠でない。schema は同居させる。外部効果は冪等。失敗は隠さない。鍵は用途ごと。**
